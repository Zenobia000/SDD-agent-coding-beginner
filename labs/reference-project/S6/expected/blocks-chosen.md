# 選了哪兩塊、為什麼 — rate-digest

> 對照重點：**你說得出為什麼選這兩塊**。不是裝得多。

---

## `/next` 說了什麼

```
你現在有：PRD、考卷、測試綠燈、抓取邏輯
你現在缺：資料存放（現在是寫 JSON 檔）

建議下一塊：db
為什麼：你的考卷有一題測冪等性（#9），但沒有真正的資料層就無法驗證
```

---

## 我選的兩塊

### ① `db` — 因為考卷第 9 題

冪等性（同一天重跑兩次不產生重複列）**沒有真正的資料層就是假的**。
現在寫 JSON 檔的做法，「重複」的定義很模糊。

有了 `UNIQUE(run_date, currency)` 約束後，冪等性變成 **DB 層保證**，
不是應用層祈禱。

### ② `etl` — 因為它是這個專案的本體

抽取 → 轉換 → **驗證** → 載入。
我原本的 code 有前兩段和最後一段，**唯獨缺 Validate**。

積木裡的 Validate 四類檢查直接可用：
```
① 筆數：這批 3 筆，跟上批比變動 0% —— 正常
② 非空：currency / rate / source 不可空
③ 型別範圍：rate > 0 且 < 1000
④ 唯一性：(run_date, currency) 無重複
```

---

## 我沒選的三塊，為什麼

| 積木 | 為什麼不選 |
|---|---|
| `api` | 只有我一個人用，跑 cron 輸出檔案就夠。**PRD 明寫不做多使用者** |
| `frontend` | 同上。純文字摘要就是需求 |
| `auth` | 沒有多使用者就沒有授權問題 |

> **這三個「不選」的理由全部來自 S1 決策卡的「不做什麼」欄位。**
> 那一欄在這裡發揮作用了。

## 接點：這兩塊怎麼接

```
三個來源 ──Extract──> 原始 HTML
              ↓ Transform（正規化）
          數值 dict
              ↓ Validate ★ ← etl 積木給的
          驗證過的 dict
              ↓ Load（upsert）
          SQLite ← db 積木給的
              ↓
          摘要輸出
```

**接點在 Validate → Load 之間**：
Validate 不過就**不進 Load**，保留上一版。這條在 `docs/db-schema.md` 寫死了。
