## 分流表

| 功能 | 寫得出 check()？ | 代價 | 落在 | 為什麼 |

| 排出一份合理的行程 | ✗ 「合理」沒有標準答案 | 低 | **AI + 考卷** | 常識判斷，但可抽樣驗證 |
| 標 `cash_only` / `card_ok` | ⚠️ 部分 —— 有明顯正負例 | 中 | **AI + 考卷** | 神社門票必定現金、百貨必定收卡，中間地帶才是判斷 |
| 加總 cash_only 金額 | ✓ 算術 | 高 | **程式** | 加法不需要 AI |
| 乘以預備金係數 | ✓ 算術 | 高 | **程式** | 同上 |
| 今日匯率 vs MA30 → 燈號 | ✓ 死規則 | 高 | **程式** | 大於/小於的比較 |
| 幣別換算與捨去 | ✓ 算術 | **高** | **程式** | 錢的計算絕不交給 AI |
| 預算超支檢查 | ✓ 比大小 | 中 | **程式** | 同上 |
| 抓即時匯率 | ✓ API 回什麼就是什麼 | 中 | **程式** | 這是 I/O，不是判斷 |
| 生成給使用者看的文案 | ✗ | 低 | **AI**（不需考卷） | 錯了只是不好看 |

## 為什麼「加總」不能交給 AI

這是學員最常犯的錯：覺得反正都要叫 AI 產行程了，順便叫它算總額比較快。

```
❌ 「請產出行程，並計算現金總額」

   問題一：算錯了你不會發現 —— 數字看起來都很合理
   問題二：同一份行程跑兩次可能得到不同的總額
   問題三：改「預備金從 10% 改成 15%」要重跑整個生成
```

```
✅ AI 只負責標每一項是 cash_only 還是 card_ok
   程式負責 sum()

   · 加法永遠不會錯
   · 改係數是改一個常數，不用重跑 AI
   · 可以寫測試釘住「空清單回 0」「單項回該項金額」
```

**一句話：算術的事交給算術。**

## 為什麼「標付款方式」不能交給程式

反過來的錯誤也有人犯：想用一張「哪些店收現金」的對照表取代 AI。

```
❌ 維護一份「日本收現金商家清單」

   問題一：永遠不完整，而且會過期
   問題二：新開的店查不到
   問題三：這份清單本身就是一個要維護的產品
```

這件事需要**世界知識 + 常識推論**（「路邊攤」「神社」「個人經營的居酒屋」多半收現金），
那正是 AI 擅長的鋸齒面。

**所以它留在 AI 那半——但配一份考卷，因為它會錯。**

## `unknown` 這個值為什麼重要

schema 的 `payment` 有三個值，不是兩個：

```
"cash_only" | "card_ok" | "unknown"
```

**沒有 `unknown` 的話，AI 遇到不確定的店會被迫二選一，而它會猜。**
猜錯了進到加總裡，你完全看不出來。

有了 `unknown`，程式可以：
- 把 unknown 的金額用**保守估計**（當成現金）算進去
- 在畫面上標出來，讓使用者自己判斷
- 統計 unknown 的比例——**太高就表示這趟行程的建議不可信**

> **設計原則**：讓「不確定」變成一個可以被下游處理的值，
> 而不是逼上游假裝確定。

## 三個外部依賴各自掛掉會怎樣

| 掛掉的 | 影響 | 預設行為 |
|---|---|---|
| LLM API | 產不出新行程 | 顯示上次的結果 + 明確說明「行程生成暫時無法使用」 |
| 匯率 API | 算不出燈號 | **換匯金額照樣算得出來**（它只需要行程），燈號顯示「暫無資料」 |
| 地圖 API | 少了距離估算 | 行程照出，移動時間標「未知」 |

**注意第二列**：因為錢的計算不依賴匯率 API，所以匯率掛掉時**核心價值還在**。

這是那條線畫對了的證據——**依賴越少的那半，越是你的核心**。
