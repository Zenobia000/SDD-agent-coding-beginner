# 循環工程四拍

## 結論卡

| | |
|---|---|

## 一、問題：對單次輸出許願

大部分人用 AI 寫程式的方式是：

```
下一次指令 → 看結果 → 不滿意 → 改指令 → 再下一次
```

這個迴圈**沒有記憶、沒有比較基準、沒有終止條件**。

實際會發生的：
```
Day 1：AI 改了 8 版，每版都「看起來不錯」
Day 2：發現第 3 版其實最好，但已經被覆蓋掉了
Day 3：想證明「新版比舊版好」，發現沒有共同的比較基準
Day 7：只能靠「我覺得」說服自己和團隊
```

**病因不是 prompt 寫得不好，是流程沒有收斂機制。**

## 二、四拍

```
① 劃邊界 Constrain  —— 一個範圍 / 一個評分 / 一個預算
② 放它跑   Run       —— 產候選，人不插手
③ 打分數   Score     —— 二元判準；程式能判就別問人
④ 收判斷   Decide    —— 看曲線、抽查最好的、決定收工
```

### 第①拍：三條乾淨限制

| 限制 | 鎖住什麼 | 沒有的後果 |
|---|---|---|
| **一個範圍** | 範圍 | 到處亂改，diff 大到無法 review |
| **一個評分** ★ | 目標 | 「感覺比較好」，證明不了有進步 |
| **一個預算** | 成本 | 無限重試燒 token |

**第二條最常被省略，也最致命。**

### 第②拍：放它跑

中途不要插手。

插手了會發生什麼：你分不清「變好了」是因為 AI 的改動，
還是因為你中途給的提示，還是因為隨機性。

**要能歸因，就不能在跑的過程中改變因。**

### 第③拍：打分數

**二元判準**，不要 1–10 分：

```
❌ 1–10 分 —— 不可重現。今天給 7 分，明天同一個東西給 5 分
✅ 對 / 錯 —— 可以加總成通過率：對的筆數 ÷ 總筆數
```

**能用程式判就別請 LLM。** LLM 當裁判不可重現、貴，而且會有偏誤。

### 第④拍：收判斷

人只做三件事：

1. **看曲線** —— 有沒有在進步？停滯了嗎？
2. **抽查最好的那個** —— 分數高不等於真的對
3. **決定什麼時候收工** —— 邊際效益遞減時就停

**第 2 件事最常被省略**，但它是防止「reward hacking」的唯一手段 ——
模型可能找到讓考卷過、但實際更糟的做法。

## 三、為什麼是「四拍」而不是「四步」

因為它會**重複**。

```
①→②→③→④→①→②→③→④→…
                 ↑
        分數不夠就回去再跑一輪
```

「步驟」暗示走完就結束。「拍子」暗示這是節奏，會一直循環。

**這個差別是循環工程和一次性開發的唯一分野。**

---

## 四、課堂怎麼用

8 小時跑六次，換六個對象：

| 站 | 對象 | 範圍 | 評分 | 預算 |
|---|---|---|---|---|
| S1 | 題目 | 一個痛點 | 五條可判斷的成功條件 | 55 分鐘 |
| S2 | 規格 | PRD | 考卷有 10 筆且含邊界 | 55 分鐘 |
| S4 | 程式 | 一個目錄 | 考卷通過率 | 5 輪 |
| S5 | 資產 | 一個 hook | 實測擋得下且不誤殺 | 20 分鐘 |
| S6 | 積木 | 兩塊積木 | 通過率不退步 | 45 分鐘 |
| S7 | 交付 | 全專案 | 五道閘門全綠 | 25 分鐘 |

**同一組動作重複六次 = 肌肉記憶。**

## 五、常見誤解

### 「我的工作沒有客觀評分標準」

多數時候這表示**還沒拆到可觀察的層次**：

```
「文案要好」            → 寫不出 check() ❌
    ↓ 拆
「≤ 30 字」             ✓
「包含產品名 + 動詞」    ✓
「不出現這 10 個禁用詞」  ✓
```

拆完之後，「好」變成三個 yes/no。剩下真正主觀的部分交給人挑。

### 「跑迴圈很花時間」

比較的基準錯了。

```
不跑迴圈：改 8 版 × 每版你都要讀一遍判斷 = 8 次人工判斷
跑迴圈：  改 5 版 × 程式自動評分 = 1 次人工抽查
```

**迴圈省的是「你的判斷次數」，不是 AI 的執行次數。**

### 「分數上升但我覺得變糟了」

**這是好消息。** 你發現了考卷的漏洞：

```
考卷說「輸出字數 ≤ 原文 20%」
    ↓
AI 學會：直接回「摘要：無」→ 字數超少，通過 ✓
    ↓
你發現了 → 補一題：「必須包含原文至少 3 個關鍵詞」
```

**每抓到一個規避手法，考卷就變強一次。**

## 六、和其他方法的關係

| 方法 | 它管的 | 和四拍的關係 |
|---|---|---|
| **TDD** | 不會壞（迴歸） | 是第③拍的一種裁判 |
| **EDD**（評估驅動） | 做得好（品質） | 就是第③拍 |
| **Scrum / Sprint** | 交付節奏 | 四拍在 sprint 之內跑 |
| **CI/CD** | 自動化執行 | 是第②③拍的基礎設施 |

**四拍不取代這些，它是把它們串起來的節奏器。**

## 三句話

1. **寫不出 `check()` 的任務，先別丟給模型。**
2. **「我覺得變好了」不是工程。**
3. **沒有拿同一份考卷比較，不准說「改好了」。**
