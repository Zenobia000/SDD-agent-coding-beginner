## 為什麼需要分流

AI 的能力不是「整體有多聰明」，而是**有些事超強、有些事爛到不行，而且兩者就在隔壁**。

| 表現 | 什麼任務 |
|---|---|
| **超強** | 有標準答案、能驗證對錯的（數學、程式碼） |
| **弱又不穩** | 常識、價值判斷、要看懂弦外之音的 |

最危險的是：**它弱的時候不會說自己不確定，會很有自信地講錯。**

所以「分辨這件事落在哪一面」本身就是一種工程能力。

## 四格

| 能用程式驗證？ | 做錯的代價 | 怎麼辦 |
|---|---|---|
| 可以 ✓ | 低 | **直接交給 AI 全自動**，事後看 log |
| 可以 ✓ | 高 | **AI 做，人核准** —— 動作可逆才自動 |
| 部分可以 | 任意 | **人機協作**：AI 產候選，人挑 |
| 不行 ✗ | 任意 | **先別做** ← 想辦法讓它變成可驗證的 |

### 三個判斷問題

1. **可驗證性**：寫得出 `check()` 嗎？怎麼寫？
2. **可逆性**：做錯了能不能還原？
3. **代價**：做錯的實際損失是什麼？

---

## 落在「先別做」怎麼辦

**不是放棄，是拆。**

```
「幫我寫出好文案」                寫不出 check() ❌
        ↓ 拆成可觀察的條件
「≤ 30 字」                       ✓
「包含產品名 + 一個動詞」          ✓
「不出現這 10 個禁用詞」           ✓
        ↓
變成：AI 產 20 個候選 → 程式篩掉不合格的 → 人從剩下的挑
                                    ＝ 人機協作
```

**拆的方法**：問「如果有兩個版本擺在我面前，我會看什麼、數什麼、比什麼？」

還是想不出來 → 換個問法：「什麼情況我會說『這個做壞了』？」
**從負面例子回推判準通常比較容易。**

## 可逆性怎麼判斷

| 操作 | 可逆 | 對分流的影響 |
|---|---|---|
| 改程式碼（有版控） | ✅ | 可以自動 |
| 寫新檔案 | ✅ | 可以自動 |
| 覆蓋既有檔案 | ⚠️ 有版控才可逆 | 確認有 commit 過 |
| 刪資料 | ❌ | **一律人核准** |
| force push | ❌ | **一律人核准** |
| 送出對外訊息（email / API 呼叫） | ❌ | **一律人核准** |
| 花錢的操作 | ❌ | **一律人核准** |

**不可逆的操作，即使可驗證，也不進全自動。**

---

## 授權矩陣

分流的結果要寫成別人看一眼就懂的表：

| 任務 | 動作描述 | 可逆？ | 風險 | 授權方式 | 由什麼強制 |
|---|---|---|---|---|---|
| 修 selector | 改 config | ✅ | 中 | AI 產候選 + 人 merge | PR review |
| 抓資料 | 讀外部 API | ✅ | 低 | **自動** | 驗證失敗不寫入 |
| 刪歷史資料 | DELETE | ❌ | 高 | **人核准** | hook 擋 |

```
低風險 ──── 自動執行 ────→ 事後查 log
              │
           風險線 ← 你要畫的就是這條
              │
高風險 ──── 人類核准 ────→ 授權層級必須可驗證
```

**全自動是陷阱，全人工是白做。** 你的工作是畫出那條線。

---

## 常見誤判

| 你以為 | 實際 |
|---|---|
| 「這個很簡單，交給 AI 就好」 | 簡單 ≠ 可驗證。先問寫不寫得出 `check()` |
| 「這個太主觀，AI 做不了」 | 多數「主觀」拆得開，拆完剩下的才真主觀 |
| 「可逆就可以全自動」 | 還要看代價。可逆但很貴的也該人核准 |
| 「有測試就等於可驗證」 | 測試測「不會壞」，考卷測「做得好」。兩者不同 |
