# M4｜答案只能從你給的資料來（RAG）

> **RAG** = Retrieval-Augmented Generation，白話就是「**先去查資料，再回答**」。
> 好處：可查、可審、**可引用**。

## 兩條死路，一條活路

- ❌ 死路 1：把背景資料全部硬塞進 prompt（塞不下，而且貴）
- ❌ 死路 2：換更大的模型（它還是不知道你公司的內部文件）
- ✅ 活路：**先檢索 → 再作答 → 附引用**

## Embedding：把文字變成一串數字

```
「人工智慧改變世界…」 → [0.21, -0.70, 0.15, 0.33, ...] → 高維向量
```

- 兩段文字意思像不像，就看兩串數字的**夾角**（餘弦相似度，越接近 1 越像）
- `dimensions` 參數可以把維度截短（省空間、省錢）
- 可以用 t-SNE 畫成 2D 圖 + KMeans 分群 → 相似主題會聚在一起

## Vanilla RAG 五步（最笨但最清楚的做法）

```
解析 Parse → 切塊 Chunk → 嵌入 Embed → 檢索 Retrieve → 生成 Generate
```

> 訣竅：叫它**先列出引用的原文，再作答** → 幻覺會明顯下降。

## 相似 ≠ 相關 → 要做兩階段檢索

**問題舉例**：你查「蘋果公司財報」，結果撈到「蘋果汁的營養價值」—— 字面很像，實際無關。

| 階段 | 名稱 | 做什麼 |
|---|---|---|
| 第一階段 | 粗篩 Recall | 用 embedding 快速撈出 top-N（寧可多撈） |
| 第二階段 | **精排 Precision** | 用 **reranker** 重新排序，取 top-k |

> **reranker** 是一種叫 cross-encoder 的模型 —— 它會把「問題」和「文件」**放在一起看**，所以判斷得比單純比數字準很多。實測分數會整個翻盤。

## 別再自己管向量陣列 → 用 ChromaDB

（向量資料庫 = 專門存這些數字、還能快速比對的資料庫）

| 功能 | 白話 |
|---|---|
| `PersistentClient` | 索引存到硬碟，**重啟不用重算** |
| `collection.add` | 一次存進文件 + 向量 + metadata |
| `query` + metadata 過濾 ★ | **語意搜尋 × 結構化條件**（例如「只找 2024 年之後、來源是 notebook 的」）—— 這是純向量檢索給不了的 |

切塊工具：`RecursiveCharacterTextSplitter`，記得設 **overlap**（相鄰兩塊重疊一點，避免句子被切斷）。

## Dynamic few-shot：範例也用檢索去挑

不要每次都塞同一組範例。改成：依照使用者這次的問題，**即時撈出最相關的範例**注入 prompt。

用 **MMR** 在「相關」和「多樣」之間取平衡（參數 `lambda_mult`）——
只挑最相似的話，範例會長得都一樣、覆蓋面太窄。

## 撞牆才升級，依瓶頸選招

不要一招打天下。以下是進階招式，**哪裡卡就補哪裡**：

| 招式 | 什麼時候用 |
|---|---|
| Query Expansion | 使用者問得太簡短 |
| HyDE | 先讓模型假想一個答案，再拿去檢索 |
| Small-to-Big | 用小塊找、拿大塊給模型看 |
| Hybrid Search | 關鍵字 + 語意一起搜 |
| Contextual Embeddings | 切塊時補上上下文再算向量 |

PDF 的升級路線：**純文字 → 版面解析 → 多模態讀圖**（讓模型直接看圖表）。

## Agentic RAG：模型控檢索，你控邊界

讓模型自己決定要查幾次、怎麼查：

```
Route（判斷該走哪條路）→ Plan → Retrieve → Sufficiency（夠了嗎？）
   → 不夠 → Retry（但有 max_steps 硬上限！）
   → 夠了 → Grounding（檢查每句話都指得出出處）
```

> **可控性 > 自動化程度。** 每一步都是閘門，重試一定要有上限，否則會無限燒錢。

## 這關的驗收

拿**同一組評估題**，比較「有 reranker」vs「沒有」的分數（例：0.62 → **0.87**）。

- 要講「分數有差」，不是「感覺比較好」
- 查不到資料時，要**明確回「資料中無相關內容」**，不要硬掰
