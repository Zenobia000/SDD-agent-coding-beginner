# M6｜找別家 AI 互相審（協作與防禦）

> 核心一句：**兩家模型互審 > 一顆模型自信。**

## 為什麼單一 agent 不可信

單一模型的偏誤（幻覺、過度自信、隨機性）**全部關在同一顆腦袋裡**，沒有外部視角能戳破它。

解法：**用結構去抵銷偏誤** —— 讓多個觀點互相審查。

```
「我覺得對」  →  「兩家互審一致認定對」
```

## Agents SDK 五個基本零件

| 零件 | 白話 |
|---|---|
| `Agent` | 一個**只做一件事**的執行單元 |
| `Runner` | 驅動迴圈的執行器 |
| `@function_tool` | 把 Python 函式變成工具 —— **型別註記自動變成 schema** |
| `handoffs` | 這個 agent 可以把工作交給哪些人 |
| `trace` | 把整個協作過程包成可觀測的追蹤紀錄 |

> 注意：**型別註記是契約，不是文件。註記寫錯，就一路傳錯下去。**

## 三種協作模式

| 模式 | 白話 | 適合什麼 |
|---|---|---|
| **Handoff** | A 整包丟給 B，**由 A 自己判斷**要不要交 | 線性流程、交接點很明確 |
| **Supervisor** | 有個主管，**每一輪挑一個下屬**去做 | 要協調多步驟、需要動態選擇 |
| **Agents-as-tools** | 把 agent 包成「工具」，讓主 agent 想用就叫 | 標準化能力、會重複用到 |

> 由左到右，**控制權越來越往模型身上移**。
> 判斷原則：**你放多少控制權出去，要跟「你能容忍多少失控」匹配。**

## Deep search：受控的檢索迴圈

```
規劃 Plan → 搜尋 Search → 反思 Reflect → 精化 Refine → （回到 Plan）
```

- `asyncio.gather`：多個搜尋**並行**跑，不要一個一個等
- Pseudo-tools：逼模型把「它在想什麼」外顯成結構化的呼叫，你才看得到
- **`max_turns` 一定要設上限** —— 沒上限 = 無限燒 token

## 四大失敗模式，各自攔在哪

| 失敗模式 | 白話：長什麼樣 | 攔在哪 |
|---|---|---|
| **Silent failure** | 表面上答得好好的，但**對不上任何來源** | 攔在**輸出處**：要求每個宣稱都能對應到原文（grounding 斷言） |
| **Spec drift** | 跑著跑著就**偏離原本的規格** | 攔在**時間軸**：每 N 輪把 spec 重貼一次 |
| **Sycophancy** | **迎合你錯誤的前提**（你說錯它也順著講） | 攔在**前提處**：要求它先質疑前提 |
| **Cascade failure** | 一個錯，**沿著交接鏈一路傳下去** | 攔在**交接處**：handoff 包一層驗證 + 熔斷 |

> **驗證閘門 = 多 agent 系統的 `assert`。**
> 沒有落成程式碼的那一格，就是你在靠運氣的地方。

## 別讓球員兼裁判

- 同一家模型自己審自己 → **對自家評分偏高、對別家偏低**
- 解法：**跨廠商互審**，用別家的偏誤抵銷自家的偏誤

## 互審架構：Writer → Reviewers → Synthesizer

```
Writer（一家模型產草稿，如 Claude）
    ↓
Reviewer A（OpenAI，輸出 JSON: {score, items, notes}）
Reviewer B（Gemini，輸出 JSON）
    ↓ 兩份審查意見算「餘弦相似度」＝ 一致性
    ↓ 一致性低 → 這是「該找人來看」的訊號
Synthesizer（再用一家模型彙整意見，產定稿）
```

## 跨模型互審 SOP 範本（六條）

1. **角色分工**：Producer 和 Reviewer **必須是不同廠商**
2. **觸發條件**：什麼情況才啟動互審
3. **審查 prompt**：要求它**先質疑前提**
4. **一致性閾值**：`consistency ≥ 0.75`
5. **升人工規則**：低於閾值怎麼辦
6. **紀錄欄位**：`{ verdict, confidence, issues: [{type, detail}] }`

> **換一個人照這份 SOP 跑，也要得到同樣的可信度。**
