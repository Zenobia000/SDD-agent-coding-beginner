# 二元判準

## 結論卡

| | |
|---|---|
| **一句話** | 「我覺得變好了」不是工程 |
| **核心動作** | 放棄 1–10 分，改成對 / 錯 |
| **為什麼** | 分數不可重現；通過率可以加總、可以比較 |
| **課堂** | S2 建考卷、S4 用考卷 |
| **下一步** | 拿你最近一次「改好了」的宣稱，試著寫成 yes/no |

---

## 問題

```
「這版比較好」
「感覺順一點」
「品質有提升」
```

這三句話的共同問題：**下週再問你同一件事，你會給不同的答案。**

不可重現的判斷，無法累積成證據。

---

## 為什麼不用 1–10 分

| | 問題 |
|---|---|
| ❌ 1–10 分 | **不可重現** —— 今天給 7 分，明天同一個東西給 5 分 |
| ✅ 對 / 錯 | **可以加總成比率** |

```
通過率 = 對的筆數 ÷ 總筆數
```

比率的好處：
- 兩次跑同一份 dataset，數字可以直接比
- 不同人跑，結果應該一樣
- 可以畫成曲線看趨勢

**LLM 當裁判時尤其重要**：讓它給分數，同一個輸入跑三次會得到三個分數；
讓它回 `{pass: true/false}`，一致性高很多。

---

## 怎麼把模糊判準拆成 yes/no

三步：

```
① 拆成可觀察的條件
   「有禮貌」→「結尾有致歉或感謝」

② 用 AND / OR 接成可核對的句子
   「結尾有致歉或感謝 AND 沒有出現命令句」

③ 想幾個負例，確認擋得住
   負例：「請自行處理。」→ 應該 fail ✓
```

### 對照表

| ❌ 不可核對 | ✅ 可核對 |
|---|---|
| 夠不夠專業 | 沒有出現「我覺得」「應該」等模糊詞 |
| 是否夠詳細 | 每個宣稱都有對應的 `citations` 條目 |
| 使用者體驗好 | 首次可互動時間 ≤ 2 秒 |
| 摘要品質高 | 字數 ≤ 原文 20% 且涵蓋三個 H2 標題 |
| 程式碼好維護 | 單檔 ≤ 800 行且圈複雜度 ≤ 10 |
| 錯誤處理完善 | 每個 I/O 呼叫都有對應的失敗路徑測試 |

**每一條都要能用一句 yes/no 回答。**

## 誰來當裁判

**能用程式判就別請 LLM。**

| 答案性質 | 裁判 | 寫成什麼 |
|---|---|---|
| 有標準答案 | **程式 assertion** ★ | 一個測試 |
| 有結構要求 | **schema 驗證** | Pydantic model / JSON Schema |
| 有參考資料 | **比對來源** | 檢查每個宣稱都指得出出處 |
| 主觀但有規則 | LLM-as-judge（**後備**） | 只回 `{pass, reason}` 的 prompt |

LLM-as-judge 的兩個陷阱：

1. **別讓球員兼裁判** —— 同一家模型自己審自己，對自家評分偏高
2. **不要讓它給分數** —— 只准回 pass/fail + 一句理由

---

## 一份考卷的最低要求

| 要求 | 為什麼 |
|---|---|
| **≥ 10 筆測資** | 少於 10 筆，一筆就佔 10%，雜訊蓋過訊號 |
| **≥ 3 筆邊界 case** | 只測主流程會給你虛假的安全感 |
| **有基線** | 沒有起點，之後所有「改好了」都無法證明 |
| **每條判準至少有一個會 fail 的案例** | 否則你不知道那條判準有沒有在工作 |

最後一條最常被忽略。**一條永遠會過的判準，等於沒有那條判準。**

## 分數上升但你覺得變糟了

**這是好消息。** 你發現了考卷的漏洞。

```
考卷說「輸出字數 ≤ 原文 20%」
    ↓
AI 學會：直接回「摘要：無」→ 字數超少，通過 ✓
    ↓
你發現了 → 補一題進考卷：「必須包含原文至少 3 個關鍵詞」
```

這個現象叫 **reward hacking** —— 模型優化的是「考卷」，不是「你真正想要的」。

**防護方法只有一個：每輪都要抽查最好的那個版本**，不能只看分數。

---

## 失敗模式聚類

跑完考卷發現通過率不夠時，**不要一筆一筆救火**。

```
① 列出所有失敗的題目
② 找共同模式
③ 針對模式改，一次消滅一整類
④ 跑同一份考卷，比較
```

範例：
| 模式 | 失敗的題號 | 一次修法 |
|---|---|---|
| 解析格式變體 | #4, #5 | 統一先正規化再解析 |
| 冷啟動 / 資料不足 | #7, #8 | 加 null 處理，不當錯誤 |
| 冪等性 | #9 | Load 改成 upsert |

**三個修法解決 5 題**，比改 5 次快。

---

## 改進優先序

**先便宜後昂貴**，每動一步就回去跑同一份考卷：

| 順序 | 做法 | 成本 |
|---|---|---|
| ① | 改指令措辭 | 最低 |
| ② | 加 few-shot 範例（對格式，不是教推理） | 低 |
| ③ | 改結構（schema / 檢索方式） | 中 |
| ④ | 換模型 / 微調 | 最高 |

**一次只改一件事。** 同時改兩件，你分不清哪件有效。

## 用在教學上

本課程把二元判準用在**教學本身**：

```
labs/reference-project/RUBRIC.md  ← 八站的二元判準
        ↓
學員打 /gate
        ↓
通過 / 未通過 + 缺什麼 + 一個下一步
```

**不給分數。** 學員只需要知道「能不能往前走」，不需要知道自己 78 分。
