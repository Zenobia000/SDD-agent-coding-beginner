# 00 — 寫一份 CLAUDE.md

## 這是什麼

**專案的站立規則。每次對話開始時自動載入，AI 一定會讀到。**

---

## 什麼時候用它而不是別的

| 內容 | 放哪 |
|---|---|
| 一句話講得完的專案事實 | **CLAUDE.md** |
| 需要解釋「為什麼」的紀律 | rule（CLAUDE.md 用一行引用） |
| 講話的形狀 | output style |
| 不可逆操作的攔截 | hook |

**判斷**：這是「每次都該知道」的事實嗎？是 → CLAUDE.md。

---

## 最大的陷阱：~70% 順從率

**已確認的事實**：寫進 CLAUDE.md 的規則，大約有 70% 的機率被遵守。

這個數字決定了你該怎麼用它：

```
可逆的事（沒寫測試、命名不對、忘了跑 lint）
    → CLAUDE.md 就夠。錯了可以補

不可逆的事（rm -rf、force push、secret 外洩）
    → 一定要用 hook。不能賭那 30%
```

**把不可逆的事寫進 CLAUDE.md 就以為安全了，是最危險的誤解。**

---

## 骨架（八節，順序有意義）

```markdown
# CLAUDE.md — <專案名>

## 1. 你的角色
## 2. <這個專案的核心節奏 / 方法論>
## 3. 動手前必讀
## 4. 主流程
## 5. 平台合約（輸出格式 / MCP / subagent）
## 6. 技術選擇
## 7. 對話風格
## 8. 絕對禁止（硬約束）
```

**為什麼是這個順序**：
角色（我是誰）→ 節奏（怎麼做事）→ 必讀（去哪找細節）→ 流程（做什麼）
→ 合約（怎麼互動）→ 選擇（預設值）→ 風格（怎麼講）→ 禁止（絕不做什麼）。

從抽象到具體，最後用禁止收尾 —— **禁止項放最後，因為它最容易被記住。**

---

## 每一節該寫什麼

### 1. 你的角色

```markdown
你是協助開發者跑 <方法論> 的 <角色>。使用者 <程度描述>。

**最高任務**：<一句話。要能當成判斷準則>

**核心信念**：
- <三條以內>
```

**「最高任務」那句要能拿來裁決衝突。**
例：「讓每一輪產出都可評分」→ 遇到「要不要先寫考卷」時，答案自明。

### 3. 動手前必讀

用表格，標明**什麼時候讀**：

```markdown
| 順序 | 檔案 | 什麼時候讀 |
|---|---|---|
| 1 | `docs/PRD.md` | 每次開工 |
| 2 | `.claude/rules/08-loop-first.md` | **開跑前** |
| 3 | `.claude/rules/09-evidence-labels.md` | **報告結論前** |
```

❌ 不要只列清單說「都要讀」—— AI 會全部讀進 context，把預算吃光。
✅ 標明時機，讓它按需要讀。

### 5. 平台合約

這節放**互動格式**，不是工程紀律：

```markdown
### 回覆結尾固定四段
1. 做了什麼（1–2 句）
2. 改了哪些檔案
3. 怎麼驗證（指令 + 預期結果）
4. 下一步（**恰好一個**動作）
```

### 8. 絕對禁止

**每一條都要說明「這條由什麼強制」**：

```markdown
- ❌ **不把 secret 寫進 code** —— 用環境變數。
  這條由 `.githooks/pre-commit` 與 `hooks/block-secret-write.sh`
  **雙層機械強制**
- ❌ **沒 spec 不寫 code** —— 這條靠自律（`rules/04`）
```

讓讀的人知道哪些是「請你遵守」、哪些是「你沒得選」。

## 三個常見錯誤

### ① 太長

**超過 200 行，AI 讀不完，重點被稀釋。**

```
CLAUDE.md 500 行
    ↓
把「為什麼」搬進 rules/，CLAUDE.md 只留一行引用
    ↓
CLAUDE.md 150 行 + 9 條 rule
```

**CLAUDE.md 是索引，不是百科全書。**

### ② 寫「請仔細檢查」這類 Model Rule

```markdown
❌ 請確保程式碼正確無誤
❌ 請一步一步仔細思考
❌ 請不要遺漏任何細節
```

這些是**你怕它出錯而加的叮嚀**，不是業務要求。

**問題**：它們無法驗證，而且**廢話是模型必須服從的雜訊** ——
你多寫一句沒用的，它就多一個要顧的東西。

```markdown
✅ 金額一律無條件捨去到小數第 2 位
✅ 來源必須是這三個網域之一
```

**保留 Business Rule（業務真的要求的、可驗證的），刪掉 Model Rule。**

### ③ 重述其他文件的內容

```markdown
❌ ## TDD 流程
   1. 先寫失敗測試
   2. 寫最少實作
   ...（又把 rules/05 抄一遍）

✅ - **沒測試不算完成** —— 實作走 `/tdd-cycle`（`rules/05`）
```

**每個事實只有一個真相源。** 重述 = 未來的矛盾。

## 怎麼驗證它真的生效

### ① 確認被載入了

```
/context
```
應該看到 CLAUDE.md 在載入的內容裡。

### ② 測一條規則

挑一條最具體的，故意違反看看：

```
> 幫我直接寫個 function，不用測試
```

它應該引用你的規則拒絕或提醒。**沒有反應 = 那條寫得不夠明確。**

### ③ 換人測試（最有效）

給一個沒看過這個專案的人（或開一個新 session）：

> 只讀 CLAUDE.md，你知道要怎麼開始工作嗎？

**他有任何一個問題要回頭問你 → 還沒寫完。**

## 範圍與優先序

| 位置 | 範圍 | 進版控 |
|---|---|---|
| `~/.claude/CLAUDE.md` | 你所有專案 | ❌ 個人的 |
| `<專案>/CLAUDE.md` | 這個專案，**團隊共用** | ✅ |
| `<專案>/.claude/CLAUDE.md` | 同上 | ✅ |
| 子目錄的 `CLAUDE.md` | 那個子目錄 | ✅ |

越近的越優先。monorepo 可以在各套件下放各自的。

## 本專案有兩份 CLAUDE.md 可以對照

| 檔案 | 治理什麼 | 特色 |
|---|---|---|
| `.claude/CLAUDE.md`（repo 根） | 寫課程這件事 | 產出物是教材，不是 feature |

**兩者規則不同，刻意不互相複製** —— 這本身就是「單一真相源」的示範。
