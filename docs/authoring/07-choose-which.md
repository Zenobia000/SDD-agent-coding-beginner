# 07 — 該做成哪一種？

## 這是什麼

一棵決策樹。輸入「我想讓 AI 每次都 ___」，輸出「做成哪種資產」。

## 決策樹

```

│

│   例：擋 rm -rf、擋寫 secret、自動格式化、注入狀態
│
└─ 否
   │
   這是一套我要跟著走的多步驟流程嗎？
   │
   ├─ 是
   │   │
   │   需要附件嗎（範本、腳本、檢核表）？
   │   │
   │   ├─ 是 ──────────────────────────────► skill（目錄形式）
   │   │   例：/spec-it 帶 6 份範本
   │   │
   │   └─ 否 ──────────────────────────────► command（單檔）
   │       例：/gate 就是照 RUBRIC 檢查一遍
   │
   └─ 否
      │
      這件事會產生一堆我不想看的中間資訊嗎？
      或者需要「不被我的意圖污染」的視角？
      │
      ├─ 是 ────────────────────────────────► subagent
      │   例：在 200 個檔案裡找東西、獨立 code review
      │
      └─ 否
         │
         這是「每次都該知道」的專案事實嗎？
         │
         ├─ 是
         │   │
         │   是一句話講得完的慣例嗎？
         │   ├─ 是 ────────────────────────► CLAUDE.md

         │
         └─ 否
            │
            這是「講話的形狀」而不是「做事的方法」嗎？

            └─ 否 ────────────────────────► 不用做成資產，直接講就好
```

## 五組容易搞混的對照

### skill vs command

**兩者都產生 `/name`。行為一樣。**

```
.claude/commands/deploy.md          →  /deploy
.claude/skills/deploy/SKILL.md      →  /deploy
```

skill 多的是：

| 能力 | skill | command |
|---|---|---|
| 帶附件目錄 | ✅ | ❌ |
| AI 自動載入（依 description 判斷） | ✅ | 較弱 |
| 控制誰能觸發（`disable-model-invocation` 等） | ✅ | ❌ |
| 唯讀限制（`disallowed-tools`） | ✅ | ❌ |

**判斷**：
- 只是一段固定步驟 → **command**（單檔，好維護）
- 有範本 / 要 AI 自動觸發 / 要限制工具 → **skill**

### rule vs CLAUDE.md

| | CLAUDE.md | rule |
|---|---|---|
| 長度 | 一句話 | 一整篇 |
| 內容 | **是什麼** | **為什麼 + 違反的後果** |
| 位置 | 直接寫 | `.claude/rules/`，由 CLAUDE.md 引用 |

**判斷**：講得出「為什麼」且那個為什麼很重要 → rule。
否則塞進 CLAUDE.md 一行就好。

**反模式**：CLAUDE.md 長到 500 行。那表示你該把說明搬進 rule。

### rule vs hook

**這是最重要的一組。**

```
rule  = 「請你不要 ___」    → 約 70% 順從率
hook  = 「你不能 ___」      → 100%
```

**判斷標準只有一個：這件事做錯了能不能還原？**

| 事情 | 可逆？ | 用什麼 |
|---|---|---|
| 沒寫測試就實作 | ✅ 可以補 | rule |
| 命名不符慣例 | ✅ 可以改 | rule |
| 沒跑 lint 就 commit | ✅ 可以修 | rule（或 PostToolUse hook 自動修） |
| `rm -rf` | ❌ | **hook** |
| force push 到 main | ❌ | **hook** |
| 把 API key 寫進檔案 | ❌ **已外洩** | **hook** |
| 刪 DB 欄位 | ❌ | **hook** |

**不可逆的事情不能賭那 30%。**

### skill vs subagent

| | skill | subagent |
|---|---|---|
| context | **主對話** | **獨立** |
| 你看得到過程嗎 | 全部看得到 | 只看到結論 |
| 適合 | 你要跟著走的流程 | 你只要結果的工作 |

**判斷兩題**：
1. 這件事會產生一堆我不想看的中間資訊嗎？（檔案內容、log、搜尋結果）
2. 這件事需要「不知道我為什麼這樣寫」的視角嗎？

任一題「是」→ subagent。

**第 2 題很重要**：code review 用 subagent 而不是 skill，
是因為**別讓球員兼裁判** —— 主對話知道你的意圖，會不自覺地配合。

### output style vs CLAUDE.md

| | output style | CLAUDE.md |
|---|---|---|
| 改的是 | **system prompt** | 對話開頭的一則訊息 |
| 管的是 | 講話的**形狀** | 專案的**事實** |
| 範圍 | 每一句回覆 | 專案相關的判斷 |

```
✅ output style：「結論先行」「清單 ≤5」「證據要標級」
✅ CLAUDE.md   ：「這個專案用 pnpm 不是 npm」「測試在 tests/」

❌ 不要把專案慣例寫進 output style —— 換專案就錯了
❌ 不要把講話風格寫進 CLAUDE.md —— 那會被淹沒在專案資訊裡
```

## 三個實例演練

### 例 1：「我不想每次都提醒它 commit 前跑測試」

```
需要自動發生嗎？→ 是，我希望它自己想起來
    ↓
hook（Stop 事件，檢查有未提交改動就提醒）
```
本模板的 `remind-verify.sh` 就是這個。

**但注意**：如果你要的是「**不准**沒跑測試就 commit」，那是 `PreToolUse` hook 擋 `git commit`。
「提醒」和「阻擋」是不同強度，先想清楚你要哪個。

### 例 2：「每次做 code review 我都問同樣的四個問題」

```
需要自動發生嗎？→ 否
是多步驟流程嗎？→ 是
需要附件嗎？    → 否（就四個問題）
    ↓
command
```

**但如果**你希望 review 的視角不被你的意圖污染 → 改成 **subagent**。
本模板的 `reviewer` 就是這樣做的。

### 例 3：「AI 老是把推測講得像事實」

```
需要自動發生嗎？→ 否
是多步驟流程嗎？→ 否
會產生一堆中間資訊嗎？→ 否
是專案事實嗎？→ 否，這是講話的方式
是講話的形狀嗎？→ 是
    ↓
output style（+ 一條 rule 說明為什麼）
```
本模板的 `output-styles/dev-decision.md` + `rules/09-evidence-labels.md`
就是這個組合：**style 管形狀，rule 管理由。**

## 常見錯誤

| 錯誤 | 後果 | 正解 |
|---|---|---|
| 把不可逆的事寫成 rule | 30% 機率出事 | 改成 hook |
| 什麼都做成 hook | 難維護、容易誤擋 | 可逆的事用 rule |
| CLAUDE.md 長到 500 行 | AI 讀不完，重點被稀釋 | 拆成 rule |
| 每個小動作都做成 command | `/` 選單爆炸 | 講第 3 次才做 |
| 用 skill 做 code review | 視角被主對話污染 | 用 subagent |

## 怎麼驗證你選對了

做完之後問自己三題：

1. **它真的被觸發了嗎？** —— 沒觸發的資產等於不存在
2. **它擋/做的是我要的那件事嗎？** —— 測一個該放行的案例
3. **三個月後的我看得懂為什麼有這個東西嗎？** —— 沒有就補一句註解
