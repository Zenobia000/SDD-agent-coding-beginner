# 01 — 寫一條 rule

## 這是什麼

**一條硬約束的完整說明：規則是什麼、為什麼、違反了會怎樣。**
放在 `.claude/rules/`，由 `CLAUDE.md` 一行引用。

---

## 什麼時候用它而不是別的

```
這件事可逆嗎？
├─ 不可逆 ────────────────────► hook（rule 不夠）
└─ 可逆
   │
   一句話講得完嗎？
   ├─ 講得完 ──────────────────► 直接寫進 CLAUDE.md
   └─ 需要解釋為什麼 ──────────► rule ← 你在這
```

**rule 存在的唯一理由是「為什麼」。**
如果你的規則不需要解釋，它就該是 CLAUDE.md 裡的一行。

---

## 最小可跑範例

`.claude/rules/10-no-any.md`：

```markdown
# Rule 10 — 不准用 any

## 鐵律

TypeScript 檔案中不使用 `any`。不確定型別時用 `unknown` 再收窄。

## 例外

- 第三方套件沒有型別定義，且已在該行加 `// TODO: 補型別` 註解
- 測試檔中模擬錯誤輸入時

## 為什麼

`any` 會讓型別檢查在該處**完全失效**，而且會沿著呼叫鏈往下傳染 ——
下游拿到的東西看起來有型別，實際上沒有。

## 違反的後果

```
Day 1：一個 any 讓某個 API 回傳型別失去檢查
Day 7：下游三個檔案都基於錯誤的假設在寫
Day 30：改那個 API 的欄位名，編譯器全綠，執行時炸
```

## 心法

> **不確定就用 `unknown`，不要用 `any`。**
> `unknown` 逼你收窄，`any` 讓你跳過思考。
```

在 `CLAUDE.md` 裡引用：
```markdown
| 10 | `.claude/rules/10-no-any.md` | 寫 TypeScript 時 |
```

## 骨架（五節）

```markdown
# Rule NN — <名稱>

## 鐵律          ← 規則本身，1–4 條
## 例外          ← 什麼情況可以不遵守
## 為什麼        ← 這節是 rule 存在的理由
## 違反的後果    ← 具體的時間線，不是抽象的「會有問題」
## 心法          ← 一句話，讓人記得住
```

**「例外」那節不能省。** 沒有例外的規則會被整條忽略 ——
人遇到第一個合理的例外情況時，會判定「這規則不切實際」然後全部不遵守。

## 填空模板

```markdown
# Rule <NN> — <名稱>

> **<一句話總結，會被引用到 CLAUDE.md>**

## 鐵律

1. <可核對的規則>
2. <可核對的規則>

（**最多 4 條。** 超過就該拆成兩條 rule）

## 例外

- <什麼情況可以不遵守>
- <什麼情況可以不遵守>

## 觸發情境

| 使用者說 | 你該做 |
|---|---|
| 「<話>」 | <動作> |

## 為什麼

- **<理由 1>** —— <展開一句>
- **<理由 2>** —— <展開一句>

## 違反的後果

```
Day 1：<具體發生什麼>
Day 7：<問題怎麼擴散>
Day 30：<最後爆炸的樣子>
```

## 心法

> **<一句話，要能被記住>**
```

## 命名與編號

```
.claude/rules/
├── 01-keep-it-simple.md
├── 02-coding-style.md
...
└── 09-evidence-labels.md
```

**編號決定 CLAUDE.md 裡的閱讀順序。**
新增時接在後面（`10-`、`11-`），不要為了插隊重編 —— 重編會讓所有引用失效。

## 三個常見錯誤

### ① 沒寫「為什麼」

```markdown
❌ # Rule 10 — 不准用 any
   ## 鐵律
   不要用 any。
   → 這該寫在 CLAUDE.md 一行就好，不值得一個檔案
```

**rule 的價值 100% 在「為什麼」和「違反的後果」。**
沒有這兩節，它只是一條被稀釋的 CLAUDE.md。

### ② 沒寫例外

```markdown
❌ 任何新功能都必須先寫測試。
   → 遇到「改個 timeout 常數」也要寫測試？
   → 使用者判定這規則不切實際 → 整條忽略

✅ ## 例外
   - 純樣式 / CSS 調整（無邏輯）
   - 純文案修改
   - 一次性 script（這個 sprint 內會刪掉的）
```

### ③ 用 rule 管不可逆的事

```markdown
❌ # Rule 11 — 不准 force push
   → 約 70% 順從率。剩下 30% 是不可逆的災難

✅ 寫進 hook（`block-dangerous-bash.sh`），
   rule 只留下「為什麼要這樣做」的說明
```

**這是 rule 最重要的邊界。**

## 怎麼驗證它真的生效

### ① 確認被引用了

rule 檔案存在但沒被 `CLAUDE.md` 引用 → **等於不存在**。

```bash
grep -n "rules/" CLAUDE.md
```

### ② 測一次違反

```
> <故意做這條 rule 禁止的事>
```

它應該引用規則拒絕或提醒。沒反應 → 「鐵律」那節寫得不夠可核對。

### ③ 檢查可核對性

把「鐵律」逐條唸出來，問：**這條能用 yes/no 判斷有沒有違反嗎？**

| 鐵律 | 判斷 |
|---|---|
| 「程式碼要寫得好維護」 | ❌ 無法核對 |
| 「單一檔案不超過 800 行」 | ✅ |
| 「錯誤處理要完善」 | ❌ |
| 「每個 I/O 呼叫都要有失敗路徑的處理」 | ✅ |
