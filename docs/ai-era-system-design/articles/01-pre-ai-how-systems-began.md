# 01 — 沒有 AI 的年代，系統定義如何開始

> 重點：2020 年前的產品開發，極少靠「完整文件」啟動。
> 真正的起點是**最小共識 + 架構草圖 + 邊做邊補定義**。
> 能力不在於一開始寫完全部文件，而在於能在不完整中控住風險。

---

## 現實的開場，不是理想流程

教科書版本是 PRD → SRS → SAD → API Spec → DB Schema → Test Plan 全部寫完才開發。實際現場通常是：

```
PM 講一個方向
  ↓
SA / Architect 畫一張粗架構圖
  ↓
工程師先開幹
  ↓
做到一半發現規則沒定義
  ↓
回頭補需求、補欄位、補流程、補例外情境
```

這不是理想流程，但它真實存在，而且在時程壓力下幾乎是常態。問題從來不是「一開始文件少」，而是「文件少卻沒有人負責讓它慢慢變完整」。後者才會變成技術債。

---

## 系統定義真正的起點：六個問題

一開始不需要完整文件，但至少要回答下面六個粗但關鍵的問題。它們是後續所有文件的種子。

| # | 問題 | 白話 | 對應產出 |
|---|------|------|----------|
| 1 | 這系統解決誰的痛？ | 使用者是誰，場景是什麼 | Problem Statement |
| 2 | 最重要的流程是什麼？ | 從哪裡進來，最後完成什麼 | User Flow / Business Flow |
| 3 | 系統邊界在哪？ | 哪些我們做，哪些外部系統做 | System Boundary |
| 4 | 核心資料是什麼？ | 主資料、交易資料、狀態資料 | ERD / Data Model |
| 5 | 誰跟誰串？ | 前端、後端、DB、第三方怎麼互動 | Architecture Diagram |
| 6 | 最怕哪裡炸？ | 權限、效能、一致性、錯誤流程 | Risk List |

這六個問題的答案可以是文件，也可以是白板照片或會議紀錄。形式不重要，**被留下來**才重要。沒有留下來，後面就會各做各的。

---

## 唯一不可省的東西

一開始可以沒有完整文件，但一定要有一個東西：

> 團隊對「要做什麼、不做什麼、先做什麼」有共同理解，而且這個理解被記錄下來。

這對應到本 repo 的「種子簡報」概念（見 [`../../../種子簡報.md`](../../../種子簡報.md)）與 Vibe Engineering 的 L1 PRD。種子簡報就是這六個問題的最小化答案，是後續一切結構化工作的入口。
