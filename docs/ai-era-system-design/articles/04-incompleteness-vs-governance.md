# 04 — 不完整不可怕，沒治理才可怕

> 重點：一開始文件不完整可以接受。
> 真正的問題是「不完整卻沒有人負責讓它慢慢變完整」。
> 治理不是把文件寫滿，而是有節奏地補完整。

---

## 沒有治理的常見症狀

| 症狀 | 後果 |
|------|------|
| 需求只在 PM 腦中 | 工程師各自理解 |
| 架構圖沒更新 | 系統實況與文件不一致 |
| API 沒規格 | 前後端互相猜 |
| 權限沒定義 | 上線前才發現資安問題 |
| 例外流程沒討論 | 一遇異常資料就 crash |
| DB schema 沒治理 | 欄位命名混亂、重複資料 |
| 測試案例不足 | QA 只能憑感覺測 |

做一個月還不完整可以，但兩個月、上線前還不完整，就是技術債在累積。

---

## 開發節奏：Phase 0–6

成熟團隊用一個有節奏的流程，允許前期模糊，但要求逐階段收斂。

| Phase | 名稱 | 重點 | 主要產出 |
|-------|------|------|----------|
| 0 | 模糊想法 | 先分類：報表 / 流程 / 交易 / 整合系統 | 背景、目標、痛點、大概使用者與時程 |
| 1 | 需求探索 | 訪談使用者，抓角色與主流程 | User Story、Business Flow、Open Questions |
| 2 | 系統輪廓 | 第一版架構與邊界 | Context / Container Diagram、初版 ERD、API 清單 |
| 3 | MVP 開發 | 只做最核心、最有風險、最能驗證價值的流程 | 可運行的主流程 |
| 4 | 細節補齊 | 把規則、例外、權限補上 | API Spec、Schema、Permission Matrix、Test Case |
| 5 | 整合測試 | 驗證不開心的 path 與外部系統失效 | 整合測試、例外處理、一致性驗證 |
| 6 | 上線與維運 | 誰看、Log 在哪、怎麼 rollback | Runbook、Monitoring、Incident SOP |

### 各階段的關鍵提醒

- **Phase 0**：不要急著寫技術規格，先判斷系統類型，四種類型差很多。
- **Phase 1**：最重要的產出是 **Open Questions**。問題一定問不完，但至少要把未知列出來。
- **Phase 3 切 MVP**：保留主流程，砍周邊功能。MVP 不是切到亂七八糟，是先驗證最核心的價值。
- **Phase 4**：真正的系統品質在這裡。最常被忽略，例如權限矩陣沒做，上線前才吵「為什麼業務看得到全部資料」。
- **Phase 5**：demo 是 Happy Path，真實系統是各種不開心的 path。前面都能 demo、一整合就爆，原因在此。

## 兩個低成本但高效的治理工具

### Open Questions 表

| Open Question | Owner | Due |
|---------------|-------|-----|
| 訂單取消是否需要主管審核？ | PM | 5/31 |
| ERP API 是否支援批次查詢？ | SA | 6/3 |
| 報表是否需要匯出 Excel？ | User | 6/5 |

很土，但它把「未知」變成「可追蹤的工作」，比寫一份假裝完整的文件有用。

### Decision Log

| 日期 | 決策 | 原因 | 影響 |
|------|------|------|------|
| 2020/03/12 | 訂單取消需主管審核 | 避免業務誤刪 | 新增 `approval_status` |
| 2020/03/18 | 報表先支援 Excel 不支援 PDF | MVP 時程限制 | PDF 放 Phase 2 |

Decision Log 比一份完美文件更實用，因為它記錄「為什麼這樣決定」。在 AI 時代，這個角色由 ADR 承接（見 [process/03](../process/03-schemas-and-traceability.md) 與 [`.agents/skills/adr`](../../../templates/antigravity_project_template/.agents/skills/adr/)）。
