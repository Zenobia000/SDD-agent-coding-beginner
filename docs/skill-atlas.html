SDD 七站技能地圖

從新題目到上線，工具箱只有一條主線與七個站。每一站都是一個可以被獨立跳過的判斷 —— 照著全走一遍是新手，知道這次哪站不用做才是熟手。

這頁把 route.png 的七站，和 .claude/skills/ 底下 36 個技能，攤在同一張圖上。

空心站 = 條件對了就可以跳過實心站 = 唯一不能跳的一站

主線七站

左邊是站，中間是這一站手上有哪些技能，右邊是什麼情況可以直接跳過它。開始之前，每個 repo 先跑一次 /setup-skills —— 那不是站，是雜務。

1

拆解問題

要做什麼

/grilling /domain-modeling /to-spec

沒有 codebase 用 /grilling，有 codebase 用 /grill-with-docs，沿路留下術語表與 ADR。

跳過條件別人已經給你 spec。那要做的是讀懂並挑戰它。
2

值不值得做

要不要做

/feasibility

技術風險、競品對照、成功指標、量級成本 —— 四問，收在一個明確判決上（✅／⚠️／❌），以 comment 掛回 spec issue。

跳過條件沒有真實不確定性：熟悉的技術、無外部依賴、內部小改動。
3

系統骨架

怎麼蓋

/to-architecture /frontend-spec /test-blueprint

出貨即刪，是鷹架不是真相。有 UI 才加 /frontend-spec；層佈局與 CI 時段還沒定才加 /test-blueprint。

跳過條件一個 session 做得完，或在既有架構內改（沒得選）。
4

拆解功能

切成什麼

/to-tickets

曳光彈票，每張標明自己的阻塞邊。第一張最薄，可以很難看。

跳過條件一張票就做完了。多 session 就不能跳。
5

建置

蓋

/implement /tdd /code-review

一張票一個 session：/clear → /implement → 回 /clear。/implement 內部自己驅動 TDD，收尾跑一次程式碼審查。

不能跳唯一不能跳的一站。其餘六站都可能跳過。
6

驗收

有沒有蓋對

/uat-cases /browser-evidence

TC 編號一發即凍結；沒有新鮮證據不准說通過。證據落在 docs/uat/，走 evidence 分支 PR 合回基底分支。

跳過條件沒有人要看證據 —— 但先確認「沒有人」包不包含三個月後的你。
7

上線交付

別人能不能跑

/wizard /git-commit /git-pr /git-release

容器化、排程、CI secrets、Runbook 都走 /wizard —— 部署沒有專用技能，是工具箱的已知缺口。

跳過條件只有你自己用，掛了沒人在意。大部分專案一輩子不用走這站。

驗收標準不是命令，是一個人

找一個沒看過這個專案的人照 Runbook 跑一次。他卡住的每個地方，都是 Runbook 缺的一行。

你自己不能當那個閘門。

交流道：不是每次都從第 1 站開始

真實工作裡，你大部分時間從這裡進場。三條匝道各自匯入主線的不同位置 —— 匯錯位置，等於把地圖丟掉。

/triage

別人回報的 bug 或需求，推過一台由分診角色組成的狀態機，直到每張票都代理可接手或關閉。

→ 匯入第 5 站 /implement
/diagnosing-bugs

難修的 bug、原因不明：重現、最小化、立假說、下探針、修好、補回歸測試。

→ 病根在架構時，轉 /improve-codebase-architecture
/wayfinder

題目大到不知從何下手，先畫成一張決策票地圖，一次解一張，直到路清晰。

→ 匯入第 1 站 /to-spec，不能直接跳 /implement

Session 邊界決策樹

由上往下，第一個 yes 就是答案。/compact 排最後不是因為它不好，是因為上面四個都更便宜或更精準。

01下一階段需要這一階段當原始資料，或還有約 150k token 空間？繼續
02這個 context 對接下來完全無關？/clear
03要換 harness、換目錄、交給別人，或分岔側支線？/handoff
04任務夠明確，可以離開鍵盤讓它跑？子代理
05以上皆非/compact（帶指令）

Session 規則

第 1 到 2 站同一個 session 一路做完，中間不 /clear —— 規格需要訪談的原文，不是它的摘要。

第 4 站之後，每張票各開一個新 session。

Session 快滿了就 /handoff，開新 session 貼路徑接著做。

搞錯的代價是單向的

清掉相關的 context，你會失去「為什麼」—— 看 diff 看不回來。

從 /compact 開始的失敗模式：新 session 對某個被摘要壓平的決定「很有自信地說錯」。

完整決策樹在 .claude/skills/compass/PHASE-BOUNDARIES.md。

全部 36 個技能

依功能分群。卡片上緣的顏色就是觸發權：藍 = 只有你打字才會啟動（24 個，編排流程的都在這裡）、紫 = 代理判斷吻合會自己伸手（12 個，裝紀律的都在這裡）。

主線七站

9idea → ship
/to-spec

把當前對話收斂成一份規格，並發佈到議題追蹤器。

/feasibility

規格與拆票之間補上可行性一關：技術風險、競品對照、成功指標、量級成本，收在 ✅／⚠️／❌ 判決。

/to-architecture

技術棧、資料模型、API 合約。每個取捨仍寫成獨立 ADR，架構文件只引用不重述。

/frontend-spec

有 UI 的規格產出路由表、每頁 design brief、四態畫面（Loading／Empty／Error／Success）的 .pen mockup。

/test-blueprint

提案測試藍圖 —— 層佈局、縫清單、CI 時段；核准後產出靜態層檢查腳本與 CI workflow。

/to-tickets

把計畫、規格或對話切成一張張曳光彈票，每張都標明自己的阻塞邊。

/implement

依規格或一組票建置，在議定的接縫上驅動 TDD，收尾跑一次程式碼審查。

/uat-cases

從規格與使用者故事推導 UAT 案例，發出凍結的 TC 編號，維護 docs/uat-cases.md。

/browser-evidence

把既定案例清單跑成可交付的證據 —— 截圖或原始回應、網路紀錄與被測版本 manifest。

交流道

3不從第 1 站進場時
/triage

把外來議題推過一台由分診角色組成的狀態機，直到每一張都代理可接手或關閉。

/diagnosing-bugs

對付硬 bug、間歇性失敗與效能回歸的紀律迴圈 —— 重現、最小化、立假說、下探針、修好、補回歸測試。

/wayfinder

把龐大而迷霧重重的工程畫成一張決策票地圖，一次解一張，直到通往終點的路清晰為止。

詞彙層

3問題出在「詞」而不是流程
/grilling

就一個計畫、決策或想法窮追不捨地拷問使用者 —— 壓力測試自己的思路。

/grill-with-docs

同樣的拷問，但沿路留下紙本軌跡：術語表與 ADR。有 codebase 時用這個。

/domain-modeling

建立並磨利專案的領域語言 —— 挑戰模糊術語、拆開超載的詞、把難以回頭的決策寫成 ADR。

建置紀律

2/implement 內部自己會叫
/tdd

測試驅動開發，紅—綠—重構。要寫出能撐過重構的測試時單獨叫它。

/code-review

沿兩條軸審查自某個定點以來的 diff：Standards（有沒有遵守 repo 規範）與 Spec（有沒有做到票要求的事）。

Git 流程

4分支生命週期，一階段一個技能
/git-commit

只提交你 staged 的內容，寫英文 commit 並推上遠端；絕不代替你 stage。

/git-merge

把指定分支合併進當前分支；發生衝突時停下來分析與建議，解法是你的決定。

/git-pr

檢視分支所有 commit 開出 PR；合併後同步 main、清理本地與遠端分支。

/git-release

更新版本號，把兩版本間的 commit 彙整成繁中發布摘要，打 tag 並發佈 release 頁面。

程式庫健康

2不在主線上
/improve-codebase-architecture

勘查程式庫的深化機會，排序後呈上，再對你挑中的那一個進行拷問。挑中即產生新題目，回到第 1 站。

/refactor

在不改變可觀察行為的前提下重整結構：特徵測試護網、一次一個 transform、綠燈即提交。

Session 與導航

3context 的管理
/compass

問這個情況該用哪個技能、走哪條流程。工具箱的路由器。

/handoff

把當前對話壓縮成一份交接文件，讓全新的 session 能接手這份工作。

/wait-what

停 —— 剛才那段沒讓人聽懂，要求代理用專案的詞彙重新講一次。

前置與編排

3跑在流程之外
/setup-skills

為 repo 設定議題追蹤器、領域文件位置與 git 護欄 hook。每個 repo 初始化跑一次。

/implement-all

從追蹤器抓出可動工的票，依阻塞邊排程，每張票派一個子代理跑 /implement。只編排不動手。

/prototype

做一個用完即丟的原型回答一個設計問題 —— 邏輯用可執行的程式，UI 做幾個可切換的變體。

需要人的地方

3代理做不到的那一段
/wizard

生成互動式 bash 精靈，引導人類完成只有人能做的步驟：開通基礎設施、憑證、CI secrets。

/to-questionnaire

把一個你無法獨力回答的決策，做成一份問卷交給掌握答案的人填。

/management-frameworks

問題其實是管理問題不是工程問題時：目標設定、流程改善、根本原因、決策怎麼拍板。

畫圖

2要給人看的時候
/diagram

依受眾與情境挑選最合適的圖表並繪製，缺資訊時先畫草稿再問。

/svg-palette

SVG 繪圖的色盤與用色規則 —— 靛青階＋單一橘強調，可用公司 CI 色覆蓋。這頁就是用它畫的。

寫給代理讀的東西

2工具箱自己的維護
/writing-for-agents

撰寫給代理讀的文件。要建立或編輯技能、或修改 AGENTS.md、CLAUDE.md 時用。

/writing-hooks

判斷哪條規則該從散文降成 hook、hook 該不該說話、怎麼防它靜默腐爛。

兩個要記住的限制

「使用者觸發」不是每個平台都有

藍色那 24 個靠 disable-model-invocation: true 鎖住。GitHub Copilot 與 Google Antigravity 都不支援這個欄位 —— 在那裡，編排型技能會被代理自行啟動。

緩解方式是那些技能的 description 本來就寫成不帶觸發語的人話摘要，但那是降低機率，不是關掉開關。這條課程線實質是 Claude Code 取向。

第 7 站有個洞

部署本身沒有專用技能，是工具箱的已知缺口。用 /wizard 生一支互動精靈補上，把只有人能做的那幾步寫死成步驟。

改了任何技能，記得回頭改 docs/SKILL-MAP.md —— 漏改會被 scripts/check-skill-map.sh 擋下來。
