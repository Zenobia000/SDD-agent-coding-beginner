# 四級系統與最小可行文件集

> 你該寫多少文件，取決於你在做哪一級的東西。
> 對應 [`DEFINE.md`](../DEFINE.md) 第 0 站。

---

## 四級系統

「簡單畫個架構圖就開工」這句話對不對，完全取決於你在做哪一級。

| 等級 | 要證明什麼 | 一張簡單架構圖夠嗎 | 典型的存活時間 |
|---|---|---|---|
| **POC**（概念驗證） | 這件事技術上做不做得到 | 夠 | 幾天到幾週，證明完就丟 |
| **MVP demo** | 這東西有沒有人要 | 勉強夠，要補主流程與資料 | 幾週到幾個月 |
| **Product**（正式產品） | 能不能持續被使用 | 不夠 | 年 |
| **Enterprise** | 能不能治理、維運、擴充 | 絕對不夠 | 十年 |

**no-code AI 平台生出來的東西，落在 POC 到 MVP demo 之間。**

這不是貶低。POC 的價值就是**用最小成本證明或推翻一個假設** —— 兩個週末換掉三個月的方向錯誤，這是所有工程活動裡投資報酬率最高的一種。

## 最常見的災難：把 POC 當 Product 用

死法每次都一樣：

1. 用 no-code 平台做出一個能跑的東西，很興奮
2. 給朋友用，朋友說不錯
3. 開始有真實使用者，開始存真實資料
4. 繼續加功能，每次都用「再叫 AI 改一下」的方式加
5. 某天資料沒了 / 某天改壞了回不去 / 某天發現個資存在一個你不知道在哪的地方

**第 3 步就已經是 Product 了，但文件、備份、權限、測試全部還停在 POC。**

分界線很清楚，就一句話：

> **當有一個「不是你」的人，開始依賴這個東西保存他的資料時，它就不再是 POC 了。**

跨過這條線，就該換軌 —— 去 [`claude`](../../tree/claude)、[`antigravity`](../../tree/antigravity) 或 [`progressive-sdd`](../../tree/progressive-sdd) 學怎麼真的做。

## 各級的文件下限

| 等級 | 至少要有 | 這條線教的 |
|---|---|---|
| **POC** | 種子簡報 + PRD + SRS | ✔ 全部 |
| **MVP demo** | 上述 + 資料模型 + 主流程圖 | ✔ 第 6 站的 SAD 覆蓋 |
| **Product** | 上述 + API 契約 + 測試案例 + 部署與回滾程序 + ADR | ✘ 超出範圍 |
| **Enterprise** | 上述 + 治理流程、稽核、權限模型、SLA、災難復原 | ✘ 超出範圍 |

## 最小可行文件集（MVD）

回到沒有 AI 的年代，一個產品專案最少需要這 7 份文件。列在這裡不是要你全寫，是**讓你知道自己少了哪幾份，以及少了會怎樣**。

| # | 文件 | 用途 | 沒有會怎樣 | 這條線在哪一站 |
|---|---|---|---|---|
| 1 | Problem Statement | 定義為什麼做 | 做出沒人要的東西 | 第 1–2 站、PRD §1 |
| 2 | User / Business Flow | 定義流程 | 系統流程混亂 | PRD §3 |
| 3 | Scope / Non-scope | 定義邊界 | 需求無限膨脹 | PRD §4 |
| 4 | Architecture Diagram | 定義系統組成 | 每個人各做各的 | SAD 圖 1 |
| 5 | Data Model | 定義資料關係 | **後期最難改的東西** | SAD 圖 2 |
| 6 | API Contract | 定義介面 | 前後端整合爆炸 | ✘ POC 沒有後端，跳過 |
| 7 | Test Scenario | 定義驗收 | 上線前才發現不符 | SRS 的 Given/When/Then |

> MVD 的精神不是文件越多越好，而是**每個關鍵維度都有第一版，而且能持續演化**。

POC 級跳過 #6 是合理的 —— 你沒有後端。但 #5 資料模型跳不掉，那是唯一不可逆的東西。

## 文件狀態約定

每份文件開頭標一個狀態，避免「AI 草稿被誤用成正式決定」：

```markdown
| 版本 | v0.1 |
| 狀態 | draft ／ reviewed ／ approved |
```

- `draft` —— AI 產的，或還沒想完的
- `reviewed` —— 你逐條看過、刪過
- `approved` —— 你拍板了，接下來的東西以它為準

POC 級的專案通常只有你一個人，`reviewed` 和 `approved` 的差別就是「我看過」和「我決定照這個做」。看起來多此一舉，但**它會逼你在某個時間點真的做決定**，而不是永遠在改文件。

## AI 協作的分工原則

整條線都建立在同一個分工上，值得單獨講一次：

```text
第一輪  AI 發散     →   第二輪  人類收斂   →   第三輪  AI 結構化
                                                      ↓
第五輪  AI 轉開發資產  ←   第四輪  人類拍板
```

| 輪 | 誰主導 | 做什麼 |
|---|---|---|
| 1 發散 | **AI** | 產出假設、選項、風險、Open Questions。**全部標成草稿，不下結論** |
| 2 收斂 | **人類** | 每條標「留 / 刪 / 問」。**這一輪不能給 AI 做** |
| 3 結構化 | **AI** | 把留下來的東西轉成 PRD / SRS / SAD 的格式 |
| 4 拍板 | **人類** | 通過 / 退回 / 改了再通過 |
| 5 產出 | **AI** | 生成實際的東西 |

**分工錯了，你會拿到一份不是你的產品。**

最常見的錯誤是第 2 輪也丟給 AI 做（「幫我挑最重要的三個」）。AI 挑的是最泛用的，不是最適合你的 —— 因為它不知道你在第 1 站說的那些細節有多重要。
