# Prompt 速查卡

> 全站的 prompt 集中在這裡，方便複製。
> **完整的說明、為什麼這樣寫、卡關處理，在 [`DEFINE.md`](../DEFINE.md)。**
> 只複製這裡的 prompt 而不讀教材，你會拿到形式，拿不到判斷。

方括號 `[ ]` 的部分換成你自己的。

---

## P1 —— 第 1 站：逼問你的痛點

> 先填完 [`templates/pain-point-intake.md`](../templates/pain-point-intake.md) 六格再貼這段，
> 連同填好的表一起貼進 System Instructions 或常駐指令欄位，效果比貼在對話裡好。

```text
你是一位懷疑論者，任務是把我下面這張「現況／期望」表逼問成一個
具體、有數字、禁得起挑戰的痛點。你不是來安慰我或幫我把話講漂亮的。

規則：
1. 一次只問我一個問題。問完停下來等我回答，不要自問自答。
2. 我的回答如果模糊（例如「有時候」「蠻多的」「很麻煩」），
   追問到我給出具體的次數、金額、時間或例子為止。不要接受形容詞當答案。
3. 檢查我表格裡的矛盾：如果「現況」跟「期望」寫得差不多，直接問我
   「這兩者的差別到底是什麼」，不要幫我腦補一個差別。
4. 至少追問一次「為什麼是這件事，不是別的」和「為什麼是現在，不是
   三個月前或三個月後」——我的答案如果只是「就是覺得煩」，繼續追問，
   直到出現一個具體事件或轉捩點。
5. 不要給我解法，不要建議我做 App。你的工作是問，不是答。
6. 問滿 8 到 12 題之後，用下面的格式收尾：

   【時機】我在什麼情況下會遇到這件事、多久一次
   【症狀】具體發生什麼、我當下怎麼反應
   【代價】我因此損失了多少錢／時間／心情（要有數字）
   【現在怎麼解】我現在實際上是怎麼處理的，為什麼不夠好
   【如果解決了】我的生活具體會有什麼不一樣，這個不一樣我會不會真的有感覺

我填好的表：

[貼上你的 pain-point-intake.md]
```

**修正用**：
- AI 一次問十題 → `請一次只問一題，問完等我回答。`
- AI 開始給解法 → `請回到逼問的角色，繼續問我問題。不要提出解法。`

## P2 —— 第 3 站第一輪：meta-prompt（求 prompt）

```text
[用兩三句話講你的情境，要有具體數字和身份]

我想針對這件事做一個工具。
請先不要給我解法 —— 請告訴我，要讓 AI 好好處理這類問題，
專業的 prompt 該怎麼寫？

請用 markdown 給我一份 prompt 範本，包含這四段：
Role（角色）／ User Profile（使用者輪廓）／
Constraints（約束，至少 5 條）／ Output Requirements（產出要求）。
```

**修正用**：
- 它直接給解法／給 code → `我要的是 prompt 範本，不是實作。請只給我 markdown 格式的 prompt。`
- 拿到的太空泛 → `請把 User Profile 量化（數量、金額、頻率），並把 Constraints 補到至少 8 條。`

## P3 —— 第 3 站第二輪：漸進加層（注入真實痛點）

```text
補充幾件我剛剛沒講、但其實是我最在意的事：

1. [你的真實限制／情境]
2. [你真正想要的那個瞬間]
3. [你不希望它變成什麼樣子]

請根據這些，把剛剛那份 prompt 範本改寫得更貼近我的情況。
一樣先不要給我解法。
```

> 第 3 點最有殺傷力。**「我不希望它變成什麼」比「我希望它是什麼」更能收斂。**

---

## P4 —— 第 3 站第三輪：逼出歧義　**整門課最重要的一段**

```text
在你根據這份 prompt 開始做任何東西之前，
請列出你必須替我假設、但我從來沒告訴過你的事情。

每一條請寫成：
- 【假設】你打算怎麼假設
- 【如果我的想法不一樣】會導致什麼東西做錯
- 【問我】一個能讓我拍板的問題

至少列 8 條，從影響最大的排到最小。不要問我瑣碎的顏色或字體。
```

**修正用**：
- 列出來的都是廢話（顏色、深色模式）→ `請只列會影響「資料怎麼存」或「數字怎麼算」的假設，介面外觀的不要列。`

**回覆格式**：一條一條回，每條寫「決定 + 理由」。這些會直接變成 PRD 的決策記錄。

## P5 —— 第 4 站：產 PRD 草稿

```text
以下是我的種子簡報與需求裁決記錄：

[貼上 seed-brief.md]

[貼上第 3 站的假設清單與我的回答]

請據此產出一份 PRD 草稿，包含以下六段：

1. 問題陳述 —— 為什麼要做，一段話
2. 目標使用者 —— 誰會用，他現在怎麼解決
3. 使用者主流程 —— 從打開到達成目的，用編號步驟寫，不超過 10 步
4. 範圍 / 非範圍 —— 這版做什麼、明確不做什麼
5. 成功指標 —— 可量測的數字
6. 開放問題 —— 還沒決定的事，每條附「什麼情況下會知道答案」

規則：
- 每一段的每一條，如果是你推測的而不是我講過的，請標記 [推測]
- 功能不要超過 5 個。如果你想到更多，把多的放進「非範圍」並註明理由
- 不要寫技術實作，這份文件不談怎麼做
- 我打算用 no-code AI 平台做這個 POC。「這版要做」裡的每一條功能，檢查它是否需要
  背景排程／自動觸發、需要伺服器端密鑰的第三方串接、多使用者權限與即時同步、
  複雜多步驟運算或規則引擎、自動化檔案解析與轉檔、複雜的多對多資料關聯。
  如果需要，不要幫我刪掉或縮小這個功能，保留完整版描述並標上
  `[no-code MVP 待簡化]`，附一句「建議簡化版：……」。我會自己決定要哪一版。
```

**修正用**：
- 給了 15 個功能 → `請只保留 3 個功能，並說明砍掉其他 12 個各自的理由。被砍的請列進非範圍。`
- AI 直接把某功能刪掉或縮小，沒給簡化版建議就先幫你決定了 → `不要直接刪或縮小，請照 no-code MVP 規則標記並附簡化版建議，我自己決定。`

**收斂**：每條標「留 / 刪 / 問 / 簡化」。**`[推測]` 的預設命運是刪**——要留，你得說得出為什麼你同意它。**`[no-code MVP 待簡化]` 的預設命運是接受簡化版**，不是刪；堅持要完整版就搬進開放問題，留給以後換 coding agent。背景說明：[`NOCODE-LIMITS.md`](./NOCODE-LIMITS.md)。

## P6 —— 第 5 站：產 SRS

```text
以下是我的 PRD：

[貼上你的 PRD]

請把它拆成 SRS，規則：

1. 功能需求編號 FR-01, FR-02...；非功能需求編號 NFR-01, NFR-02...
2. 每條需求必須附 Given / When / Then 格式的驗收條件
3. 每條需求必須標註來源（PRD 的哪一段）
4. 一條需求只講一件事。出現「並且」「同時」就要拆成兩條
5. PRD 沒講到的東西不要自己加。如果你認為缺了關鍵需求，
   列在最後的「建議補充」區，不要給編號
6. 寫不出 Then 的，不要硬編號，列進「無法驗證」區並說明原因

非功能需求請至少涵蓋這四類：
效能（多快）、資料（存哪、存多久、誰看得到）、
易用性（幾步完成）、失效行為（沒網路 / 輸入錯 / 資料空的時候怎樣）
```

**修正用**：
- 產出 40 條 → `請只保留支撐 PRD 那 3 個功能所必需的需求。其餘列進「建議補充」不給編號。`

## P7 —— 第 6 站：要架構選項（不要它替你選）

```text
以下是我的 SRS：

[貼上 SRS]

我要用 no-code 平台（Lovable / Bolt / Replit / AI Studio）做這個 POC。

請給我 3 個不同的架構方案。每個方案包含：
1. 適用條件 —— 什麼情況下該選它
2. 資料存在哪裡，以及使用者換一台裝置會發生什麼事
3. 優點
4. 風險 —— 特別是「做到一半才會發現」的那種
5. 哪些決定之後很難改（不可逆的部分）
6. 需要我拍板、你不該替我決定的問題

不要推薦，不要下結論。我要自己選。
```

**修正用**：
- 三個方案都差不多 → `請讓三個方案在「資料存哪裡」這件事上必須不同。`
- 看不懂技術名詞 → `請用不懂技術的人聽得懂的話重講一次，每個技術名詞都要有比喻。`

## P8 —— 第 7 站：build prompt 四段

> **分四段貼，每段貼完等它回應再貼下一段。**
> 完整範例：[`examples/subtrim/build-prompt.md`](../examples/subtrim/build-prompt.md)

### 第 1 段：要做什麼

```text
我要做一個 [PRD §問題陳述的一句話]。
使用者是 [PRD §目標使用者，一句話]。
這是一個 POC，只要能跑、能驗證想法，不需要考慮上線與擴充。

先不要開始做。請先複述一次你理解的需求，我確認之後再開始。
```

### 第 2 段：資料模型

```text
資料模型如下，請完全照這個結構，不要自己增減欄位：

[貼 SAD 圖 2；沒做第 6 站的話，直接列出你要存的欄位]

資料存在瀏覽器本機（localStorage），不上傳任何伺服器。
請提供匯出成 JSON 檔的功能。
```

### 第 3 段：功能（一次三條）

```text
請實作以下功能，每條後面是驗收條件，請確保都滿足：

[貼 SRS 的 FR-01 到 FR-03，含完整 Given/When/Then]

做完這三條就停下來，我要先驗收。
```

### 第 4 段：非功能需求

```text
以下是品質要求：

[貼 SRS 的 NFR 全部]

請檢查目前的實作是否滿足，不滿足的請修正，
並明確告訴我哪幾條你做不到、為什麼。
```

## P9 —— 第 7 站：驗收沒過時怎麼講

```text
[需求編號] 未通過。

驗收條件是：
- Given [貼原文]
- When [貼原文]
- Then [貼原文]

目前的狀況是 [你實際看到什麼]。
請 [具體要它怎麼改]，不要動其他部分。
```

**四個要素缺一不可**：

| 要素 | 作用 |
|---|---|
| 需求編號 | AI 知道你在講哪一條，不會順手改壞別的 |
| 貼上驗收條件 | AI 知道什麼叫「改好了」 |
| 你實際看到什麼 | 把「怪怪的」變成可處理的資訊 |
| **不要動其他部分** | **能省下你一半的來回** |

## P10 —— 通用：逼 AI 招認限制

> 每一輪結尾都可以用。**不問，它不會說。**

```text
以上這些，哪幾條你做不到？為什麼？
哪幾條你做了但只做到一半？
```

---

## 一句話總結這十張卡

| 階段 | 卡 | 核心動作 |
|---|---|---|
| 想 | P1 | 讓 AI **問你**，不是答你 |
| 想 | P2–P3 | 用 prompt **求** prompt，而且分兩層給 |
| 想 | **P4** | **逼它把替你做的假設攤出來** |
| 寫 | P5–P7 | AI 發散，**你收斂** |
| 生成 | P8–P9 | 分段餵，**用編號驗收** |
| 全程 | P10 | 主動要它招認做不到的 |

**P4 是這整套裡不可取代的一張。** 其他九張你都能自己摸索出替代品，只有 P4 是「你不知道自己不知道」的解藥。
