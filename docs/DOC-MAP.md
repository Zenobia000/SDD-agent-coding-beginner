# 這句話該寫在 PRD、SRS 還是 SAD？

> 三份文件最常見的問題不是「寫不出來」，是**同一件事寫在三個地方，然後互相打架**。
> 這份是判斷表。

---

## 一句話分工

| 文件 | 回答 | 一句話記法 |
|---|---|---|
| **PRD** | 為誰做、解什麼、**不做**什麼、怎麼算成功 | **為什麼**要有這個東西 |
| **SRS** | 具體要滿足哪些可驗證的需求 | **什麼**叫做做好了 |
| **SAD** | 系統由哪些部分組成、資料長什麼樣 | **怎麼**組起來的 |

---

## 判斷流程

拿到一句話，照這個順序問：

```text
這句話裡有技術名詞嗎（框架、資料庫、API、localStorage）？
   ├─ 有 ──────────────────────────────────▶ SAD
   └─ 沒有
        │
        這句話能寫成「Given / When / Then」嗎？
           ├─ 能 ───────────────────────────▶ SRS
           └─ 不能
                │
                這句話是在講「為誰、為什麼、值不值得」嗎？
                   ├─ 是 ───────────────────▶ PRD
                   └─ 不是 ─────────────────▶ 它可能不該存在
```

最後一格不是玩笑。**一句既不能驗證、又不解釋為什麼、又不描述系統的話，通常是廢話或願望。** 廢話刪掉，願望進 SRS 的「無法驗證區」。

## 對照表

同一件事在三份文件裡的樣子：

| PRD（為什麼） | SRS（什麼叫做好了） | SAD（怎麼組起來） |
|---|---|---|
| 使用者填到第四筆就會放棄，所以輸入速度是這個產品的生死線 | **NFR-02**：Given 使用者已知道要填的內容，When 從點新增到儲存完成，Then 不超過 3 個必填欄位、不需要換頁 | 新增與編輯共用同一頁上的面板，不做獨立路由 |
| 使用者的訂閱資料是敏感財務資訊，我不敢存 | **NFR-03**：Given 使用者新增訂閱，When 檢視網路請求，Then 沒有任何資料送到外部 | 儲存層用瀏覽器 localStorage，沒有後端 |
| 年繳攤平會跟真實帳單對不起來 | **FR-02**：Given 年繳訂閱下次扣款在 11 月，When 8 月檢視，Then 不計入 8 月總額但顯示平均月成本 | 計算層：cycle 為 yearly 時，依 nextChargeAt 判斷是否計入當月 |

**由左往右，每一格都更具體，而且每一格都追得回左邊那一格。** 追不回去的，就是有人在中間偷偷加了東西。

## 常見的擺錯

| 這句話 | 常被錯放在 | 該放 | 為什麼 |
|---|---|---|---|
| 「用 React 做」 | PRD | SAD | PRD 不談技術。談了，你就在還沒想清楚要做什麼之前先選了工具 |
| 「介面要簡潔好用」 | SRS | **哪裡都不放** | 不可驗證。改寫成「必填欄位 ≤ 3 個」才進 SRS |
| 「不做雲端同步」 | SAD | PRD §非範圍 | 這是產品決定，不是技術決定。技術上做得到，是你決定不做 |
| 「資料存 localStorage」 | PRD | SAD | 這是上一條的技術實作。PRD 說「不同步」，SAD 說「所以存本機」 |
| 「目標是幫使用者省錢」 | SRS | PRD §問題陳述 | 這是目的，不是需求。需求是「顯示總額」 |
| 「金額欄位只接受正整數」 | PRD | SRS（NFR 失效行為） | 這是可驗證的行為規則 |
| 「這個欄位以後可能會想加」 | SRS | SAD §不可逆的決定 | 這是架構風險，不是需求 |

## 三份文件的上下游關係

```text
seed-brief.md
      │  （痛點、約束、成功指標）
      ▼
   PRD.md ────────────────┐
      │  （每條需求標來源） │  （非範圍限制了架構選項）
      ▼                    ▼
   SRS.md ──────────▶  SAD.md
         （NFR 直接推出架構決定）
```

**箭頭只有單向。** 這代表：

- SRS 的每一條都要追得回 PRD 的某一段
- SAD 的每個決定都要追得回 SRS 的某一條，或 PRD 的某條非範圍
- **反過來不行**：不能因為「SAD 這樣比較好做」，回頭去改 PRD 說使用者要的其實是別的

最後這條是所有工程專案裡最容易犯、也最貴的錯 —— **讓實作方便反過來定義使用者要什麼。**

---

## 什麼時候該回頭改上游

不是不能改，是**改要留痕**。

| 情況 | 做法 |
|---|---|
| 寫 SRS 時發現 PRD 某條講不清楚 | **回去改 PRD**，然後 SRS 的來源標指向改過的那段 |
| 寫 SAD 時發現某條 NFR 做不到 | **不要偷偷放寬 NFR。** 在 SRS 標「無法達成」+ 理由，並在 PRD 開放問題留一條 |
| 第 7 站發現需求本身有矛盾 | **回第 5 站改 SRS**，PRD 開放問題加一條記錄。不要只在對話裡改一改 |

**對話會消失，文件不會。** 這是整條線唯一的理由。
