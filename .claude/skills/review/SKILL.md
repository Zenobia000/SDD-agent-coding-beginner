# Review — 審查

審查的價值來自**不知道作者為什麼這樣寫**。

寫 code 的人（人或模型）對自己的產出有系統性偏誤：看得懂含糊的命名，因為知道意圖；不覺得缺註解，因為記得原因；測試照著實作寫，所以測不到沒想到的情況。

所以審查時不要問作者的意圖。**只看 code 說了什麼。** 看不出意圖，本身就是一個發現。

需要真正獨立的視角時派 `reviewer` subagent——它在自己的 context 裡跑，看不到你們剛才的對話。

## 四個鏡頭

**它有沒有解決它宣稱要解決的問題。** 找出宣稱（spec、commit message、使用者的話），找出證據（測試？實際跑過？）。沒有證據的宣稱標成「未驗證」，不要當成通過。

**它有沒有帶進新問題。** 呼叫端還能運作嗎？改了行為但沒改測試嗎？錯誤路徑處理了嗎——不是只有 happy path。

**測試真的測到東西了嗎。** 弱斷言（`assert x is not None`）、同義反覆、mock 掉要測的東西本身、只測主流程——這四種讓覆蓋率好看但抓不到 bug。

**六個月後接手的人看得懂嗎。** 命名說得出意圖嗎？非顯而易見的決定有寫下為什麼嗎？有沒有要看三個檔案才理解得了的邏輯？

## 安全鏡頭

改動碰到認證、金流、檔案上傳、對外 endpoint、或處理使用者輸入時，加這一層。詳細清單在 [`../../references/security.md`](../../references/security.md)。

最短的版本是三個問題：**我能餵什麼進去**（含 header、檔名、第三方回應）、**它會流到哪裡**（SQL？shell？檔案路徑？HTML？prompt？）、**換個 id 我能不能看到別人的東西**。

第三個問題最常被漏掉，而它是最常見的漏洞。

## 架構鏡頭

改動讓某個模組同時知道太多事、或讓兩個模組必須一起改時，加這一層。判準與重構手法在 [`../../references/architecture.md`](../../references/architecture.md)。

## 重構

重構屬於這裡，不屬於紅綠燈循環。

前提是有綠燈測試護著。**沒有測試覆蓋的 code 不重構**——那不叫重構，叫重寫，而且你不會知道行為變了沒。

重構時測試不該改。測試跟著改就表示你改的是行為，那是另一件事，要回到 `tdd`。

## 回報的形狀

判定、然後最多五個問題，依嚴重度排。每個問題附**位置**（檔案:行號）、**證據**（引用實際 code）、**會怎麼壞**（什麼輸入 → 什麼結果）。

講不出「會怎麼壞」的具體情境，那可能不是問題。

最後列出**你沒能驗證的東西**。只講壞消息的報告，讀的人無法評估它查了多少。
