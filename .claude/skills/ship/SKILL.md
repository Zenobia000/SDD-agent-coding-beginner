# Ship — 交付

能上線不等於能維運。判準是**換一個人照著你留下的東西做，不用回頭問你**。

## 順序：便宜的先，不可逆的最後

品質檢查幾秒鐘、掃描幾十秒、考卷幾分鐘、寫維運卡十幾分鐘、部署可能不可逆。

部署到一半才發現 lint 沒過，代價高太多。**一站紅燈就停，不要「先上再說」。**

## 憑證：一定要掃歷史

`git rm .env` 之後 key 仍然在歷史裡。公開 repo 等同外洩。

```bash
git log --all --oneline --name-only --diff-filter=A -- '*.env' '*.env.*'
git log -p --all -S 'sk-' --oneline | head
```

翻到東西的時候，**第一件事是輪換那把 key**。清歷史是善後，不是修補——你不知道誰已經抓過那份 repo。

其餘掃描維度在 [`../../references/security.md`](../../references/security.md)。報告裡要包含**「不適用」那一段**：這個專案沒有的風險類別要明講查過了，只講壞消息的報告無法評估覆蓋範圍。

## 維運卡

一頁。超過一頁，半夜沒人會看。內容與範本在 [`../../references/ops.md`](../../references/ops.md)。

七格裡最重要的是**不可回滾的操作**。刪欄位的 migration、刪使用者資料、送出的通知——這些要在卡片上獨立列出來，因為未來的你在跑之前必須看到。

失敗模式**依實際發生過的頻率排，不是依理論可能性**。第一次寫沒有歷史資料時，用這個順序：設定沒帶到、外部服務掛了或改了、資料格式跟預期不一樣、資源不足、程式本身的 bug。每次真的壞掉後回來更新——這是維運卡唯一會持續增值的部分。

**沒演練過的回滾等於沒有回滾。** 沒演練就在卡上標「未演練」，不要寫得像已驗證。

## 健康檢查要兩層

淺層證明程序活著，深層跑一次真實的端到端動作。

只有淺層的系統會出現「監控全綠但沒人能用」。

## Commit 訊息

主旨用祈使句，說做了什麼。內文說**為什麼**——動機、取捨、影響範圍。

六個月後讀 git log 的人不需要你重述 diff，他需要知道當時你在權衡什麼。

## 風險線

低風險自動執行、事後查 log；高風險人類核准。**你的工作是畫出中間那條線，而不是選一端。**

全自動是陷阱，全人工是白做。判斷依據跟 `frame` 的分流一樣：可驗證性、可逆性、代價。
