# Spec — 契約

寫得更少，但寫到無法誤解。

Spec 的用途是讓你和模型對「要做什麼」有同一份理解。它不是給人看的文件，是**你們之間的合約**——所以判準是「同一份 spec 餵給不同模型，吐出來的結構應該一致」。不一致表示還不夠明確。

## 刪掉怕它出錯的叮嚀

Spec 裡的規則只有兩種。

**業務規則**是你的領域真的要求的：「金額無條件捨去到小數第二位」「來源必須是這三個網域之一」。它們可以驗證，留著。

**保母規則**是你怕模型出錯而加的：「請再仔細檢查」「請確保正確無誤」「請一步一步思考」。刪掉。

刪的理由不是它們囉唆，是**廢話是模型必須服從的雜訊**——你多寫一句沒用的，它就多一個要顧的東西。而且越強的模型越不需要你教它怎麼做：與其寫四個步驟教它流程，不如講清楚結果該長什麼樣。**刪掉過程，給它形狀。**

## 三層，按需要寫

**意圖層**永遠要寫：解什麼問題、誰用、成功長什麼樣。不寫等於沒方向。

**介面層**在有 API 或資料庫時寫：系統邊界的合約。不寫等於讓模型猜介面，而它猜得很有自信。

**行為層**寫主流程加邊界：對不對的判定條件。這層直接餵給 `evals`。

範本在 `templates/`：PRD、user story、API contract、DB schema、BDD scenarios、test cases、ADR。**挑需要的用，不必七份都寫。**

## 七個欄位

小需求用四格就夠：脈絡、任務（一句話）、約束、輸出格式。

大一點的展開成七欄：角色、目標、輸入、約束、輸出格式、**成功判準**、範例。

第六欄是接點——它直接變成 `evals` 的考卷。寫的時候就用「能不能拿去當考卷」來檢驗自己。

第七欄的範例是**對格式，不是教推理**。推理交給模型自己，你只需要示範輸出長什麼樣。

## 架構決策

遇到兩個以上合理選項在競爭時，值不值得寫下來看三題：影響超出單一功能嗎？有真正的取捨嗎？三個月後想換會痛嗎？三題都是才寫。

寫下來的價值不在你會回頭看，在於**未來的 session 會自動讀到**——它會參考過去的決定，而不是推翻它。範本是 `templates/spec-template.md`。

PRD 已經寫死的技術不用寫 ADR。那是條件，不是決策。

## 使用者說「不對」的時候

不是改 code，是回來對齊意圖。改 code 修的是症狀。
