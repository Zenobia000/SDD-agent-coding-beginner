# TDD — 紅綠燈

紅 → 綠是循環本身。這份是讓循環產出**值得留下的測試**的參考：什麼是好測試、測在哪、哪些是假測試、循環的規矩。

## 好測試測行為，不測實作

測試驗證的是公開介面的行為。實作可以整個換掉，測試不該跟著換。

好測試讀起來像規格：「空輸入時回傳友善錯誤」告訴你這個能力存在。它撐得過重構，因為它不在乎內部怎麼寫。

## 縫

**縫**是你觀察行為的公開邊界——不伸手進去也看得到結果的地方。測試住在縫上。

**先講好縫再寫測試。** 動手前寫下這次要測哪些縫，跟使用者確認。沒確認過的縫不寫測試。你不可能測完所有東西，事先講好縫，測試的力氣才會落在關鍵路徑和複雜邏輯上，而不是每個角落。

問一句：「這裡的公開介面是什麼？我們要測哪幾條縫？」

## 假測試

**耦合實作的**——mock 掉內部協作者、測私有方法、或從側門驗證（去查資料庫而不是用介面）。徵兆：你重構了但行為沒變，測試卻紅了。

**同義反覆的**——斷言用跟實作一樣的方式算出預期值（`expect(add(a,b)).toBe(a+b)`、手工推出來的快照、常數等於自己），它從構造上就會過，永遠不可能跟 code 意見相左。**預期值必須來自獨立的真相源**：已知的字面值、手算的例子、規格。

**橫向切的**——先寫完所有測試再寫所有實作。整批寫的測試驗證的是**想像中的**行為：你測的是東西的形狀而不是使用者眼中的行為，測試對真實改動變得不敏感，而且你在理解實作之前就把測試結構定死了。改成**縱向切**：一個測試 → 一個實作 → 重複，每個測試都是一發**曳光彈**，回應上一輪教你的事。

## 循環的規矩

**先紅再綠。** 先寫會失敗的測試，然後只寫剛好讓它過的 code。不要預先實作未來的測試，不要加投機的功能。

**一次一片。** 一條縫、一個測試、一份最小實作。

**重構不屬於這個循環。** 它屬於審查階段（見 `review`），不屬於紅 → 綠。

## 邊界 case 從哪來

空、零、負數、極大、null、格式不對、重複、順序顛倒。

還有時間、網路、隨機——這三個要注入或凍結，不要依賴真的。依賴真實時間的測試會在半夜壞掉，而你隔天才發現。

## 為既有 code 補測試

那是不同的事。這時測試記錄的是**現在的行為**，不保證那是**正確的行為**。

發現目前行為看起來是 bug 時，照現況寫測試然後標記出來，不要順手改掉——那會讓你同時在改兩件事，出問題時分不清是哪件。

## 相關
