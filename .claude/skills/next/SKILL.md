# Next — 現在做什麼

這裡沒有必經的關卡。**這些技能是參考書，不是流程圖**——你可以任何順序取用，也可以完全不用。

打 `/next` 就是問一句「以我目前的狀態，接下來做什麼比較不會白做」。

## 先看現況

實際去看檔案，不要憑對話記憶：有沒有把題目寫下來、有沒有 spec、有沒有考卷、有沒有測試、測試現在是綠的嗎、有沒有未提交的改動。

## 建議

**還沒動手**，題目也還很模糊 → `frame`。花二十分鐘把痛點問成可判斷的題目，通常省下的比花掉的多。已經很清楚了就直接開始，不用先寫文件。

**要開始寫了但範圍講不清楚** → `spec`。功能牽涉到 API、資料結構、或別人要接的介面時特別值得。純粹自己用的小東西可以跳過。

**改了兩三輪還在原地** → `evals`。這通常不是實作問題，是沒有判準——你在憑感覺判斷有沒有進步，而感覺不可重現。

**要寫新功能或修 bug** → `tdd`。先寫會失敗的測試。

**寫完了，要 commit 或 PR** → `review`。碰到認證、金流、上傳、對外 endpoint 時加上安全鏡頭。

**要部署或交給別人** → `ship`。

**卡在選擇或找不到根因** → `decide`。

## 可以派出去的工作

`explorer` 在陌生 code 裡找東西、`test-writer` 為既有 code 補測試、`reviewer` 給獨立視角的審查、`security-auditor` 對高風險改動做深度推演。

會產生一堆你不想看的中間資訊，或需要不被你的意圖污染的視角時，派出去。

## 一件貫穿的事

改東西的時候，先講清楚三件事：**這輪動哪些檔案、什麼算變好、幾輪後停**。

不是規定，是經驗——這三件事沒講清楚的時候，改到第五版你會分不清哪版比較好，也不知道什麼時候該收手。

第二件（什麼算變好）最常被跳過，也最貴。
