# Frame — 問對問題

大部分失敗的軟體，是對錯誤問題的正確答案。

這件事的產出是**一頁紙**：交給另一個人，他能做出差不多的東西。

## 用訪談，不要填表

問一題，等回答，讓答案決定下一題。一次丟五題會得到五個敷衍的答案；一次一題會得到一個真的答案。

三件事要追到具體為止：

**現在的成本。** 誰在做、一次多久、多久一次。三個數字。「很煩」不是數字，而一個熬了一年卻講不出這三個數字的痛，通常不值得為它寫程式。

**判準。** 如果兩個版本擺在面前，你會看什麼來決定哪個好？這題最重要，也最常被滑過去。卡住時反過來問：**什麼情況你會說「這個做壞了」？** 負面例子比正面例子好講。

**邊界。** 這次**不做**什麼？現在做功能很便宜，所以需求會自己長大——這張清單就是攔住它的東西。

## 分流：這件事能交出去多少

兩個軸決定自主程度：程式判不判得出對錯，以及做錯的代價。

判得出、做錯很便宜 → 讓它自己跑，事後看 log。判得出但代價高 → agent 做、人核准，而且僅限**動作可逆**時。只判得出一部分 → agent 產候選，人挑。完全判不出 → **框還沒問完**。

最後一格不是拒絕，是訊號：繼續拆。「文案要好」抗拒檢查；「三十字內、含產品名與一個動詞、避開這十個詞」不抗拒。拆到有東西可以核對為止，剩下真正主觀的那塊再交給人。

**不可逆的動作留給人，不管它多可驗證。** 刪資料、force push、寄信、花錢——檢查告訴你它有沒有做對，不會告訴你能不能收回來。

## 寫下來

一頁：一句話講清楚給誰用、取代什麼；三個成本數字；判準（每條都能用「是/否」回答）；不做什麼；分流結論與理由。

然後是第一輪的邊界——**哪些檔案在範圍內、什麼算變好、幾輪後停**。這三件事決定了你是在迭代還是在遊蕩。

## 框好了的訊號

使用者講得出「什麼情況我會放棄這個題目」。講不出來，表示他還沒框，只是已經決定要做了。
