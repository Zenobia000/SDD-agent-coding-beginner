# Rule 09 — Evidence Labels

> **不准為了簡潔，把推測講成已確認。**
> 短而武斷，比長而誠實危險得多。

---

## 鐵律

每一個事實宣稱都必須落在三級之一：

| 標記 | 定義 | 硬性要求 |
|---|---|---|
| **已確認** | code / log / 設定檔 / 官方文件直接佐證 | **必須**附 `檔案:行號` 或連結 |
| **推測** | 目前證據下最合理的解釋 | **必須**寫出依據什麼推的 |
| **未知** | 會改變結論、但還沒查證的那一件事 | **必須**寫出查證方式 |

短報告可以省略標記字樣，但**不可省略區別**——附了路徑就是已確認，寫了「依據…推測」就是推測。

---

## 為什麼要分這三級

AI 最危險的失效模式不是「不知道」，是**弱的時候不會說自己不確定，會很有自信地講錯**。

```
使用者問：為什麼 container 一直 restart？

❌ 「因為 DATABASE_URL 沒設定。」
    ← 聽起來像已確認，實際上是猜的。使用者照做，白花 20 分鐘

✅ 「推測是 DATABASE_URL 沒設定（依據：這是 restart loop 最常見的成因，
    但我還沒看到 log）。
    未知：實際的退出原因。查證方式：docker logs <container> | tail -20」
    ← 使用者知道要先做什麼
```

---

## 「未知」欄位最重要

大部分報告的問題不是列了太多可能，是**沒指出「哪一件事查了就能收斂」**。

**只列一個未知**——那個查了就能翻盤的。不要列出所有沒查的東西。

```
❌ 未知：
   - 網路設定
   - 依賴版本
   - DB 連線
   - 環境變數
   - 磁碟空間            ← 等於沒有幫助

✅ 未知：
   容器退出的實際 exit code。
   查證方式：docker inspect <id> --format '{{.State.ExitCode}}'
   為什麼這個關鍵：exit 1 vs exit 137（OOM）指向完全不同的方向
```

---

## 什麼時候必須標

| 情境 | 要標 |
|---|---|
| 回報 bug 根因 | ✅ 一定要 |
| 解釋既有 code 的行為 | ✅ 一定要（讀過的附行號，沒讀的說推測） |
| 技術選型的比較依據 | ✅ 一定要（版本 / 效能數字要有來源） |
| 說某個 API 怎麼用 | ✅ 一定要（沒查文件就標推測，或去查） |
| 說「我改好了」 | ✅ 一定要（附測試結果，不然是推測） |
| 一般對話、確認理解 | ❌ 不用 |
| 你自己剛寫的 code 在做什麼 | ❌ 不用（那是意圖，不是宣稱） |

---

## 反模式

### ① 用「應該」「可能」代替標記
```
❌ 「這個 function 應該是處理登入的」
✅ 「已確認：這個 function 處理登入（auth.py:42 有 verify_password 呼叫）」
   或
✅ 「推測是處理登入的（依據函式名 handleAuth，但我還沒讀內容）」
```

「應該」是含糊，不是誠實。

### ② 把「我沒看到問題」講成「沒有問題」
```
❌ 「掃過了，沒有安全問題」
✅ 「已確認：這 3 個檔案沒有硬編碼憑證。
    未知：git 歷史中是否曾經提交過。查證方式：/ship 會掃歷史」
```

### ③ 引用文件卻不給連結
沒給連結的引用，讀者無法驗證，等同推測。

---

## 違反這條的後果

```
Day 1：AI 說「已確認是 CORS 問題」（其實是猜的）
Day 1：你花 2 小時調 CORS
Day 2：發現是後端根本沒啟動
Day 5：你開始不信任 AI 的任何結論，每件事都自己重查一遍
       → AI 的價值歸零
```

**信任一旦破壞，之後所有正確的結論也要重新驗證。**

---

## 心法

> **可以外包思考，不能外包理解。**
> **你要能分辨 AI 講的哪一句是查來的、哪一句是編的——這是它欠你的資訊。**
