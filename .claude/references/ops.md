# 部署與維運

需要時查。`ship` 指向這裡。

---

## 一頁維運卡

超過一頁，半夜沒人會看。七格：

**這是什麼** — 一句話。壞掉的時候誰會有感覺？

**長什麼樣** — 3–8 個節點的圖。超過 8 個表示該拆服務了。

**怎麼部署** — 可直接複製執行的指令，加上「預期看到什麼」和「花多久」。

**怎麼確認它活著** — 見下方「兩層健康檢查」。

**壞了先看哪裡** — 最多五條，依實際發生頻率排。

**怎麼回滾** — 指令、耗時、**會失去什麼**、以及**不可回滾的操作**。

**什麼情況要找人** — 症狀、找誰、多急。

判準是：拿給沒碰過這個系統的人，他能不能照著救回來。他有任何一個問題要回頭問你，這張卡就還沒寫完。

---

## 兩層健康檢查

淺層證明程序活著（`/healthz` 回 200）。

深層跑一次**真實的端到端動作**。

只有淺層的系統會出現「監控全綠但沒人能用」。

---

## 失敗模式的順序

**依實際發生過的頻率排，不是依理論可能性。**

第一次寫沒有歷史資料時用這個預設：

1. 環境變數或設定沒帶到 —— 最常見，也最容易誤診成別的
2. 依賴的外部服務掛了或改了 —— API 限流、憑證過期、對方改版
3. 資料格式跟預期不一樣 —— 上游改了 schema
4. 資源不足 —— 記憶體、磁碟、連線數
5. 程式本身的 bug —— 其實最少見

每次真的壞掉後回來更新這個順序。**這是維運卡唯一會持續增值的部分。**

## 回滾

**沒演練過的回滾等於沒有回滾。**

「revert 上一個 commit 然後重新部署」不是回滾計畫，是一句話。演練過的版本長這樣：指令、實際耗時、會失去哪些資料、上次演練的日期。

沒演練就標「未演練」，不要寫得像已驗證。

### 不可逆的操作

這一格是整張卡最重要的資訊：

| 操作 | 可逆 | 降風險 |
|---|---|---|
| 部署新版程式 | ✅ | 保留前一版 artifact |
| 加欄位的 migration | ✅ | — |
| **刪欄位 / 改型別** | ❌ | 分兩次部署（先停用再刪）；先備份 |
| **刪使用者資料** | ❌ | 軟刪除 + 保留期 |
| 換 API 版本 | ⚠️ 看呼叫端 | 舊版並行一段時間 |

不可逆的操作不進自動流程。

## 部署目標

| 專案型態 | 建議 | 回滾方式 |
|---|---|---|
| 純靜態前端 | Cloudflare Pages / GitHub Pages | 後台切回上個 deployment |
| 前端 + 輕量 API | Cloudflare Workers / Vercel | 平台的 rollback 指令 |
| 有狀態後端 + DB | Fly.io / Railway | 重新部署上一版 image；**DB 另外處理** |
| 排程工作 | GitHub Actions cron | 停用 workflow + 重跑上一版 |

## 環境變數

啟動時就驗證必要的變數存在，不要等到第一次用到才炸。

「設定沒帶到」是第一名的失敗模式，而它的診斷成本很高——症狀通常看起來像別的問題。
