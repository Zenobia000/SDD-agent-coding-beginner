# /ship — 交付總檢

> 這是 S7 的主要動作。**一站紅燈就停，不要「先上再說」。**

## 執行順序（不可調換）

```
① /verify     品質五維度 —— 格式 / lint / 型別 / 測試+覆蓋率 / 依賴
      ↓ 全綠才往下
② /sec-scan   資安五維度 —— 憑證(含歷史) / 暴露面 / 輸入 / 授權 / 依賴漏洞
      ↓ 無阻擋項才往下
③ 考卷回測    跑 evals/ —— 通過率不得低於基線
      ↓ 不退步才往下
④ /ops-card   維運卡 —— 部署 / 健康檢查 / 回滾 / 找誰
      ↓
⑤ 部署        照 ops-card 第 3 格執行
      ↓
⑥ 驗收        照 ops-card 第 4 格確認活著
```

**為什麼是這個順序**：由便宜到昂貴、由可逆到不可逆。
`/verify` 幾秒鐘，部署可能是不可逆的。先做便宜的檢查。

## 每一站的處理

### 紅燈時
**停下來，不要繼續往下**。回報：

```
在第 ② 站停下：/sec-scan 有 2 個阻擋項

1. <標題> — <位置> — <修法>
2. <標題> — <位置> — <修法>

下一步：<修第一個的具體動作>
```

### 全綠時
只回報一行往下走，不要每站都寫落落長的報告。

## Step ③ 考卷回測的細節

```
基線（<日期>）：<N> / <M>
現在：        <N'> / <M>

判定：不退步 / 退步了
```

**退步了就是紅燈**，即使測試都綠燈。
理由：測試測的是「不會壞」，考卷測的是「做得好」。兩者不能互相取代。

沒有 `evals/` 目錄 → 明講「這個專案沒有考卷，跳過第 ③ 站」，並建議跑 `/eval-set` 補上。

## 最終輸出

```
## 交付結果
已上線 / 未上線（停在第 <N> 站）

## 網址
<公開 URL>

## 這次交付的東西
- <一句話>

## 驗收證據
- 健康檢查：<實際跑過的結果>
- 主流程：<實際跑過的結果>
- 考卷：<N/M>

## 未驗證的
<你沒能實際確認的，明講>

## 下一步
<恰好一個動作 —— 通常是 /retro>
```

## 硬規則

- ❌ **不准跳站** —— 即使使用者說「趕時間」
- ❌ **不准在紅燈時繼續往下**
- ❌ **不准把「應該可以」寫成「已驗收」** —— 沒實際跑過就標未驗證（`rules/09`）
- ❌ **不准自動執行部署指令** —— 部署是不可逆邊界，列出指令讓使用者自己按
- ✅ **每站只報結論** —— 詳細內容各自的 skill 已經有了，不要重述
