# Rule 08 — Loop First

> **沒有評分函式，不開跑。**
> 這條在所有規則之前生效——包括 spec-first 和 TDD。

---

## 鐵律

任何工作開始前，四拍的四格必須都填得出來：

```
① 劃邊界 Constrain  —— 這一輪只准動什麼？
② 放它跑   Run       —— 產候選，中途不停下來問人
③ 打分數   Score     —— 怎麼判斷這輪比上輪好？
④ 收判斷   Decide    —— 跑幾輪後收工？
```

**任一格填不出來 → 停下來問使用者，不要硬跑。**

---

## 三條乾淨限制（缺一條就會發散）

| 限制 | 白話 | 鎖住什麼 | 沒有的後果 |
|---|---|---|---|
| ① **一個範圍** | 這輪只准動 `src/summarizer.py` | 範圍 | 到處亂改，diff 爆炸到無法 review |
| ② **一個評分** ★ | 「好不好」要能變成一個數字或 yes/no | 目標 | 「感覺比較好」，證明不了有進步 |
| ③ **一個預算** | 最多跑 3 輪 / 最多 20 分鐘 | 成本 | 無限重試燒 token |

**第二條最常被省略，也最致命。**

---

## 評分函式怎麼來

依答案的性質選裁判，**能用程式判就別請 LLM**：

| 答案性質 | 裁判 | 例子 |
|---|---|---|
| 有標準答案 | **程式 assertion** ★ | 測試綠燈、schema 驗證通過、lint 零錯 |
| 有參考資料 | 比對來源 | 每個宣稱都指得出出處 |
| 沒有標準答案 | LLM-as-judge（**後備手段**） | 文案語氣、UI 排版 |

判準一律**二元**（pass / fail），不要 1–10 分：

```
❌ 1–10 分 —— 不可重現。今天給 7 分，明天同一個東西給 5 分
✅ 對 / 錯 —— 可以加總成通過率：通過數 ÷ 總數
```

寫不出 yes/no 判準的條件，就是還沒想清楚。
「夠不夠專業」「是否夠詳細」❌ ／「結尾有致歉或感謝」「回傳的 JSON 有 `citations` 欄位且非空」✅

---

## 什麼情況可以跳過

| 情境 | 為什麼可以跳 |
|---|---|
| 純樣式 / 文案 / typo | 沒有「更好」的定義，看一眼就知道對不對 |
| 一次性探索（「這個 API 長怎樣？」） | 目的是取得資訊，不是產出成品 |
| 使用者明確說「先隨便跑跑看」 | 這是使用者的判斷，尊重 |

**其他一律不能跳。**

---

## 放手之後，人類只做三件事

跑起來後不要每一輪都插手：

1. **看分數曲線** —— 有沒有在進步？停滯了嗎？
2. **抽查最好的那個** —— 分數高不等於真的對
3. **決定什麼時候收工** —— 邊際效益遞減時就停

中途插手改 prompt，會讓你分不清「變好」是因為改動還是因為隨機性。

---

## 違反這條的後果

```
Day 1：沒定評分，AI 改了 8 版，每版都「看起來不錯」
Day 2：發現第 3 版其實最好，但已經覆蓋掉了
Day 3：想證明「新版比舊版好」，發現沒有共同的比較基準
Day 7：只能靠「我覺得」說服自己和團隊
```

---

## 心法

> **寫不出 `check()` 的任務，先別丟給模型。**
> **「我覺得變好了」不是工程。**
> **沒有拿同一份 dataset 比較，就不准說「改好了」。**
