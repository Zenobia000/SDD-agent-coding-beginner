# /eval-set — 二元判準考卷產生器

> **核心**：先有考卷，才有開發。「我覺得變好了」不是工程。

## 🚨 自動觸發訊號

### 強訊號
- 「怎麼算做完」「怎麼驗收」「什麼叫做好」
- **「感覺比較好」「好像順一點」** ← 最強訊號，這句話等於承認沒有判準
- 準備跑 `/loop` 但第②格（評分）填不出來
- `/spec-it` 剛跑完，`docs/PRD.md` 有 Success criteria 但沒有對應的可執行檢查

### 反訊號
- 純樣式 / 文案（看一眼就知道對不對）
- 已經有測試套件覆蓋這個行為（那就是考卷）

---

## 執行步驟

### Step 1：找出判準的來源

依序找，找到就用：

1. `docs/PRD.md` 的 **Success criteria** 欄位 ← 最優先，`/spec-it` 產的七欄位 spec 裡就有
2. `tests/features/*.feature` 的 BDD scenario
3. 使用者口頭描述 → 進 Step 2 拆解

### Step 2：把模糊判準拆成 yes/no

三步：

```
① 拆成可觀察的條件
   「摘要要夠精簡」 → 「輸出字數 ≤ 原文 20%」

② 用 AND / OR 接成可核對的句子
   「輸出字數 ≤ 原文 20% AND 包含原文的三個主要論點」

③ 想幾個負例，確認擋得住
   負例：輸出 500 字（原文 600 字）→ 應該 fail ✓
   負例：只有 50 字但漏掉兩個論點 → 應該 fail ✓
```

**每一條都要能用一句 yes/no 回答。**

| ❌ 不可核對 | ✅ 可核對 |
|---|---|
| 夠不夠專業 | 沒有出現「我覺得」「應該」等模糊詞 |
| 是否夠詳細 | 每個宣稱都有對應的 `citations` 條目 |
| 使用者體驗好 | 首次可互動時間 ≤ 2 秒 |
| 摘要品質高 | 字數 ≤ 原文 20% 且涵蓋原文三個 H2 標題 |

### Step 3：決定每一題誰來判

**能用程式判就別請 LLM。**

| 判準性質 | 裁判 | 寫成什麼 |
|---|---|---|
| 有標準答案 | **程式 assertion** ★ | `pytest` / `vitest` 的一個測試 |
| 有結構要求 | **schema 驗證** | Pydantic model / JSON Schema |
| 有參考資料 | **比對來源** | 檢查每個宣稱都指得出出處 |
| 主觀但有規則 | LLM-as-judge（**後備**） | 一個只回 `{pass, reason}` 的 prompt |

### Step 4：至少 10 筆測資

**少於 10 筆的通過率沒有意義**（一筆就佔 10%，雜訊太大）。

每筆包含：
```
| # | 輸入 | 預期 | 這筆在測什麼 |
|---|---|---|---|
| 1 | 500 字英文新聞 | pass | 主流程 |
| 2 | 空字串 | fail 且回友善錯誤 | 邊界 |
| 3 | 10 萬字超長文 | pass 或明確拒絕 | 邊界 |
| … |
```

**至少要有 3 筆邊界 case**（空值 / 超長 / 格式錯誤）。只測主流程的考卷會給你虛假的安全感。

### Step 5：產出兩個檔案

**① `evals/eval-set.md`** —— 人看的
```markdown
# 驗收考卷：<對象>

## 判準（全部二元）
| # | 判準 | 裁判 | 對應 |
|---|---|---|---|
| C1 | 輸出是合法 JSON 且含 summary / citations 兩欄 | schema | AC-1 |
| C2 | 字數 ≤ 原文 20% | 程式 | AC-2 |
| C3 | 空輸入時回傳友善錯誤而非 exception | 程式 | AC-3 |

## 測資（≥ 10 筆）
| # | 輸入 | 預期 | 測什麼 |
|---|---|---|---|

## 基線
日期：____　通過率：__ / __　備註：____
```

**② `evals/run_eval.<ext>`** —— 機器跑的
一個可以直接執行、印出 `通過 N/M` 的腳本。

### Step 6：立刻跑一次，記錄基線

```
基線通過率：6/10

失敗的是：#2（空輸入）、#5（超長文）、#7（非英文）、#9（含表格）
失敗模式聚類：邊界處理缺失（3 筆）、格式解析（1 筆）
```

**沒有基線，之後所有「改好了」都無法證明。**

---

## 硬規則

- ❌ **不准用 1–10 分** —— 不可重現。今天 7 分明天 5 分
- ❌ **不准少於 10 筆測資**
- ❌ **不准全部都是主流程** —— 至少 3 筆邊界
- ❌ **不准寫出無法核對的判準** —— 寫不出 yes/no 就回 Step 2 重拆
- ❌ **不准跳過基線** —— 建完考卷立刻跑一次並記下來
- ✅ 能用程式判的**一定**用程式，LLM-as-judge 是最後手段

---

## 改進優先序（跑完考卷之後）

發現通過率不夠時，**先便宜後昂貴**，每動一步就回來跑同一份考卷：

| 順序 | 做法 | 成本 |
|---|---|---|
| ① | 改 system prompt / 指令措辭 | 最低 |
| ② | 加 few-shot 範例 | 低 |
| ③ | 改結構（schema / 檢索方式） | 中 |
| ④ | 換模型 / 微調 | 最高 |

**先做失敗模式聚類，再改。** 消滅一整類，不要一筆一筆救火。

---

## 心法

> **沒有拿同一份 dataset 比較，就不准說「改好了」。**
> **好的考卷不只驗收，還是自動優化的燃料 —— `/loop` 的第③拍直接用它。**
