# /decide — 開發決策協議

> **核心**：不要把判斷丟回給使用者。先告訴他你建議選什麼、依據是什麼。

## 🚨 自動觸發訊號

### 強訊號
- 「該選哪個」「A 還是 B」「用 ___ 還是 ___」「幫我決定」
- 「為什麼會壞」「這是什麼問題」
- 「這個能不能交給 AI 自動做」
- **你自己正準備列出 3 個以上選項讓使用者挑** ← 這是最重要的自我觸發訊號

### 反訊號
- 只有一個合理選項（那不是決策，是條件）
- 使用者已經決定了，只是要你動手
- 決策等級到 ADR（影響全專案 + 2 個以上選項 + 之後換會痛）→ 改跑 `/adr`

---

## 三種模式

### 模式 A：選型 / 架構 / 比較

```
建議：<選哪一個>

理由：
- <只寫會改變決策的差異，最多三點>

例外：
<什麼情況這個建議會翻盤 —— 只寫一個>

下一步：<一個動作>
```

**鐵則**：被問「該選哪個」時，**不准用一個動作開頭**。

```
❌ 「先打開你的設定檔看看目前用哪個。」   ← 有動作，沒決策
✅ 「建議用 SQLite。只有在需要多寫入者並行時才換 Postgres。」
```

**只寫會改變決策的差異。** 兩邊都有的功能不要列——那不影響選擇。

### 模式 B：Debug / 故障

```
問題：<實際壞在哪，不是症狀>

最可能根因：<只列一個>

證據：
- 已確認：<檔案:行號 或 log 片段>

修正：<可直接執行的指令或 diff>

驗證：<一個方法>
```

**第一個修正失敗前，不要列理論上的其他可能。**
失敗後才說「第二順位是 ___」。

### 模式 C：任務分流（該不該交給 AI）

先問一句：**這件事寫得出 `check()` 嗎？**

| 能用程式驗證？ | 做錯的代價 | 結論 |
|---|---|---|
| 可以 ✓ | 低 | **直接交給 AI 全自動**，事後看 log |
| 可以 ✓ | 高 | **AI 做，人核准**——動作可逆才自動 |
| 部分可以 | 任意 | **人機協作**：AI 產候選，人挑 |
| 不行 ✗ | 任意 | **人類把關**——先想辦法讓它變成可驗證的 |

輸出：
```
分流結論：<四格之一>

理由：
- 可驗證性：<寫得出 check() 嗎？怎麼寫>
- 可逆性：<做錯了能不能還原>
- 代價：<做錯的實際損失>

建議的授權方式：<自動 / 人核准 / 人做>
下一步：<一個動作>
```

## 證據分級（三種模式都強制）

| 標記 | 硬性要求 |
|---|---|
| **已確認** | 附 `檔案:行號` 或連結 |
| **推測** | 寫出依據什麼推的 |
| **未知** | 寫出查證方式，**只列一個**——那個查了就能收斂的 |

完整規則見 `rules/09-evidence-labels.md`。

**短而武斷，比長而誠實危險得多。**

---

## 時間估計

只對「使用者要自己做的事」估，一律給區間 + 前提：

```
✅ 5–15 分鐘（前提：現有測試會過）
✅ 未知 —— 要先看到失敗的 log
❌ 15 分鐘
```

---

## 硬規則

- ❌ **不准用「看情況」「都可以」「各有優缺點」結尾** —— 那是把判斷丟回去
- ❌ **不准列超過 3 個選項** —— 超過表示你還沒收斂
- ❌ **不准為了簡潔把推測寫成已確認**
- ❌ **不准給沒有前提的時間估計**
- ✅ 使用者明確問「有哪些選項」→ 可以給 2–4 個**排序過**的，但仍要標出建議哪一個

## 範例

**問**：「這個爬蟲每天跑一次，要不要讓 AI 自動修 selector？」

```
分流結論：AI 做，人核准。

理由：
- 可驗證性：寫得出 check() —— 抓下來的欄位不為空 + 型別對 + 筆數在合理區間
- 可逆性：可逆，selector 改壞了改回來就好（有版控）
- 代價：中等。抓錯資料會污染下游 DB，但不是不可逆

建議的授權方式：
AI 偵測到 selector 失效時自動產生修正候選並跑 check()，
通過後開 PR，人 merge。不要讓它直接 push。

未知：下游有沒有其他系統直接讀這張表。
查證方式：grep 一下 repo 裡有誰 SELECT 這張 table。
若有其他消費者，代價會升到「高」，就要改成人工核准每一次修改。

下一步：先跑 `/eval-set` 把那三條 check() 寫成可執行的驗證。
```
