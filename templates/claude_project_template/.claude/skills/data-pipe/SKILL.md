# /data-pipe — 資料層契約

> **核心**：資料的問題永遠比程式的問題貴。
> 程式錯了改一行；資料錯了，錯的資料已經流到下游了。

## 🚨 自動觸發訊號

### 強訊號
- 「要存到資料庫」「設計 schema」「加一張表」
- 「定期抓 ___」「同步 ___」「匯入 / 匯出」
- 「資料從哪來」「怎麼更新」
- 專案出現**第二個地方在讀同一份資料** ← 這時就需要契約了

### 反訊號
- 純前端狀態（用 localStorage 就夠）
- 一次性的資料清理 script

## 兩種模式

### 模式 A：Schema 設計（存資料）

產出 `docs/db-schema.md`。**每張表都要回答這五題**：

```markdown
## 表：<name>

**這張表回答什麼問題**：<一句話。答不出來就不該有這張表>

| 欄位 | 型別 | 可空 | 預設 | 為什麼要這欄 |
|---|---|---|---|---|

**主鍵**：<欄位> —— 為什麼選它
**索引**：<欄位> —— 對應哪個查詢
**外鍵**：<關聯> —— 刪除時怎麼處理（CASCADE / RESTRICT / SET NULL）

**生命週期**：資料什麼時候進來、什麼時候該刪掉
**成長預估**：一年後大概幾筆
```

**五個常見錯誤，逐一檢查**：

| 錯誤 | 為什麼糟 | 正確做法 |
|---|---|---|
| 什麼都 nullable | 之後每個查詢都要防空 | 想清楚哪些真的可空 |
| 沒有 `created_at` | 出事時無法回溯 | 一律加，用 UTC |
| 用浮點數存錢 | `0.1 + 0.2 != 0.3` | 用整數存最小單位（分）或 `DECIMAL` |
| 硬刪除 | 誤刪不可逆 | 重要資料用 `deleted_at` 軟刪除 |
| 沒有唯一約束 | 重複資料靠應用層防，遲早破 | DB 層加 `UNIQUE` |

### 模式 B：ETL 管線（搬資料）

產出 `docs/pipelines/<name>.md` + 可執行的檢查。

**四段結構，每段都要有失敗處理**：

```
Extract 抽取  →  Transform 轉換  →  Validate 驗證  →  Load 載入
     ↓                ↓                  ↓              ↓
  來源掛了？        格式變了？         資料不對？      寫一半掛了？
```

| 段 | 必答的問題 | 失敗時的預設行為 |
|---|---|---|
| **Extract** | 來源是什麼？多久抓一次？有沒有限流？ | 重試 N 次後**停止並告警**，不要靜默跳過 |
| **Transform** | 哪些欄位要改？時區怎麼處理？ | 轉不動的**單筆隔離**，不要整批失敗 |
| **Validate** ★ | **怎麼判斷這批資料是好的** | 不通過就**不載入**，保留上一版 |
| **Load** | 覆蓋還是追加？重跑會不會重複？ | 要能**冪等**——同一批跑兩次結果一樣 |

**Validate 那格是最重要也最常被省略的。** 至少要有這四類檢查：

```
① 筆數：這批 <N> 筆，跟上批比變動 <X>% —— 超過 50% 就要人確認
② 非空：關鍵欄位不可為空（列出是哪幾欄）
③ 型別 / 範圍：日期在合理區間、金額不為負、列舉值在允許集合內
④ 唯一性：主鍵沒有重複
```

**每一條都要能用程式跑，回傳 pass / fail。** 寫不出來就回 `/eval-set` 拆解。

## 執行步驟

### Step 1：先問資料的三個來源問題

1. **誰是真相源？** 同一份資料如果兩個地方都能改，遲早會不一致
2. **可以重跑嗎？** 重跑會不會產生重複資料？（冪等性）
3. **壞掉會怎樣？** 下游有誰在讀？他們會發現嗎？

### Step 2：寫契約（模式 A 或 B）

### Step 3：把 Validate 寫成可執行的檢查

放在 `evals/` 或 `tests/data/`，跟 `/eval-set` 的考卷同一個地方。

### Step 4：回答「壞了怎麼發現」

```
❌ 「有問題我會看 log」        ← 不會有人主動看 log
✅ 「Validate 失敗時：
     ① 不載入，保留上一版
     ② 寫一筆到 alerts 表
     ③ 下次成功時自動清掉告警」
```

## 硬規則

- ❌ **不准跳過 Validate** —— 沒有驗證的管線是「自動產生髒資料機」
- ❌ **不准用浮點數存金額**
- ❌ **不准對外部來源假設格式不會變** —— 上游一定會改，只是不通知你
- ❌ **不准寫不可冪等的 Load** —— 重跑會炸的管線，你不敢重跑，出事就沒救
- ✅ **關鍵欄位一律 NOT NULL** —— 不確定就先設 NOT NULL，之後放寬比收緊容易

---

## 決策：該用哪種儲存

| 情境 | 建議 | 什麼時候升級 |
|---|---|---|
| 單機、單使用者、< 10 萬筆 | **SQLite** | 需要多寫入者並行 |
| 多使用者、需要交易一致性 | **Postgres** | — |
| 只是快取 / session | **Redis** | — |
| 檔案 / 圖片 | 物件儲存（R2 / S3），**DB 只存路徑** | — |
| 純前端暫存 | `localStorage` | 需要跨裝置同步 |

**預設選 SQLite。** 換成別的是 ADR 等級的決策 → 先跑 `/adr`。
