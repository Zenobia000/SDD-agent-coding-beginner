# /loop — 循環工程四拍

> **核心**：不要對單次輸出許願，要設計一個會收斂的流程。

## 🚨 自動觸發訊號

### 強訊號
- 「改到好」「調到能用」「優化 ___」「試試看哪種比較好」
- 同一件事已經來回修改 **2 次以上**還沒收斂
- 使用者說「感覺好像好一點了？」← 這句話本身就是缺評分函式的證據

### 反訊號（不要觸發）
- 一次就能做完的事（改 typo、加一個欄位）
- 純探索（「這個 API 長怎樣？」）
- 使用者已經知道要改什麼，只是要你動手

---

## 執行步驟

### 第 ① 拍：劃邊界（跟使用者確認，不要自己假設）

三格都要填滿。**任一格填不出來就停下來問**。

```
範圍：這一輪只准動 ___
評分：怎麼判斷這輪比上輪好 → ___
預算：最多跑 ___ 輪 / ___ 分鐘
```

**評分那格填不出來** → 先跑 `/eval-set` 建考卷，再回來。

問使用者的話術：
> 開跑前要先鎖三件事，不然會發散：
> ① 這輪只准動哪個檔案？
> ② 「變好了」怎麼判斷——有沒有一個能跑的檢查？
> ③ 跑幾輪就停？
>
> 第②項我建議 `<你的提案>`。可以嗎？

### 第 ② 拍：放它跑

- 在邊界內產出候選版本
- **中途不要停下來問使用者**——問了就不是自動迴圈，是人工改稿
- 每一輪記錄：改了什麼 + 拿幾分

### 第 ③ 拍：打分數

跑評分函式。**能用程式判就別請 LLM**。

輸出一張表，不要用散文：

| 輪次 | 改了什麼 | 分數 | 比上輪 |
|---|---|---|---|
| 0（基線） | — | 6/10 | — |
| 1 | 加了 few-shot 範例 | 7/10 | ↑1 |
| 2 | 改用 structured output | 9/10 | ↑2 |

**沒有基線就沒有比較。第 0 輪一定要先量。**

### 第 ④ 拍：收判斷

只回報三件事，然後**停下來等使用者決定**：

```
分數曲線：6 → 7 → 9（第 2 輪跳最多）
最佳版本：第 2 輪（改用 structured output）
抽查結果：<你自己看過最佳版本後的一句判斷>

建議：收工 / 再跑一輪（並說為什麼）
下一步：<一個動作>
```

**分數高不等於真的對。** 一定要自己抽查最佳版本，不要只報數字。

---

## 硬規則

- ❌ **沒有第 0 輪基線不准開跑** —— 沒有基線，「進步」是無法證明的
- ❌ **不准中途改評分標準** —— 改了就要從第 0 輪重跑，並明講
- ❌ **不准超出預算** —— 到頂就停，回報「預算用完，目前最佳是第 N 輪」
- ❌ **不准只報分數不抽查** —— 分數可能被規避（reward hacking）
- ❌ **不准說「感覺比較好」** —— 這句話在本 skill 裡是禁語

## 常見情境對照

| 你要做的 | 範圍 | 評分 | 預算 |
|---|---|---|---|
| 提高摘要品質 | `prompts/summarize.txt` | `/eval-set` 的 10 題通過率 | 5 輪 |
| 修一個難搞的 bug | 出錯的那個模組 | 重現測試變綠燈 | 3 輪 |
| 加快查詢 | `db/queries.py` | 同一組查詢的 p95 延遲 | 4 輪 |
| 減少 token 花費 | system prompt | 同樣通過率下的平均 token 數 | 3 輪 |

## 卡關處理

**連續 2 輪分數沒動** → 停下來，這通常表示：
1. 評分函式抓不到你真正在意的東西 → 回去改考卷
2. 邊界劃太小，真正的問題不在這個檔案 → 重劃範圍
3. 已經到這個做法的天花板 → 換做法，不是繼續調

**分數上升但你覺得變糟** → 評分函式有漏洞。這是**好消息**——你發現了考卷的缺口，補一題進 `/eval-set`。
