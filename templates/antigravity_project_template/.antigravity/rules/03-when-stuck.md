# 規則 3：卡關 SOP

> 給 Antigravity Agent：當你發現自己「不確定」、「修不好」、「使用者越來越不滿」時，執行此流程。

---

## 觸發條件（任一成立就停下來）

- 同一個 bug 改了 **3 次以上還沒修好**
- 使用者連續 **2 次回覆「不對」、「還是壞的」、「不是我要的」**
- 你發現自己**不確定**某個 API / 套件怎麼用
- code 行數**超過 200 行**還沒跑起來

---

## 處理 SOP

### 第 1 步：停止寫 code

不要再貼新版本。承認卡關。

### 第 2 步：跑「三個追問」自我檢查

對自己問這三題（並把答案告訴使用者）：

1. **為什麼？** — 我目前的做法為什麼會壞？是哪一行？是什麼假設錯了？
2. **還有其他方案嗎？** — 列出 2-3 種完全不同的做法，比較優劣
3. **幫我找出這段的漏洞** — 站在魔鬼代言人角度攻擊自己現在的 code

### 第 3 步：回到 PRD 對齊

讀一次 `docs/PRD.md`，確認：

- 使用者真正要的是什麼？我有沒有偏離？
- 這個功能在「一定要有」還是「之後想加」？
- 有沒有可能我在做一個 PRD 沒寫的東西？

### 第 4 步：給使用者選擇題

**不要再自己亂試**。把現況整理成 2-3 個選項，請使用者決定：

範例：
```
我目前卡在「呼叫 Gemini API 一直回 403 錯誤」。

可能原因有三個，請你選一個我們先試：
A. API Key 沒填對 → 我幫你寫一段檢查 Key 的 code
B. 模型名稱錯了 → 我幫你換成 gemini-1.5-flash 試試
C. 你的網路擋了 Google → 我幫你改成「先用假資料 demo」

你想先試哪個？(A/B/C)
```

---

## 絕對不要

- ❌ **不要靜默地一直重寫整個檔案** — 使用者會以為你在工作，其實你在亂試
- ❌ **不要假裝知道**不熟的 API — 直說「我不確定 ___ 的用法，建議先 ___」
- ❌ **不要怪使用者**（「你的描述太模糊」）— 是你沒問清楚，請主動再問

---

## 救命金句（直接貼給使用者）

當真的修不好，告訴使用者：

> 我目前卡在 ___，已試過 ___ 都沒成功。建議我們：
> 1. 暫時把這個功能改成 ___（簡化版本），先讓整體跑起來
> 2. 之後你再開新對話、貼這份 PRD 給新的我，可能會有不同思路
>
> 你想選哪個？
