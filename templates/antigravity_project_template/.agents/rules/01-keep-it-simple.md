# 規則 1：簡單第一原則（KISS / YAGNI）

> 對 Antigravity Agent：違反此規則 = 任務失敗。

---

## 核心信念

**簡單是為了「可維護」，不是為了偷懶。** KISS 約束的是**實作的複雜度**，不是**工程紀律**——測試、spec、文件不是複雜度，是讓你能放心保持簡單的安全網。

---

## 強制規則

### ✅ 一定要做

- **最小可行實作**：寫剛好讓測試通過的 code（這正是 `/tdd-cycle` 的 GREEN 步驟）
- **YAGNI**：不為假想的未來需求加抽象 / 設定 / 擴充點
- **單一職責**：一個 function 做一件事
- **清楚命名 > 聰明寫法**
- 能用標準庫 / 既有依賴解決，就不要引入新套件

### ❌ 絕對不要

- 不要過度設計：「萬一未來要 ___」的彈性，等真的要時再加
- 不要 premature optimization：先正確、被測試覆蓋，再談效能
- 不要為了「正規」而拆過多檔案 / 加過多層抽象
- 不要引入沒有 ADR 支持的重型框架 / 工具
- 不要重構與當前 task 無關的 code（除非 `/verify` 標出問題）

---

## KISS 與 Vibe Engineering 不衝突（關鍵）

很多人誤以為「簡單」跟「先寫 spec、先寫測試」對立。實際相反：

| 你以為的衝突 | 實際關係 |
|---|---|
| 「寫測試很麻煩，不 KISS」 | 測試讓你敢刪 code、敢重構 → 是維持簡單的**前提** |
| 「先寫 spec 很重」 | spec 防止你寫一堆「以為要、其實不要」的 code → 是最大的 **YAGNI** |
| 「TDD 三步驟很繁瑣」 | GREEN 步驟「寫最少 code 讓測試過」**就是 KISS 本身** |

**簡單的是 code 的實作，不是省略紀律。**

---

## 取捨判斷

| 兩種寫法 | 選哪個 |
|---|---|
| A 寫起來 5 行；B 寫起來 50 行更「正規」 | 選 A（但兩者都要有測試）|
| A 直接實作；B 先加一層介面「以後好擴充」 | 選 A（YAGNI，要擴充時再抽介面）|
| A 用標準庫；B 裝一個新套件省 3 行 | 選 A |
| A 變數叫 `news`；B 用泛型 `T extends Content` | 選 A |

**口訣**：簡單的是 code，不是紀律。讓 spec、測試、文件保護你的簡單。
