## 圖 1：系統組成

```text
[使用者瀏覽器]
      │
      ├─ 畫面層：清單頁 / 新增表單 / 設定（匯率）
      │
      ├─ 計算層：月支出換算
      │            ├─ 年繳 → 只計扣款當月，另算平均月成本   （FR-02）
      │            ├─ 外幣 → 乘以使用者自設固定匯率          （FR-05）
      │            └─ 試用中 → 以未來月費計入                （FR-06）
      │
      └─ 儲存層：localStorage（只在這台裝置，不上傳）        （NFR-03）
                    │
                    └─ 匯出：JSON 檔下載                     （FR-08）
                              ↑
                        使用者自己保管的唯一備份
```

**只有三層，沒有後端。** 這是刻意的 —— 見下方架構選擇。

## 圖 2：資料模型　**最重要的一張**

```text
Subscription（一筆訂閱）
├─ id            系統給的唯一編號
├─ name          服務名稱             例：Netflix
├─ amount        金額（正整數）        例：390
├─ currency      幣別                 TWD / USD
├─ cycle         扣款週期             monthly / yearly
├─ nextChargeAt  下次扣款日           例：2026-09-15
├─ status        狀態                 active / trial / cancelled
└─ note          備註（自由填）        例：與室友合分，我實付 1/3

Settings（全域設定，只有一份）
└─ fxRate        使用者自設的 USD→TWD 匯率    例：31.5
```

### 每個欄位「少了它會怎樣」

| 欄位 | 少了它會怎樣 |
|---|---|
| `name` | 清單上全是數字，使用者認不出是哪個服務 |
| `amount` + `currency` | 算不出總額。**`currency` 少了，美金訂閱會被當台幣加進去，總額直接錯掉** |
| `cycle` | 分不出年繳月繳，FR-02 整條做不了 |
| `nextChargeAt` | 不知道年繳那筆該算在哪個月，FR-02 做不了 |
| `status` | 分不出試用中，FR-06 做不了；也無法保留已取消的紀錄做前後對比 |
| `note` | **少了它不會壞，但它是唯一的緩衝** —— 見下方不可逆決定 |

### 刻意保留的緩衝：`note`

`note` 是唯一一個「沒有需求指定要它」的欄位。留著它是因為 PRD 有兩個開放問題（Q1 使用狀態、Q3 家庭方案分攤）還沒答案。

在答案出現之前，那些資訊全部塞進 `note`。等哪一天真的要做成正式欄位，資料至少沒有遺失 —— 使用者已經自己記在備註裡了。

**一個自由文字欄位，換掉一次資料遷移。POC 階段這筆交易划算。**

## 圖 3：畫面與流程

```text
   ┌─────────────────────────────────────────────┐
   │  清單頁                                      │
   │  ┌───────────────────────────┐              │
   │  │  本月總支出  NT$ 1,847     │  ← 最大字級  │
   │  └───────────────────────────┘              │
   │  Netflix    NT$390/月         active         │
   │  ChatGPT    USD20/月 (NT$630) active         │
   │  Bearly     NT$390/月         trial ← 顏色不同│
   │  Notion     USD96/年          11 月扣款       │
   │             平均月成本 NT$252                 │
   └─────────────────────────────────────────────┘
        │                    │              │
   [點新增]             [點某一筆]      [點匯出]
        ▼                    ▼              ▼
   新增表單            編輯 / 刪除     下載 JSON 檔
   （3 個必填）              │
        │                    │
        └────[儲存]──────────┘
                  ▼
            回清單（總額更新）
```

**沒有換頁。** 新增與編輯都用同一頁上的面板 —— 這是 NFR-02（不需要換頁）直接推出來的設計。

## 圖 4：外部依賴

```text
外部依賴：無。

- 匯率不即時抓 —— 使用者在設定裡自己填一個固定值（PRD 決策 D3）
- 沒有登入、沒有第三方帳號
- 沒有後端伺服器
- 沒有分析、沒有追蹤
```

**「無」是這一格最好的答案。** POC 每多一個外部依賴，就多一個會在 demo 當天壞掉的東西 —— 而且每一個都會讓 NFR-03（資料不外傳）變得難以驗證。

## 架構選擇

第 6 站要了 3 個方案，選 A：

| 方案 | 資料存哪裡 | 評估 |
|---|---|---|
| **A（選這個）** | 瀏覽器 localStorage | ✔ 零依賴、零設定、五分鐘能跑起來。NFR-03「不外傳」用「根本沒有後端」來滿足 —— **最好的實作是不實作** |
| B | 平台內建的雲端資料庫 | 換裝置能用，但資料交給第三方（違反 NFR-03 的精神），而且被鎖在該平台 |
| C | 使用者自己的 Google Sheet | 資料歸使用者，但要 OAuth 授權。**光是授權流程就會讓 NFR-01（5 分鐘填完）破功** |

**選 A 的代價寫在下面的風險表第一條。作者知道自己在接受什麼。**

---

## 不可逆的決定

| 決定 | 為什麼難改 | 將來要改的成本 |
|---|---|---|
| **資料模型的欄位** | 存了幾十筆之後才加欄位，舊資料全部是空的 | 要寫一次性遷移，或叫使用者重填。`note` 欄位就是為了拖延這一天 |
| **`status` 只有三種值** | 之後想加「已暫停」「共用中」，舊資料要重新分類 | 中等。三種值改五種，舊的 active 不用動，但畫面邏輯要全面檢查 |
| 存在 localStorage | 換成雲端要重寫儲存層，且要處理「本機已有資料」的合併 | 高，但 POC 階段本來就不打算做 |

**第一條是這份文件唯一真正的價值。** 其他的都能重生成，這條不能。

## 風險表

| 風險 | 什麼時候會炸 | 我打算怎麼辦 |
|---|---|---|
| 資料只存瀏覽器，清快取就沒了 | 使用者換裝置、清瀏覽資料、用無痕視窗 | 做 FR-08 匯出 JSON。**POC 階段接受這個風險**，並在畫面上明講「資料只存在這台裝置」 |
| 資料模型漏欄位，之後要遷移 | 存了幾十筆之後才想加欄位 | 保留 `note` 自由欄位當緩衝，先撐過 POC |
| no-code 平台改版或免費額度用完 | 隨時 | 匯出 JSON 就是逃生門。**不把資料鎖在單一平台**，這是選方案 A 的另一個理由 |
| 使用者自設匯率長期沒更新，總額慢慢失真 | 匯率變動超過 5% 而使用者沒察覺 | POC 階段接受。已記在 PRD 開放問題 Q4 |
