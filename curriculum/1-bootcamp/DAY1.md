## 單元 1｜Harness 解剖與典範轉移

**為什麼**：多數人第一次用 AI 寫程式的經驗是「三十秒做出畫面，然後改了兩小時越改越歪」。問題不在工具，在流程。
而流程要靠檔案撐住：agent 每次啟動都會讀一組檔案，決定它要守什麼規則、會什麼技能、哪些事做不到。

### 重點：從敏捷到 SDD agentic coding

| | 傳統開發 | 敏捷 | Vibe Coding（沒有紀律） | SDD agentic coding（這門課） |
|---|---|---|---|---|
| 誰寫程式 | 人 | 人 | AI | AI |
| 規格 | 厚重 Word | 用故事卡取代 | 沒有，靠對話 | 六份輕量 Markdown，是唯一事實來源 |
| 怎麼知道做完 | 驗收測試 | Sprint review | 「看起來可以」 | 每條需求都對到一個會失敗、再變綠的測試 |
| 最貴的東西 | 寫程式 | 溝通 | 改來改去 | **想清楚** |

**AI 開發的核心限制**：它會替你做決定而且不告訴你；它記不住；它答錯和答對一樣有自信；它說「完成了」不代表完成。
**一句話**：人負責收斂與決策，AI 負責發散與生成。

### 重點：harness 解剖

用上課 repo 本身當標本，讀 [`HARNESS.md`](https://github.com/Zenobia000/leavebot-bootcamp/blob/main/HARNESS.md)。只要記住一張表：

| | 是什麼 | 強度 |
|---|---|---|
| **規則**（`AGENTS.md`） | 每次對話都帶著的文字 | agent 大部分時候會遵守，不是每一次 |
| **技能**（`.claude/skills/`） | 叫了才載入的流程 | 叫了就照流程走 |
| **hook**（`.claude/hooks/`） | 動作前自動跑的腳本 | **做不到**，agent 繞不過去 |

### 實作

| 軌 | 做什麼 |
|---|---|
| 全組 | 在 repo **根目錄**打開 Claude Code 或 Codex，打 `/compass`（Codex：`$compass`） |
| 全組 | 請 agent 跑 `git add -A`，看它被擋下。找出是哪個檔案擋的、在哪裡登記的 |

### 通過訊號

- [ ] 說得出「`git add -A` 被擋」是 `.claude/hooks/guard-git.sh` 做的，登記在 `.claude/settings.json`
- [ ] 說得出 `AGENTS.md` 和 hook 的差別：哪一個 agent 可以違反、哪一個不行

## 單元 2｜Project Brief

**為什麼**：沒寫「為什麼做」，後面每一份文件都會長出多餘的東西。沒寫「不做什麼」，AI 會很熱心地幫你做。

### 重點

- **Goal 要能被推翻**：寫得出怎麼量、目標值多少。PRD 的每個 epic 都要追得回某一條 G。
- **Non-goal 要有理由**：沒理由的非目標，三天後就會反悔。`LEAVEBOT.md` 的 MVP 範圍直接寫進來。
- 這份**不寫功能、不寫技術**。

### 實作

| 軌 | 做什麼 |
|---|---|
| 📋 規格軌（主導） | 用 `/grilling` 讓 AI 拷問你這個題目，照 `templates/01-brief.md` 產出 `docs/01-brief.md` |
| 🛠️ 工程軌 | 每條 goal 問一次：「這個數字誰來算、怎麼算？」算不出來的劃掉 |

### 可以這樣問 AI

```text
/grilling

我要做一個「一句話請假」系統。題目、公司規章與 MVP 範圍在 @LEAVEBOT.md。
先拷問我「為什麼要做、做到什麼程度算成功、明確不做什麼」，一次一輪。
問完後照 @templates/01-brief.md 的格式產出 docs/01-brief.md。
＜換成你們自己最在意的痛點，例如：主管每週花太多時間審假＞
沒問到、我沒回答的，不要替我填。
```

### 通過訊號

- [ ] `docs/01-brief.md` 存在，goal 與 non-goal 各至少 3 條，都有編號
- [ ] 每條 goal 說得出怎麼量

## 單元 3｜PRD

**為什麼**：PRD 是規格軌和 AI 之間的合約。驗收條件寫得出 Given / When / Then，明天的測試就有東西可以對。

### 重點

| 段落 | 要點 |
|---|---|
| **Persona** | 2–3 個，寫行為與處境，不寫年齡星座 |
| **User flow** | Mermaid 流程圖，從打開到達成目的，分支只畫會改變結果的 |
| **Epic → Story** | Epic 對到 goal；story 寫「身為／我想要／以便」 |
| **BDD 驗收條件** | 每個 story 至少 2 條，**至少一條是失敗路徑**；日期、數字、訊息文字寫具體 |

**讓 AI 問你，而不是讓 AI 答你。** `LEAVEBOT.md` 的規章故意不完整：「跨年度的特休怎麼算？」「半天病假剛好遇到午休？」這些洞要被問出來，寫進「待決事項」。

### 實作

| 軌 | 做什麼 |
|---|---|
| 📋 規格軌（主導） | 同一個 session 接著 `/grilling`，照 `templates/02-prd.md` 產出 `docs/02-prd.md` |
| 🛠️ 工程軌 | 每當答案會影響資料怎麼存，就喊停記下來 —— 那是單元 6 ER 圖的素材 |
| 全組（最後 15 分鐘） | 和隔壁組交換 PRD，各圈出 3 句「我判斷不了過了沒」的驗收條件 |

### 可以這樣問 AI

```text
接著拷問我這個系統的使用者與流程：誰會用、從打開到請完假的每一步、哪裡會出錯。
扮演一個挑剔的人資主管，專挑規章裡沒寫清楚、但上線後一定會遇到的情況。
問完後照 @templates/02-prd.md 產出 docs/02-prd.md，
＜例：先只寫員工請假與主管核准兩個 epic＞。
驗收條件裡不准出現「正確」「合理」「適當」；寫不出具體數字的，放進待決事項。
```

### 通過訊號

- [ ] User flow 在 Mermaid 預覽裡畫得出來
- [ ] 每個 story 至少 2 條 AC，至少一條是失敗路徑
- [ ] 隔壁組圈出來的句子，你們已經改掉

## 單元 4｜SRS

**為什麼**：PRD 寫的是使用者看得到的結果；SRS 把它拆成系統**必須做到**的行為，一條一條可以驗。明天每個測試都會指回這裡的編號。

### 重點

- **一條只講一件事**。出現「並且」「同時」「以及」就拆成兩條。
- **每條都標來源**，追得回 PRD 的 US 或 AC。追不回去的，就是有人在中間偷偷加了東西。
- **NFR 至少涵蓋**：效能、安全（**包含 AI 被注入**）、失效行為（模型逾時怎麼辦）。
- 編號發出去就凍結；砍掉的留著標「已作廢」；不重用。

### 實作

| 軌 | 做什麼 |
|---|---|
| 📋 規格軌（主導） | 讓 AI 依 PRD 起草 `docs/03-srs.md`，逐條檢查來源與「一條一件事」 |
| 🛠️ 工程軌 | 審 NFR：每條都寫得出「怎麼驗」嗎？驗不了的移到「無法驗證區」 |
| 全組 | 跑 `python scripts/trace.py`，看矩陣裡是不是每條 AC 都出現了 |

### 可以這樣問 AI

```text
根據 @docs/02-prd.md，照 @templates/03-srs.md 起草 docs/03-srs.md。
每條 FR / NFR 都要標來源（US 或 AC 編號）。PRD 沒寫到的行為，不要自己加，列在最後問我。
NFR 一定要有一條是「理由欄被塞指令時，系統不能改變假單狀態」。
```

### 通過訊號

- [ ] PRD 的每條 AC，至少有一條 FR 承接
- [ ] NFR 涵蓋效能、安全、失效行為
- [ ] `trace.py` 列得出全部編號

## 單元 5｜SAD

**為什麼**：架構決定了「什麼交給 AI、什麼交給程式碼」。這張表畫錯，後面的程式就會把判斷交給模型 —— 那是整個系統最危險的地方。

### 重點

| 段落 | 要點 |
|---|---|
| **C4 L1 / L2** | 系統情境、容器。技術棧已由 `STACK.md` 固定（Next.js → FastAPI → SQLite / LLM） |
| **資訊流** | 一條主要路徑的循序圖。**一定要畫出 AI 的輸出在哪裡被驗證** |
| **誰負責什麼** | 錯了會有人受傷 → 程式碼或人；規則寫不完、錯了能補救 → AI |
| **技術選型（ADR）** | 在 STACK 邊界內做的選擇，寫選了什麼、放棄了什麼、可不可逆 |

一定會有組想把「算剩餘天數」交給 AI。問自己：**算錯一次會發生什麼？**

### 實作

| 軌 | 做什麼 |
|---|---|
| 🛠️ 工程軌（主導） | 用 `/to-architecture` 從 PRD 與 SRS 產出 `docs/04-sad.md` 與 `docs/05-sds.md` 的草稿（單元 5、6 一起跑） |
| 📋 規格軌 | 拿著 SRS 逐條找「SAD 裡哪一塊負責它」，找不到的就是架構漏了 |

### 可以這樣問 AI

```text
/to-architecture

依 @docs/02-prd.md 與 @docs/03-srs.md，照 @templates/04-sad.md 與 @templates/05-sds.md 起草兩份文件。
技術棧以 @STACK.md 為準，不准換框架或加套件；要例外先問我。
＜例：我們決定 AI 只解析、不給建議天數＞
先給我看 SAD 的「誰負責什麼」與資訊流，我確認後再寫 SDS。
```

### 通過訊號

- [ ] 三張圖（C4 L1、L2、資訊流）都在 Mermaid 預覽裡畫得出來
- [ ] 資訊流裡看得到 AI 輸出被驗證的位置
- [ ] 「誰負責什麼」裡，剩餘天數與核准不是 AI

## 單元 6｜SDS

**為什麼**：SDS 細到 agent 可以照著寫程式、你可以照著驗收。明天的 I0 骨架就是照這一份生的。

### 重點

- **ER**：只畫這一版需要的表；員工原本打的那句話要存下來，AI 出錯時才查得到。
- **API**：每支都寫錯誤情況，只寫成功路徑的話，AI 會自己發明錯誤處理。`API-01` 是 `STACK.md` 固定的 `POST /api/parse`，照抄。
- **畫面**：每個畫面對到 PRD user flow 的某一步、呼叫哪支 API。
- **模組**：AI 的部分與規則的部分**分成不同模組**，規則才測得了。

### 實作

| 軌 | 做什麼 |
|---|---|
| 🛠️ 工程軌（主導） | 審 `/to-architecture` 產出的 SDS 草稿，補錯誤情況與模組簽名 |
| 📋 規格軌 | 對照 PRD user flow，每一步都找得到畫面與 API |

### 通過訊號

- [ ] ER 圖畫得出來；`API-01` 符合 STACK 的合約；每支 API 都有對應需求
- [ ] AI 與規則在不同模組

## 單元 7｜Test Plan

**為什麼**：只有前五份的話，測試是明天寫程式時才臨時想的，V-model 只有左半邊。先寫好「每條需求怎麼驗」，明天的 `/tdd` 才有依據。

### 重點：窮舉交給 AI，判斷交給人

| | 驗收測試 | 邊界測試 |
|---|---|---|
| 來源 | PRD 的 AC | AI 窮舉 |
| 誰決定「預期結果」 | **人** | AI 提議，**人審核** |
| 失敗代表 | 沒做到需求 | 有沒想到的情況 |

**最危險的事**：讓 AI 同時決定「要測什麼」和「預期結果是什麼」，再讓它寫程式去通過。這等於讓學生自己出題、自己改考卷。

**AI 的上線門檻**：eval 準確率要多少才能上線？沒有標準答案。「準確率 85%，但所有假單都要員工確認後才送出」可能就夠了。重點是**你們做了這個決定，而且寫下來了**。

### 實作

| 軌 | 做什麼 |
|---|---|
| 📋 規格軌（主導） | 讓 AI 窮舉 50 個邊界情境，逐一標「保留／刪除／要問人資」；保留的給 TC 編號 |
| 🛠️ 工程軌 | 每個 TC 填層級（驗收 / 系統 / 整合 / 單元）；注入攻擊至少 2 個 TC |
| 全組 | 訂 eval 門檻並寫理由；跑 `python scripts/trace.py` 到沒有「沒有 TC」的缺口 |

### 可以這樣問 AI

```text
讀 @docs/02-prd.md、@docs/03-srs.md 和 @LEAVEBOT.md 的規章。
針對「員工用一句話請假」窮舉 50 個邊界情境：日期表達、跨月跨年、半天、週末、額度不足、
同組同日人數、奇怪的輸入、惡意的輸入。
用表格輸出：編號、輸入、情境、你建議的預期結果、你的信心（高/中/低）、它驗哪條 AC 或 FR。
「預期結果」只是你的建議，最後由我決定。
```

> 注意最後一句。不寫的話，它的建議會被當成正確答案直接進測試。

### 通過訊號

- [ ] 每條 AC 都有 TC，或寫進「不測什麼」並有理由
- [ ] 刪掉的情境至少 3 個，說得出為什麼
- [ ] eval 門檻有數字，也寫了為什麼
