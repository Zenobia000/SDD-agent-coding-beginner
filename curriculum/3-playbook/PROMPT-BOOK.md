# Prompt 魔法書

> 課程裡用到的提示詞，分四篇。每一段都標了 **⚙️ 要換掉的地方**和 **🔒 不要刪的那一句**。
>
> 原封不動貼上的效果通常最差。這些提示詞的價值不在字面，在它們**限制 AI 的方式**。

| 篇 | 用在 | 核心技巧 |
|---|---|---|
| [一、需求收斂篇](#一需求收斂篇) | Brief、PRD、SRS | 讓 AI 問你，不要讓 AI 答你 |
| [二、架構繪圖篇](#二架構繪圖篇) | SAD、SDS、疊代拆票 | 先劃清 AI 與程式碼的分工 |
| [三、測試窮舉篇](#三測試窮舉篇) | Test Plan、TDD、eval | 窮舉交給 AI，預期結果由人定 |
| [四、Debug 救援篇](#四debug-救援篇) | AI 卡住、改壞、繞圈 | 縮小範圍，重新給 context |

---

## 好提示詞的四個零件

| 零件 | 例子 | 沒有它會怎樣 |
|---|---|---|
| **給它看什麼** | `讀 @docs/02-prd.md` | 它會憑空想像你的需求 |
| **要它做什麼** | `照 @templates/04-sad.md 產出 docs/04-sad.md` | 它會做它覺得有用的事 |
| **不准它做什麼** | `不要替我決定`、`不准改測試` | 它會很熱心地多做 |
| **怎樣算完成** | `跑測試，把輸出貼給我` | 它會說「完成了」，但沒跑過 |

**第三個零件最常被漏掉，也最重要。**

## 一、需求收斂篇

### 1-1 讓 AI 拷問你

```text
/grilling

我要做一個 ⚙️＜一句話描述系統＞。背景資料在 ⚙️@＜檔案＞。

請扮演一個挑剔的 ⚙️＜利害關係人角色，例：人資主管＞，
專挑沒寫清楚、但上線後一定會遇到的情況。
🔒 一次只問一個問題，等我回答再問下一題。
🔒 問滿 ⚙️＜10＞ 題之前不要幫我總結。
```

### 1-2 MECE 檢查

```text
這是我列的 ⚙️＜功能 / 角色 / 情境＞ 清單：
⚙️＜貼上清單＞

用 MECE 原則檢查：
1. 哪些項目互相重疊？
2. 少了哪些類別？
3. 有沒有「其他」這種垃圾桶分類？
🔒 只指出問題，不要直接幫我重寫清單。
```

### 1-3 產出規格文件（Brief、PRD、SRS 都適用）

```text
用 @templates/⚙️＜02-prd＞.md 的格式，
根據 @docs/⚙️＜01-brief＞.md 和我們剛剛的討論，產出 docs/⚙️＜02-prd＞.md。

🔒 討論中沒有決定的事，放進「待決事項」，不要替我決定。
🔒 驗收條件裡的日期、數字、訊息文字都寫具體的。
寫完後，列出你自己覺得最模糊的 3 條驗收條件。
```

### 1-4 驗收條件健檢

```text
讀 @docs/02-prd.md 的驗收條件。
找出所有「交給一個沒參加討論的人，他判斷不了過了沒」的句子。

用表格輸出：編號、原句、為什麼判斷不了、建議改法。
🔒 不要直接修改檔案。
```

## 二、架構繪圖篇

### 2-1 劃分 AI 與程式碼的責任

```text
讀 @docs/03-srs.md。把每一條 FR 拆成具體的工作，
每一項標記：交給 LLM、寫成程式規則、或由人決定，並寫理由。

判斷原則：錯了會有人受傷 → 程式碼或人；規則寫不完而且錯了能補救 → LLM。
🔒 特別列出「交給 LLM 很誘人，但其實不該」的項目。
```

### 2-2 產出架構文件

```text
/to-architecture

依 @docs/02-prd.md 與 @docs/03-srs.md，照 @templates/04-sad.md 與 @templates/05-sds.md
產出 docs/04-sad.md 與 docs/05-sds.md。

技術棧以 @STACK.md 為準。
🔒 不要換框架、不要引入其他套件；要例外先問我。
🔒 資訊流一定要畫出 AI 的輸出在哪裡被驗證。
🔒 只設計這一版範圍內需要的表與 API。
```

### 2-3 Mermaid 圖

```text
根據 @docs/05-sds.md 的資料模型段落，畫一張 Mermaid erDiagram。
🔒 只畫文件裡有的表和欄位，不要自己加。
畫完後，列出你覺得文件裡沒寫清楚的關聯。
```

Mermaid 畫不出來時：把錯誤訊息整段貼給 AI，這種錯通常一次就修好。

### 2-4 拆票

```text
/to-tickets

依 @docs/05-sds.md 與 @docs/06-test-plan.md，切成 I0–I4 五張疊代票。
I1 必須是垂直切片：⚙️＜從哪裡開始，穿過哪些元件，到哪裡結束＞。
🔒 每個 TC 只落在一張票裡。
🔒 先給我看清單，我確認後再寫檔。

每張票寫明：要讓哪些 TC 變綠、驗收指令、被哪一張票擋住。
```

## 三、測試窮舉篇

### 3-1 窮舉邊界情境

```text
讀 @docs/02-prd.md、@docs/03-srs.md ⚙️＜和其他規則來源＞。
針對 ⚙️＜功能＞ 窮舉 ⚙️＜50＞ 個邊界情境，涵蓋：
⚙️＜日期表達、跨月跨年、額度不足、重複送出、奇怪的輸入、惡意的輸入…＞

用表格輸出：編號、輸入、情境說明、你建議的預期結果、你的信心（高／中／低）、它驗哪條 AC 或 FR。
🔒 「預期結果」只是你的建議，最後由我決定。
```

### 3-2 從驗收條件產生測試

```text
/tdd

為 ⚙️＜TC 編號＞ 寫測試（見 @docs/06-test-plan.md），放進它指定的層級，
標上 @pytest.mark.req("⚙️＜TC-xx＞", "⚙️＜AC-xx.x＞")。

🔒 先只寫測試，跑給我看它失敗。我確認之後你才能寫實作。
🔒 單元測試不准呼叫真的 LLM，用假物件。
```

### 3-3 找測試的洞

```text
讀 ⚙️@＜測試檔＞ 和 ⚙️@＜被測的程式碼＞。
如果要你故意改壞程式碼、但不讓任何測試失敗，你會改哪裡？
列出 5 個這樣的位置。
🔒 不要真的改，只列出來。
```

> 這是「破壞測試法」的反向版本：讓 AI 幫你找測試沒蓋到的地方。

### 3-4 AI 功能的 eval

上課 repo 已附 `scripts/run_eval.py`，直接跑：`.venv/bin/python scripts/run_eval.py --min ⚙️＜門檻＞`。答錯之後：

```text
這是 eval 答錯的清單：
⚙️＜貼上 run_eval.py 的 ✗ 那幾行＞

把答錯的句子分類，找出共同原因。只建議怎麼改 prompt，不要改任何測試或 fixtures。
🔒 改完我會自己重跑 eval，不要說「應該會更好」。
```

自己的專案沒有現成腳本時，照這個合約寫一支：讀 fixtures、逐筆打 API、逐欄比對、印準確率與答錯清單，不放進 pytest。

## 四、Debug 救援篇

### 4-1 測試失敗，讓 AI 自己修

```text
⚙️＜測試指令＞ 失敗了，輸出如下：
⚙️＜貼上完整錯誤訊息，不要只貼最後一行＞

找出原因並修好。修完跑完整測試，把結果貼給我。
🔒 不准修改任何測試檔。
```

### 4-2 AI 繞圈，越改越糟

先 `/clear` 開新對話，再貼：

```text
我在做 ⚙️@＜票＞。規格在 ⚙️@＜規格檔＞。
之前的嘗試失敗了，症狀是：⚙️＜一句話描述＞。

🔒 先不要寫程式。
1. 用你自己的話說明這張票要做什麼
2. 列出你打算的步驟
3. 列出你不確定的地方
我確認後你再動手。
```

### 4-3 不確定 AI 改了什麼

```text
用白話列出你這次改了哪些檔案、每個檔案改了什麼、為什麼。
然後跑 git diff --stat，確認你的描述和實際改動一致。
```

### 4-4 規格與程式碼對不上

```text
比對 @docs/03-srs.md 的需求與 ⚙️@＜程式碼目錄＞ 的實作，並參考 `.venv/bin/python scripts/trace.py` 的缺口。
列出：
1. 規格有寫、程式碼沒做的
2. 程式碼有做、規格沒寫的
3. 兩邊都有、但行為不一致的
🔒 不要修改任何檔案。哪一邊是對的，由我決定。
```

## 最常被刪掉、但最不該刪的五句話

| 這一句 | 擋住的問題 |
|---|---|
| 不要替我決定 | AI 默默做了你沒授權的產品決策 |
| 一次只問一題 | AI 自問自答，你只是在旁邊看 |
| 先不要寫程式 | AI 還沒搞懂就動手，改了一大堆 |
| 不准修改測試 | AI 改測試讓它通過，紅線形同虛設 |
| 把輸出貼給我 | AI 說「完成了」，但根本沒跑過 |
