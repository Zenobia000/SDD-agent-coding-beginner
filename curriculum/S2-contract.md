# S2 定契約

## 結論卡

| | |
|---|---|
| **做什麼** | 把決策卡變成七欄位 spec，**並把驗收條件寫成可執行的考卷** |
| **為什麼** | 考卷是四拍第③拍的裁判。沒有它，後面所有「改好了」都無法證明 |
| **產出** | `docs/PRD.md` + `evals/evals.md` + 基線通過率 |
| **下一步** | 跑 `/gate` 確認 S2 過關 |

**這一站對「規格」跑一輪四拍。**

## 課堂 15 分鐘版

**老師講**（5 分）：

1. **廢話是模型必須服從的雜訊**——你多寫一句沒用的叮嚀，它就多一個要顧的東西
2. 只留 **Business Rule**（業務真的要求的），刪掉 **Model Rule**（「請再仔細檢查一次」這種）
3. 七欄位裡的 **Success criteria 直接拿來當考卷**——這是 S2 接 S4 的接點

**學生做**（10 分）：

```
> /spec
> 依 decision-card.md 產生 PRD

> /evals
> 依 PRD 的 Success criteria 建考卷，至少 10 筆
```

老師巡場只盯一件事：**考卷有沒有邊界 case。** 只測主流程的考卷會給人虛假的安全感。

## 動手

1. 產生七欄位 spec
   ```
   > /spec
   ```

2. 檢查 spec 裡**有沒有 Model Rule**，有就刪掉
   ```
   ❌ 刪：「請確保答案正確無誤」「請一步一步思考」「請不要遺漏細節」
   ✅ 留：「金額一律無條件捨去到小數第 2 位」「來源必須是這三個網域之一」
   ```

3. 建考卷
   ```
   > /evals
   ```

4. 確認考卷有**至少 3 筆邊界 case**（空值 / 超長 / 格式錯誤）

5. **跑一次考卷，記下基線**
   ```
   基線通過率：___ / ___
   ```
   還沒實作所以會很低，這正常。**重點是有個起點可以比。**

## 我做對了嗎

對照 [`../labs/reference-project/S2/expected/`](../labs/reference-project/S2/expected/)：

- `PRD.md` —— 比對**欄位結構**，不是內容

自我檢查最快的方法：把你的判準逐條唸出來，問「這句能用 yes 或 no 回答嗎？」

| 你的判準 | 判斷 |
|---|---|
| 「摘要品質要好」 | ❌ 回動手第 3 步重拆 |
| 「輸出字數 ≤ 原文 20%」 | ✅ |
| 「錯誤處理要完善」 | ❌ |
| 「輸入為空時回傳 `{ok:false}` 且 error 非空」 | ✅ |

## 回家展開版

### 七欄位 spec：你跟模型的契約

| # | 欄位 | 白話 |
|---|---|---|
| 1 | Role | 它扮演什麼角色 |
| 2 | Goal | 目標 |
| 3 | Inputs | 它會拿到什麼資料 |
| 4 | Constraints | 硬規則（= Business Rule） |
| 5 | Output format | 輸出格式 |
| 6 | **Success criteria** ★ | **怎樣算成功** → 直接當考卷 |
| 7 | Examples | 範例（**只是對格式，不是教推理**） |

**檢驗方法**：同一份 spec 餵給不同模型，吐出來的結構應該一致。
不一致 = 你寫得還不夠明確。

### CTCO 四格（比七欄位輕量的版本）

小需求用這個就夠：

| 格 | 放什麼 |
|---|---|
| **C**ontext | 背景與輸入 |
| **T**ask | **一句話**講清楚任務 ★ |
| **C**onstraints | 硬約束 |
| **O**utput | 輸出格式 |

### 為什麼「刪掉過程，給它形狀」

越強的模型，越不需要你教它怎麼做：

| ❌ 保母型 | ✅ 給結果形狀 |
|---|---|
| 第一步：收集資料 | 要預測什麼？ |
| 第二步：特徵工程 | 好的結果長什麼樣？ |
| 第三步：調參 | 用什麼指標衡量？ |
| 第四步：錯誤分析 | |

你教的步驟會限制它——它只能照你想到的路走。**給目標，讓它自己找路。**

### 二元判準怎麼寫

```
① 拆成可觀察的條件
   「有禮貌」→「結尾有致歉或感謝」

② 用 AND / OR 接成可以核對的句子
   「結尾有致歉或感謝 AND 沒有出現命令句」

③ 想幾個負例，確認擋得住
   負例：「請自行處理。」→ 應該 fail ✓
```

**為什麼不用 1–10 分**：
```
❌ 1–10 分 —— 不可重現。今天給 7 分，明天同一個東西給 5 分
✅ 對 / 錯 —— 可以加總成通過率：對的筆數 ÷ 總筆數
```

### 誰來當裁判

| 答案性質 | 裁判 |
|---|---|
| 有標準答案 | **程式 assertion** ★ ——**能用程式判就別請 LLM** |
| 有結構要求 | schema 驗證（Pydantic / JSON Schema） |
| 有參考資料 | 比對來源，檢查每個宣稱都指得出出處 |
| 沒有標準答案 | LLM-as-judge（**後備手段**） |

LLM-as-judge 的兩個陷阱：
1. **別讓球員兼裁判**——同一家模型自己審自己，對自家評分偏高
2. 裁判只回 `{pass: true/false, reason: "..."}`，**不要讓它給分數**

### 為什麼要 10 筆

少於 10 筆，一筆就佔 10%，雜訊蓋過訊號。
你會看到通過率從 6/8 變 7/8 就以為改好了，其實只是那一筆剛好過。

### 改進優先序（S4 會用到）

發現通過率不夠時，**先便宜後昂貴**，每動一步就回來跑同一份考卷：

| 順序 | 做法 | 成本 |
|---|---|---|
| ① | 改指令措辭 | 最低 |
| ② | 加 few-shot 範例 | 低 |
| ③ | 改結構（schema / 檢索方式） | 中 |
| ④ | 換模型 / 微調 | 最高 |

**先做失敗模式聚類，再改。** 消滅一整類，不要一筆一筆救火。
