## 課堂 15 分鐘版

**老師講**（5 分）：

1. 上午的 v0 丟掉。**這次重新開始**——差別是這次有測試、有考卷、有版控
2. TDD 的 GREEN 步驟「寫最少 code 讓測試過」**就是 KISS 本身**，不是額外負擔
3. 寫完不是結束。**跑 `/next`，用考卷把它從「能動」推到「夠好」**

**學生做**（80 分）：三段——拆任務（10）→ TDD（50）→ 跑迴圈（20）。

老師在第 50 分鐘要喊一次：**「還在寫 code 的人，停下來跑 `/review`。」**
（最常見的失控是學員一路寫到收工都沒驗證過。）

## 動手

1. 拆任務
   ```
   > 內建 plan 模式
   ```
   確認 `tasks/sprint-current.md` 的 Now 只有 **1–3 個** task。

2. 跑第一輪 TDD
   ```
   > /tdd
   > 實作 T-101
   ```
   看著它跑 🔴 RED → 🟢 GREEN → 🔵 REFACTOR。**紅燈那步不要跳過**。

3. 重複第 2 步直到 Now 的 task 都完成

4. 驗證
   ```
   > /review
   ```
   五維度全綠才往下。

5. **跑考卷，跟基線比**
   ```bash
   # 跑 evals/ 裡的腳本
   ```
   ```
   基線（S2）：___ / 10
   現在：      ___ / 10
   ```

6. 通過率不夠 → **跑迴圈**
   ```
   > /next
   > 把考卷通過率拉到 8/10 以上
   ```
   它會先跟你確認三條限制（範圍 / 評分 / 預算），再開始跑。

7. 收工並記錄
   ```
   > /review
   > /ship
   ```

## 回家展開版

### 四拍在這一站長什麼樣

```
① 劃邊界  → /next 開頭問你的三條限制
② 放它跑  → AI 改一版，你不插手
③ 打分數  → 跑 evals/，得到一個數字
④ 收判斷  → 看曲線、抽查最好的、決定收工或再跑
```

**第④拍最容易被跳過。** 分數上升就以為好了——但分數可能被規避
（reward hacking：它找到讓考卷過但實際更糟的做法）。**一定要抽查。**

### 分數上升但你覺得變糟了？

這是**好消息**。你發現了考卷的漏洞。

```
考卷說「輸出字數 ≤ 原文 20%」
    ↓
AI 學會了：直接回「本文摘要如下：無」→ 字數超少，通過 ✓
    ↓
你發現了 → 補一題進考卷：「輸出必須包含原文至少 3 個關鍵詞」
```

**每次抓到一個規避手法，考卷就變強一次。** 這是考卷會增值的原因。

### 連續兩輪分數沒動怎麼辦

停下來，三種可能：

| 可能 | 怎麼判斷 | 修法 |
|---|---|---|
| 考卷抓不到重點 | 你覺得有變好但分數沒動 | 回去改考卷 |
| 邊界劃錯了 | 真正的問題不在這個檔案 | 重劃範圍 |
| 到天花板了 | 每輪改動越來越小 | 換做法，不是繼續調 |

**不要無限重試。** 這就是第三條限制（預算）存在的理由。

### TDD 三步的意義

| 步 | 做什麼 | 為什麼 |
|---|---|---|
| 🔴 **RED** | 寫一個會失敗的測試 | **強迫你先想清楚「正確長怎樣」** |
| 🟢 **GREEN** | 寫最少的 code 讓它過 | 防止過度設計——這就是 KISS |
| 🔵 **REFACTOR** | 在綠燈保護下改好 | 有測試當靠山，才敢改 |

**跳過 RED 的後果**：測試會傾向確認「現在這樣寫是對的」，邊界 case 全漏。

### 為什麼測試和考卷都要有

| | 測的是 | 失敗代表 |
|---|---|---|
| **測試** | 不會壞（迴歸） | 你改壞了既有行為 |
| **考卷** | 做得好（品質） | 這個版本沒有比上一版好 |

兩者不能互相取代。測試全綠但考卷 3/10 是很常見的狀態——
它表示「程式沒 bug，但做出來的東西不是使用者要的」。

### 改進優先序（先便宜後昂貴）

| 順序 | 做法 | 成本 | 通常提升 |
|---|---|---|---|
| ① | 改指令措辭 | 最低 | 意外地大 |
| ② | 加 few-shot 範例（**對格式，不是教推理**） | 低 | 中 |
| ③ | 改結構（schema 約束 / 換檢索方式） | 中 | 大 |
| ④ | 換模型 | 最高 | 不一定 |

**每動一步就回去跑同一份考卷。** 一次改兩件事，你分不清是哪件有效。

### 三層輸出保證（如果你的專案有 LLM 呼叫）

| 層 | 手段 | 保證什麼 |
|---|---|---|
| 1 | prompt 裡拜託它回 JSON | **什麼都不保證** |
| 2 | JSON mode | 弱：能解析，但有哪些欄位它說了算 |
| 3 | **Structured Outputs / schema** ★ | 強：**保證符合你的格式** |

**不要用 prompt 防漏欄位，要用 schema 讓漏欄位變成「不可能」。**

事後檢查 vs 事前約束的差別：事後檢查發現錯了只能重來；
事前約束是它每生一個字都被限制只能走向合法結構——**根本錯不了**。
