## 單元 1｜AI 時代的軟體開發典範轉移

**為什麼**：同一個需求，三年前是人一行一行寫；現在是人交代任務、AI 產出、人驗證與整合。工作方式變了，人的價值放在哪裡也跟著變。

### 重點：AI 從對話走向執行

```text
生成式 AI 對話  →  Copilot 程式補全  →  Coding Agent  →  多代理協作
「問它答案」        「它幫你寫下一行」     「它讀檔、改檔、跑指令」  「好幾個 agent 分工」
```

每往右一格，AI 能做的事變多，**人要檢查的東西也變多**。

### 重點：人的競爭力在哪裡

| 能力 | 為什麼 AI 時代更重要 |
|---|---|
| 領域知識 | AI 不知道你們公司的請假規章，也不知道哪條規則最常被抱怨 |
| 需求判斷 | 要做什麼、不做什麼，是決策，不是生成 |
| 架構與風險判斷 | 哪些事錯了會有人受傷，不能交給 AI |
| 驗收能力 | AI 說「完成了」不代表完成 |

FDE（Forward Deployed Engineer）、π 型人才（兩項專長＋廣度）都指向同一件事：**懂業務又懂得指揮 AI 的人**。這是趨勢觀察，不是預言。

### 通過訊號

- [ ] 說得出生成式 AI、Copilot、Coding Agent 三者的差別：AI 能動手做到哪一步

## 單元 2｜從傳統開發走向 AI 協作

**為什麼**：多數人第一次用 AI 寫程式的經驗是「三十秒做出畫面，然後改了兩小時越改越歪」。問題不在工具，在流程。

### 重點：四種做法，不是一條演進線

| | 瀑布式 | 敏捷 | Vibe Coding（沒有紀律） | SDD（這門課） |
|---|---|---|---|---|
| 誰寫程式 | 人 | 人 | AI | AI |
| 規格 | 厚重文件，一次寫完 | 用故事卡取代 | 沒有，靠對話 | 輕量 Markdown，是唯一事實來源 |
| 需求變更 | 很貴 | 每個 sprint 吸收 | 隨時改，改到哪算哪 | 先改規格、再改測試、再改程式 |
| 怎麼知道做完 | 驗收測試 | Sprint review | 「看起來可以」 | 每條需求都對到一個會失敗、再變綠的測試 |
| 最貴的東西 | 寫程式 | 溝通 | 改來改去 | **想清楚** |

瀑布和敏捷是**專案管理方法**；Vibe Coding 和 SDD 是 **AI 開發的實踐方式**。兩組可以交叉：敏捷團隊一樣可以用 SDD。Vibe 也不是錯，探索與做原型時它最快；要交付給別人用時，回到規格。

### 重點：Copilot 和 Coding Agent 差在哪

| | Copilot（補全／聊天） | Coding Agent（Claude Code） |
|---|---|---|
| 看得到什麼 | 你打開的檔案 | 整個專案資料夾 |
| 能做什麼 | 建議下一行、回答問題 | 讀檔、規劃、改多個檔案、執行指令、跑測試 |
| 人的角色 | 逐行接受或拒絕 | **下任務 → 審核計畫 → 審核結果** |

### 重點：AI 開發的四個核心限制

1. **它會替你做決定，而且不告訴你。**
2. **它記不住。** 對話清掉就忘了，只記得檔案。
3. **它答錯和答對一樣有自信。**
4. **它說「完成了」不代表完成。**

**一句話**：人負責收斂與決策，AI 負責發散與生成。

### 通過訊號

- [ ] 說得出 Vibe Coding 適合什麼時候、什麼時候該換成 SDD
- [ ] 背得出四個核心限制裡的至少三個

## 單元 3｜AI 時代的軟體工程與規格治理

**為什麼**：AI 讓「寫程式」變便宜，但「想清楚要寫什麼」沒有變便宜。規格就是把想清楚的結果寫下來，讓 AI 有東西可以對、讓人有東西可以驗。

### 重點：一個軟體產品怎麼誕生

```text
Plan ──▶ Build ──▶ Verify ──▶ Ship
 ▲                              │
 └────────── 回饋與變更 ◀────────┘
```

| 階段 | 回答 | AI 能幫 | 人不能放手 |
|---|---|---|---|
| Plan | 誰有什麼問題、做什麼、不做什麼 | 拷問你、整理文件、窮舉情境 | 決定範圍與規則 |
| Build | 怎麼做 | 寫程式、寫測試 | 審計畫、審 diff |
| Verify | 做對了沒 | 跑測試、找邊界 | 決定預期結果、親手驗收 |
| Ship | 安全地交出去 | 整理 commit、檢查清單 | 按下合併 |

### 重點：先確認誰有問題，再談功能

「我要一套請假系統」不是需求。要問：**誰**在請假時卡住？卡在哪一步？做好了，什麼數字會變？

### 重點：MVP 與 non-goal

| | 例子（請假系統） |
|---|---|
| Must-have | 員工填表請假、系統擋下錯誤日期、看得到自己的假單狀態 |
| Nice-to-have | 主管核准、額度檢查、AI 一句話請假 |
| Non-goal | 登入、通知、月報、人資後台 |

**Non-goal 要有理由。** 沒寫「不做什麼」，AI 會很熱心地幫你做。
**垂直切片**：從畫面一路穿到資料庫的一條最薄的路，比「先做完資料庫層」更早知道接縫對不對得上。

### 重點：傳統團隊的角色，AI 時代還在

PM、BA、SA、Architect、Developer、QA、DevOps 各自負責的決策沒有消失。AI 可以在每一棒幫忙起草，**但每一棒的簽核還是人**。

### 重點：四層文件

| 文件 | 回答 | 一句話例子 |
|---|---|---|
| **PRD** | 為誰做、做什麼、怎麼算做對（Why / What） | 「員工可以填表請假，送出後看到待審核」 |
| **SRS** | 系統必須做到的行為，一條一條可驗 | 「FR-02：結束日期早於開始日期時，系統拒絕並顯示錯誤訊息」 |
| **SAD** | 怎麼組起來（Architecture） | 「瀏覽器 → FastAPI → SQLite」 |
| **SDS** | 每一塊怎麼做（Detailed Design） | 「`POST /api/leaves`，欄位、錯誤碼、資料表」 |

上課 repo 再加兩份：前面的 **Brief**（為什麼做、不做什麼）與最後的 **Test Plan**（每條需求怎麼驗）。

### 重點：一條需求怎麼一路變成程式

```text
US-01 身為員工，我想填表請假，以便不用找主管口頭報備
  └─ AC-01.2 Given 開始 10/20、結束 10/19  When 送出  Then 顯示「結束日期不能早於開始日期」，不存檔
       └─ FR-02 系統必須拒絕結束日期早於開始日期的申請
            └─ API-01 POST /api/leaves 回 422，訊息同上
                 └─ TC-03 送出 10/20～10/19 → 422，資料表筆數不變
                      └─ @pytest.mark.req("TC-03", "AC-01.2")
```

這就是**追溯（Traceability）**。鏈斷在哪裡，就是哪裡有人偷偷加了東西或漏了東西。

### 重點：可驗收的需求

| ❌ 判斷不了 | ✅ 判斷得了 |
|---|---|
| 請假功能要好用 | Given 員工沒選假別 When 送出 Then 顯示「請選擇假別」，不存檔 |
| 日期要合理 | 結束日期不得早於開始日期 |
| 回應要快 | 送出後 2 秒內看到結果 |

Given / When / Then 裡不准出現「正確」「合理」「適當」「好用」。**至少一條要是失敗路徑。**

### 重點：怎麼避免 AI 把軟體改壞

```text
修改前：git 有乾淨的 commit、測試是綠的
   ↓
修改：AI 依規格改程式
   ↓
驗證：跑測試（TDD：先紅再綠）、人看 git diff、Code Review
   ↓
修改後：測試還是綠的、沒有秘密進版控 → commit
```

Git、TDD、Code Review、DevSecOps 都是**交付閘門**：AI 寫得再快，過不了閘門就不算數。

### 實作：把模糊需求改寫成驗收條件（20 分鐘）

| 軌 | 做什麼 |
|---|---|
| 全組 | 把「**請假功能要好用**」改寫成至少 3 條 Given / When / Then，其中至少一條是失敗路徑 |
| 全組 | 和隔壁組交換，各圈出一條「我判斷不了過了沒」的句子 |

### 通過訊號

- [ ] 說得出 PRD、SRS、SAD、SDS 各回答什麼問題
- [ ] 寫出 3 條 Given / When / Then，隔壁組判斷得了每一條過了沒

## 單元 4｜Claude Code 基礎操作

**為什麼**：讓 AI 動手之前，先知道怎麼讓它讀懂專案、怎麼看它做了什麼、怎麼叫它停下來。

### 重點：介面與常用操作

| 想做 | 怎麼做 |
|---|---|
| 啟動 | 在 repo **根目錄**打 `claude` |
| 指定一個檔案給它讀 | `@course/LEAVEBOT.md` |
| 先討論計畫、不准動手 | **Shift+Tab** 切到 plan mode |
| 清空對話（換下一個任務） | `/clear` |
| 壓縮對話（同一個任務太長） | `/compact` |
| 不知道下一步用哪個技能 | `/compass` |
| 看 MCP 連線 | `/mcp` |

### 重點：讓 AI 動手之前要確認什麼

| 確認 | 怎麼看 |
|---|---|
| 它在哪個目錄 | 啟動時的路徑；一律在 repo 根目錄 |
| 它要做什麼 | plan mode 先看計畫 |
| 它要執行什麼指令 | 權限詢問時**看完再按**，看不懂就拒絕並問它 |
| 它改了什麼 | `git status`、`git diff` |
| 改壞了怎麼回去 | `git restore <檔案>` |

**兩個新手最常踩的坑**：
1. **在子目錄啟動。** 技能讀得到，但專案根目錄的 hooks 不會生效。
2. **跑 `/init` 蓋掉專案大腦。** 上課 repo 已經有 `CLAUDE.md` 和 `AGENTS.md` 了，要讓它讀懂專案，請它讀檔，不要 `/init`。

### 實作

| 軌 | 做什麼 |
|---|---|
| 全組 | 用[唯讀探索提示](./appendix/prompt-book.md#單元-4唯讀探索)讓 agent 解釋上課 repo，先不准改任何檔案 |
| 全組 | 請它在 `README.md` 最後加一行字，跑 `git diff` 看它改了什麼，再用 `git restore README.md` 還原；`git status` 回到乾淨才算過 |

### 通過訊號

- [ ] 用一句話說得出上課 repo 是做什麼的
- [ ] 看過一次權限詢問，知道自己按下去的是什麼
- [ ] 會用 `git status`、`git diff` 確認 agent 改了什麼

## 單元 5｜Context Engineering 與 Agent Harness

**為什麼**：Prompt 只是 agent 讀到的一小部分。它每次啟動都會讀一組檔案，決定它要守什麼規則、會什麼技能、哪些事做不到。

### 重點：怎麼交代清楚一個任務

| 零件 | 例子 | 沒有它會怎樣 |
|---|---|---|
| **Goal** 要它做什麼 | 「產出 docs/02-prd.md」 | 它做它覺得有用的事 |
| **Context** 給它看什麼 | `@course/LEAVEBOT.md` | 它憑空想像你的需求 |
| **Constraints** 不准它做什麼 | 「不要替我決定公司制度」 | 它很熱心地多做 |
| **Success Criteria** 怎樣算完成 | 「跑測試，把輸出貼給我」 | 它說完成了，但沒跑過 |
| **Output Format** 長什麼樣 | 「用表格：編號、問題、選項」 | 你要自己整理 |

**Constraints 最常被漏掉，也最重要。**

### 重點：Harness 解剖

Agent ＝ 模型 ＋ 上下文 ＋ 工具 ＋ 權限 ＋ 工作流程 ＋ 回饋。**Prompt 不等於整套 agent 系統。**

用上課 repo 本身當標本，讀 [`course/HARNESS.md`](https://github.com/Zenobia000/leavebot-bootcamp/blob/main/course/HARNESS.md)。只要記住一張表：

| | 是什麼 | 強度 | 例 |
|---|---|---|---|
| **規則**（`CLAUDE.md` → `AGENTS.md`） | 每次對話都帶著的文字 | agent 大部分時候會遵守，**不是每一次** | 「說完成前要貼測試結果」 |
| **技能**（`.claude/skills/`） | 叫了才載入的流程 | 叫了就照流程走 | `/tdd`：先紅燈再綠燈 |
| **MCP**（`.mcp.json`） | 讓 agent 多出一組外部工具 | 給它**能力**，不是限制它 | 開瀏覽器點畫面、查最新文件 |
| **hook**（`.claude/hooks/`，登記在 `.claude/settings.json`） | 工具動作前後自動跑的腳本 | **做不到**，agent 繞不過去 | `git add -A` 被擋下 |

判斷口訣：**違反了會有人受傷的，做成 hook；其他寫成規則。缺的是能力，接 MCP；重複的流程，做成技能。**
**提示規則和可執行限制不是同一種東西。** 寫在 `AGENTS.md` 的「不准」是建議；hook 才是擋下來。

### 重點：文件和圖由誰產

| 產出 | 誰負責 |
|---|---|
| PRD、SRS、SAD、SDS、Test Plan | Claude Code ＋ `course/templates/` 的模板（`/grilling`、`/to-architecture`） |
| 流程圖、架構圖、ERD | **Archify** 技能（`.claude/skills/archify/`） |
| 測試案例與測試程式 | Claude Code ＋ `/tdd` |

Archify 只畫圖，不會產出 PRD 或 SRS。需要 Node 18 以上；沒有 Node 就用 Mermaid。

### 實作

| 軌 | 做什麼 |
|---|---|
| 全組 | 請 agent 跑 `git add -A`，看它被擋下。找出是哪個檔案擋的、在哪裡登記的 |
| 全組 | 打開 `.claude/skills/` 隨便讀一個 `SKILL.md`，說出它被叫起來之後會照什麼流程走 |

### 通過訊號

- [ ] 說得出「`git add -A` 被擋」是 `.claude/hooks/guard-git.sh` 做的，登記在 `.claude/settings.json`
- [ ] 說得出 `AGENTS.md` 和 hook 的差別：哪一個 agent 可以違反、哪一個不行
- [ ] 能把一個模糊任務改寫成 Goal／Context／Constraints／Success Criteria／Output Format 五段

## 單元 6｜Coding Agent 能力體驗 Demo

**為什麼**：先親眼看到 AI 做得到什麼，再學怎麼控制它。也要親眼看到它做錯。

### 重點：講師示範

講師在 `playground/` 用 Claude Code 從一句話做出一個「會議室預約」網頁，再一步步收斂。提示詞是附錄的 [D1-1 到 D1-4](./appendix/prompt-book.md#一d1-示範提示詞)。

| 段落 | 看什麼 |
|---|---|
| D1-1 一句話 | AI 只聽一句話能做到什麼？它替你做了哪些決定？ |
| D1-2 加上情境與限制 | 同一個網站，結構化提示詞的差別在哪裡？ |
| 執行紀錄 | 它讀了哪些檔、建了哪些檔、跑了哪些指令、讀到什麼錯誤 |
| D1-3 修一個問題 | 發現問題 → 描述差異 → 修改 → 預覽 → 確認 |
| 故意輸入錯誤 | 結束時間早於開始時間、兩筆預約撞期，它擋得住嗎？ |

**能執行、符合需求、品質可靠，是三件不同的事。**

| 觀察 | 你的紀錄 |
|---|---|

| 它做對的一件事 | |
| 它做錯、或擋不住的一個輸入 | |
| 如果要交給同事用，還缺什麼 | |

## 單元 7｜使用 Archify 建立專案規格

**為什麼**：剛剛的網站裡，有一堆決定只存在對話裡。對話會被清掉，下一個人（或下一個 agent）不會知道。要把它們變成可以追蹤的文件。

### 重點：從 vibe 走向規格治理

1. 請 AI 回顧剛剛的網站：**它做了哪些假設？哪些需求我們從來沒確認過？**（D1-4）
2. 把確認過的需求照模板寫成 PRD 草稿；沒確認的放進待決事項。
3. 用 Archify 把主流程畫成一張圖，人看圖找漏掉的分支。（D1-5）

### 實作
