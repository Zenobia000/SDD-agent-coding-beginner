# Prompt 魔法書

> 課程裡用到的提示詞。每一段都標了 **⚙️ 要換掉的地方**和 **🔒 不要刪的那一句**。
>
> 原封不動貼上的效果通常最差。這些提示詞的價值不在字面，在它們**限制 AI 的方式**。
> 投影片只放卡號，完整文字在這裡。

| 篇 | 用在 | 核心技巧 |
|---|---|---|
| [一、D1 示範提示詞](#一d1-示範提示詞) | D1 單元 4、6、7 | 先看 AI 能做什麼，再把對話收斂成規格 |
| [二、D2 提示詞卡 A–K](#二d2-提示詞卡-ak) | D2 投影片 33–43，一頁一張 | 讓 AI 問你；預期結果由人定；先紅再綠；不准改測試 |
| [三、通用技巧](#三通用技巧) | 隨時 | MECE、驗收條件健檢、修圖、Debug 救援 |

---

## 好提示詞的五個零件

| 零件 | 例子 | 沒有它會怎樣 |
|---|---|---|
| **Goal 要它做什麼** | `照 @course/templates/02-prd.md 產出 docs/02-prd.md` | 它會做它覺得有用的事 |
| **Context 給它看什麼** | `讀 @course/LEAVEBOT.md` | 它會憑空想像你的需求 |
| **Constraints 不准它做什麼** | `不要替我決定`、`不准改測試` | 它會很熱心地多做 |
| **Success Criteria 怎樣算完成** | `跑測試，把輸出貼給我` | 它會說「完成了」，但沒跑過 |
| **Output Format 長什麼樣** | `用表格：編號、問題、選項、影響` | 你要自己整理 |

**Constraints 最常被漏掉，也最重要。**

## 一、D1 示範提示詞

### 單元 4｜唯讀探索

```text
🔒 這一輪只讀，不要修改或建立任何檔案。
讀 @README.md、@AGENTS.md、@course/HARNESS.md。
用三段告訴我：
1. 這個 repo 是做什麼的
2. ⚙️＜哪個檔案會擋下危險的 git 指令，在哪裡登記＞
3. 如果我要開始做請假系統，第一個該讀的檔案是哪一個，為什麼
```

### D1-1 一句話做網站

講師在 `playground/` 示範。故意只給一句話。

```text
在 playground/meeting-room/ 幫我做一個會議室預約網頁。
```

看完輸出問全班：它替我們決定了哪些事？（幾間會議室、時段多長、能不能撞期……）

### D1-2 加上情境與限制

```text
在 playground/meeting-room-v2/ 重做會議室預約網頁（第一版留著，等一下要並排比較）。

情境：⚙️＜30 人的辦公室，3 間會議室：大、中、小＞，同事用手機和電腦都會開。
要能：選會議室、選日期、選開始與結束時間、填預約人，送出後在下方列表看到。
限制：
- 單一 HTML 檔，不要用任何框架或外部套件
- 資料存在瀏覽器的 localStorage 就好
🔒 先告訴我你打算怎麼做，我確認後再寫
完成後告訴我怎麼打開它。
```

> 這張卡沒有提「結束時間不能早於開始時間」，也沒有提「時段不能重疊」。看看 AI 會不會自己想到：單元 6 最後一段會回來檢查。

### D1-3 修一個問題

```text
⚙️＜描述你看到的問題，例：手機上預約列表的時間被切掉一半＞。
我期望的是：⚙️＜描述你要的樣子＞。
🔒 只改跟這個問題有關的地方，改完列出你改了哪幾行。
```

**描述差異，不要描述解法。** 說「我看到 X，我要 Y」，讓它決定怎麼改，你決定它改得對不對。

### D1-4 回顧假設：從 vibe 走向規格

```text
回顧 playground/meeting-room-v2/ 這個網站和我們剛剛的對話。
用表格列出：
1. 你自己做的假設（我們從來沒討論過，但你寫進程式的）
2. 我們確認過的需求
3. 還沒確認、但上線前一定要確認的問題
🔒 不要修改任何檔案。哪些假設要留，由我決定。
```

### D1-5 寫成 PRD 草稿並畫流程圖

```text
根據我們剛剛確認過的需求，照 @course/templates/02-prd.md 的格式，
產出 playground/meeting-room-v2/prd.md。
🔒 我沒確認的，放進「待決事項」，不要替我決定。
🔒 驗收條件寫成 Given / When / Then，至少一條是失敗路徑。

接著用 archify 把「預約一間會議室」的主流程畫成 workflow，
包含成功、時間錯誤、撞期三個分支，存在 playground/meeting-room-v2/。
🔒 只畫 prd.md 裡有的步驟。archify 不能用的話，告訴我原因，改用 Mermaid 寫在 prd.md 裡，不要假裝完成。
```

### 卡 A｜需求訪談

投影片 33。先問問題，不要急著開發。

```text
/grilling

你是一位資深企業系統分析師。讀 @course/LEAVEBOT.md 和 @docs/01-brief.md，
協助我們規劃好日子科技的請假系統。這次只做 brief 裡定義的基本範圍。

從使用者角色、主要流程、業務規則、例外情境、資料欄位、成功標準六個面向，
一輪最多問 6 個需要我們確認的關鍵問題；我們回答後，最多再問一輪就收斂，剩下的列成待決事項。
每個問題提供 2–3 個可能選項，並說明不同選擇對系統的影響。
⚙️＜例：我們最在意的是員工常常把日期填反＞

🔒 目前只做需求探索，禁止撰寫程式。
🔒 不要自行決定任何公司制度，規章沒寫的就問我。
🔒 等我們回答後再進行下一步。
```

### 卡 B｜PRD 與 User Story

投影片 34。接著卡 A 的對話。

```text
根據我們剛剛確認的需求，照 @course/templates/02-prd.md 產出 docs/02-prd.md。
模板裡的 💡 提示是寫給你的規則，要遵守，但不要出現在產出裡。

內容包含：persona、user flow（Mermaid）、epic、User Story、Acceptance Criteria。
User Story 用「身為＜角色＞，我想要＜任務＞，以便＜目標＞」。
規模：story ≤ 4、AC ≤ 10，每個 story 至少一條失敗路徑。
⚙️＜例：主管核准不在這次範圍，寫進 non-goal＞

🔒 區分「已確認需求」、「待確認問題」與「假設」三類。
🔒 不可自行捏造請假天數、假別資格或主管核准規則。
🔒 AC 裡不准出現「正確」「合理」「適當」；寫不出具體數字或訊息文字的，放進待決事項。
寫完後，列出三個最值得人工審查的地方。
```

### 卡 C｜SRS

投影片 35。`/clear` 後開始。

```text
讀已核准的 @docs/02-prd.md，照 @course/templates/03-srs.md 建立 docs/03-srs.md。

把主要需求轉成編號的功能需求（FR-01…，≤ 10 條），每條寫明：
輸入條件、驗證規則、正常行為、例外行為，
以及可測試的 Given / When / Then，並標出它來自哪條 US 或 AC。
一條只講一件事；出現「並且」「同時」就拆開。
⚙️＜例：NFR 至少寫一條「送出後 2 秒內看到結果」＞

🔒 PRD 沒寫到的行為不要自己加；規則尚未確定的標「待確認」，不可擅自填補。
🔒 先輸出追溯表（US/AC → FR）與缺口清單給我審查，我確認後再寫檔。
```

### 卡 D｜流程圖（Archify）

投影片 36。

```text
讀 @docs/03-srs.md，用 archify 建立「員工提交請假申請」的 workflow 圖。

🔒 以 SRS 為唯一業務規則依據，不得自行加入主管審批或通知。
🔒 圖存在 diagrams/。跑 archify 自己的驗證流程，回報實際產出的檔案路徑。
```

```text
存成 diagrams/submit-leave.md。
必須包含：填表、送出、驗證、存檔成功、資料錯誤分支；每個節點標 FR 編號。
```


### 卡 F｜測試案例

投影片 38。

```text
讀已核准的 @docs/02-prd.md 與 @docs/03-srs.md，設計 6–12 個有代表性的測試案例。

至少包含：正常輸入、必填欄位缺漏、日期順序錯誤、資料持久化（送出後再讀得到）、一個邊界情境。
⚙️＜例：開始與結束同一天、跨週末＞

用表格輸出：TC 編號、對應 AC 或 FR、測試情境、輸入、你建議的預期結果、你的信心（高/中/低）、風險。

🔒 「預期結果」只是你的建議，最後由我決定。
🔒 先不要寫任何測試程式。
等我確認後，照 @course/templates/06-test-plan.md 寫進 docs/06-test-plan.md，包含追溯矩陣。
```

> 最後一句🔒很關鍵。不寫的話，它的建議會被當成正確答案直接進測試。

### 卡 G｜拆票與骨架

投影片 39。兩軌同時做，各開一個對話。

**📋 規格軌：拆票**

```text
/to-tickets

依 @docs/05-sds.md 與 @docs/06-test-plan.md 切成兩張票：
issues/000-skeleton.md（骨架）與 issues/001-submit-leave.md（新增請假的垂直切片）。
每張票寫明：要讓哪些 TC 變綠、驗收指令、被哪一張票擋住。
⚙️＜例：進階挑戰都不要排進任何一張＞

🔒 每個 TC 只落在一張票裡。
🔒 先給我看清單，我確認後再寫檔。
```

**🛠️ 工程軌：骨架**

```text
做 @issues/000-skeleton.md。嚴格照 @course/STACK.md 的骨架段：

🔒 不要寫任何請假邏輯。
🔒 不要加白名單以外的套件，不要開 CORS。
```

### 卡 H｜垂直切片 TDD

投影片 40。

```text
/tdd

做 @issues/001-submit-leave.md：員工填表 → 驗證 → 存檔 → 「我的假單」顯示狀態。
相關規格：@docs/03-srs.md、@docs/05-sds.md ⚙️＜貼上票上指的段落編號，例：API-01、API-02、UI-01＞。

先給我看檔案修改計畫，我核准後照 TDD 做：
1. 從票上第一個 TC 開始，只寫測試，標 @pytest.mark.req("TC-xx", "AC-xx.x")，跑給我看它失敗

4. 下一個 TC，重複
```

### 卡 I｜除錯修復

投影片 41。

```text
.venv/bin/pytest 失敗了，輸出如下：
⚙️＜貼上完整錯誤訊息，不要只貼最後一行＞

先不要修改任何檔案。列出：
1. 失敗的證據（哪個測試、預期什麼、實際什麼）
2. 可能的原因
3. 最小的修復方式
4. 這個修復會不會影響其他需求或測試
我核准後你才動手。修完跑完整的 pytest，把結果貼給我。

🔒 不准修改任何測試檔。
```

> 「不准修改任何測試檔」是關鍵。不寫這句，AI 常常會選擇改測試讓它通過。

### 卡 J｜變更影響分析

投影片 42。

```text
需求變更：
⚙️＜同一位員工的假單日期不可重疊，待審核的也算。重疊時顯示「這段期間你已經有假單」。＞

先不要修改任何檔案。列出這個變更會影響的：
1. 文件：docs/ 底下哪幾份、哪幾段（PRD 的 US/AC、SRS 的 FR、SDS 的 API）
2. 測試案例：要新增或修改哪些 TC
3. 程式：哪些檔案、哪些函式
4. 風險：會不會讓現有的測試失敗

我核准後，依序：改規格 → 改 docs/06-test-plan.md → 寫新測試並跑給我看紅燈 → 改程式 → 跑完整回歸測試。
🔒 不准刪除或放寬既有的測試。
```

### 卡 K｜交付檢查

投影片 43。

```text
準備交付。依序做：
1. git diff --stat 與 git status，用白話整理這次改了什麼
2. 跑完整的 .venv/bin/pytest，貼出輸出
3. 從 docs/06-test-plan.md 的追溯矩陣隨機抽 3 列，打開對應的測試檔，確認標註存在、測的真的是那件事
4. 基本資安檢查：秘密沒有進版控（.env 在 .gitignore）、輸入有驗證、SQL 用參數化查詢
5. 產出交付檢查表：需求追溯、測試結果、資安檢查、git diff 摘要、已知風險
6. 擬一則 Conventional Commits 格式的 commit 訊息，⚙️＜例：feat(leave): …＞

🔒 沒有實際執行或驗證的項目，一律標「未驗證」，不能宣稱通過。
🔒 不要自己 commit，訊息給我看，我來 commit。
```

## 三、通用技巧

### MECE 檢查

```text
這是我列的 ⚙️＜功能 / 角色 / 情境＞ 清單：
⚙️＜貼上清單＞

用 MECE 原則檢查：
1. 哪些項目互相重疊？
2. 少了哪些類別？
3. 有沒有「其他」這種垃圾桶分類？
🔒 只指出問題，不要直接幫我重寫清單。
```

### 驗收條件健檢

```text
讀 @docs/02-prd.md 的驗收條件。
找出所有「交給一個沒參加討論的人，他判斷不了過了沒」的句子。

用表格輸出：編號、原句、為什麼判斷不了、建議改法。
🔒 不要直接修改檔案。
```

### 找測試的洞

```text
讀 ⚙️@＜測試檔＞ 和 ⚙️@＜被測的程式碼＞。
如果要你故意改壞程式碼、但不讓任何測試失敗，你會改哪裡？
列出 5 個這樣的位置。
🔒 不要真的改，只列出來。
```

這是破壞測試的反向版本：讓 AI 幫你找測試沒蓋到的地方。

### Mermaid 畫不出來

```text
這段 Mermaid 預覽時報錯：
⚙️＜貼上錯誤訊息與那段 Mermaid＞
修好語法。🔒 只改語法，不要增減任何節點或關聯。
```

### Debug 救援：AI 繞圈，越改越糟

先 `/clear` 開新對話，再貼：

```text
我在做 ⚙️@＜票＞。規格在 ⚙️@＜規格檔＞。
之前的嘗試失敗了，症狀是：⚙️＜一句話描述＞。

🔒 先不要寫程式。
1. 用你自己的話說明這張票要做什麼
2. 列出你打算的步驟
3. 列出你不確定的地方
我確認後你再動手。
```

### Debug 救援：不確定 AI 改了什麼


## 最常被刪掉、但最不該刪的五句話

| 這一句 | 擋住的問題 |
|---|---|
| 不要替我決定 | AI 默默做了你沒授權的產品決策 |
| 等我回答 | AI 自問自答，你只是在旁邊看 |
| 先不要寫程式 | AI 還沒搞懂就動手，改了一大堆 |
| 不准修改測試 | AI 改測試讓它通過，紅線形同虛設 |
| 沒驗證的標「未驗證」 | AI 說「完成了」，但根本沒跑過 |
