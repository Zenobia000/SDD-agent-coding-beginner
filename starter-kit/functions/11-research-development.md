# 研發：工程師要會拆任務、編排 AI 與驗收成果，團隊才能擴大交付

<p class="lede">AI 參與研發後，工程師的工作會延伸到定義問題、分派任務、協調代理與驗收成果。企業要同步改造任務分工、績效衡量與工作負荷管理，才能把更多程式碼轉成可交付的產品。先讓一個小隊做出可重現的交付流程，再決定是否擴大並行。</p>

## 現況證據

**研究**：METR 在 2025 年對 16 位熟悉自己專案的開源開發者、246 項任務進行隨機對照實驗，使用當時 AI 工具的任務平均耗時增加 19%。[^rd-metr] 這說明導入工具後仍要實測交付效率；它不代表所有團隊、所有工具都會得到相同結果。

**研究機構觀點**：DORA 2025 報告將 AI 描述為組織既有優點與缺點的放大器，強調要改善整個研發工作系統。[^rd-dora] 因此，研發文化轉型需要一起處理規格、測試、審查、整合與責任分工。

**本指南的建議框架**：用下面四步安排團隊訓練與試點，每一步都以可驗收的成果過關。這是規劃工具，尚未經過企業樣本驗證；它描述研發協作能力，和第 9 章的企業組織成熟度是不同層次。

看團隊操作方式時，可以辨識八種樣態。它們會同時出現在不同任務中，不能直接拿來替員工排名：

| 操作樣態 | 看得到的行為 | 主管要確認什麼 |
|---|---|---|
| 人工開發 | 人直接寫程式與排錯 | 哪些工作值得先試 AI，哪些仍需專業判斷 |
| IDE 內問答 | 用 AI 查語法、理解既有程式 | 建議是否被理解、查證及測試 |
| 大段產出直接套用 | 接收大量生成內容，驗證不足 | 這是品質警訊，先補驗收能力 |
| 以對話委派任務 | 工程師說明目標，由 agent 提出修改 | 任務邊界、驗收標準與高風險變更是否寫清楚 |
| 非同步協作 | agent 執行後，人檢視結果與紀錄 | 能否追溯修改、重現測試並拒絕不合格交付 |
| 多代理並行 | 多個 agent 同時處理不同任務 | 任務是否能獨立、介面是否一致、誰負責整合 |
| 代理互相干擾 | 改同一批檔案、反覆覆寫、測試失敗 | 這是整合失控，應減少並行並重切任務 |
| 編排與驗收 | 依規格分派、檢查、整合與升級例外 | 自動檢查涵蓋哪些風險，人工放行由誰負責 |

**這代表什麼**：離開 IDE、少看程式碼、同時開更多 agent，都不足以證明能力提升。應該看交付能否通過驗收，以及團隊能否解釋、追溯和修正結果。

## 先做這一件

**先挑一個低風險、可回復、測試結果明確的維護任務，讓一個小隊跑完「規格 → agent 執行 → 測試 → 人工審查 → 整合」。**

第一輪先由一個 agent 完成任務，記錄實際工時、重工與工具成本。流程穩定後，再試兩項互不衝突的任務並行，觀察整合是否吃掉省下的時間。

1. 寫清楚任務目標、可修改範圍、禁止事項與驗收標準。
2. 由工程師先確認規格與測試方式，再讓 agent 執行。
3. 指定一位整合負責人，將審查、修正與等待時間一起計入。
4. 用同類任務比較交付週期與品質；效果未達標時，先縮小任務或調整分工。

這裡的範圍以軟體研發為主。涉及硬體、韌體或產品安全時，還要納入相應的實機測試與工程驗證。

## 不能交給 AI 的決策

| 決策 | 為什麼 | 人要保留的責任 |
|---|---|---|
| 需求優先順序與驗收定義 | 牽涉客戶、商業取捨與品質標準 | 產品與技術負責人確認範圍、成功條件 |
| 架構與關鍵介面的核定 | 影響後續維護、相容性與跨團隊工作 | 技術負責人核定設計與變更 |
| 機密資料與工具權限開放 | 可能影響智財、正式環境與外部系統 | 資料與系統負責人核准授權 |
| 正式發布與回復決策 | 上線會影響真實使用者 | 依風險由具名負責人放行，並確認回復方式 |

## 加 AI 還是重建

**在既有流程加 AI**：保留版本管理、CI 測試、PR 審查和發布機制，讓 AI 參與文件、測試草稿與有邊界的修改。第一輪就把成本與重工納入基準線。

**用 AI 重新設計流程**：以規格與驗收標準建立任務清單，再由多個 agent 分工；每件任務有獨立工作區與分支，整合負責人統一驗收。Git worktree 可以讓同一儲存庫保有多個工作目錄與分支，[^rd-worktree] 但共同介面的變更仍要先協調。

主管的管理方式也要同步調整：

| 管理面向 | 具體做法 | 管理會議要看的結果 |
|---|---|---|
| 團隊分工 | 明確分配問題定義、代理委派、測試、審查與整合責任；先讓小隊完整跑通 | 卡在哪一個交接點，哪種能力需要培養 |
| 績效衡量 | 看通過驗收的交付、交付週期與品質；Token 和模型費用列入成本 | 是否更快交出可用成果，代價是否合理 |
| 工作負荷 | 訂定同時進行的任務上限，安排審查與除錯緩衝，每週檢視負荷 | 等待審查、切換任務與重工是否持續增加 |

## 雷區

**把 Token 消耗量改成績效排名。** 用量是投入，交付才是結果。鼓勵合理使用工具，也要讓團隊能說明每件交付的工具成本與人工成本；獎勵高消耗容易誘發無效重試。

**把少審程式碼當成升級。** 可以用規格、測試與工具降低重複檢查的負擔，但關鍵業務邏輯、資安與高風險變更仍需要人工判斷。

**把混亂視為升級必經階段。** 當多個 agent 反覆覆寫、介面不一致或整合失敗，就先減少並行數，重新切分任務與責任。

**把十倍產能或特定人數配比當成普遍承諾。** 團隊規模與效益倍數只能是待驗證的情境假設。先用同類任務和相同品質標準比較，再談編制與擴張。

**長時間高強度監看多個 agent。** 持續切換、審查與除錯需要管理。若重工、等待或疲勞回饋增加，先降低並行量、調整排程，再決定要增加哪些工具。

## 該量的三個指標

| 指標 | 怎麼量 | 多久看一次 |
|---|---|---|
| 驗收通過的交付數與交付週期 | 固定任務範圍與品質門檻，量從開工到驗收通過的中位時間 | 每週 |
| 交付品質與重工 | 測試失敗、發布後缺陷、回復次數，以及審查後重工時數 | 每週 |
| 每件驗收交付的總成本 | 模型與工具費用，加執行、審查、整合及修正的人工成本，再除以驗收通過件數 | 每個衝刺 |

另外每週檢視團隊負荷：同時在做幾件事、待審查佇列多長、成員是否需要更多緩衝。這些資訊用來改善排程，避免做成個人的消耗排名。

本季先完成一輪「一個小隊、一類任務、一套驗收標準」的試點。每次檢視都問三件事：交付有沒有更快、品質有沒有守住、整合與審查的負擔有沒有增加。三件事講得清楚，再擴大多代理協作。
