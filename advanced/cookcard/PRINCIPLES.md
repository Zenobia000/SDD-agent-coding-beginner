# 心法：AI 時代怎麼把軟體做出來

> 這一冊不教工具，不教語法，也不會叫你貼任何 prompt。
> 它只回答一個問題：**在 AI 能一次生出幾百行程式碼的時代，人還必須守住什麼？**
>
> 讀完約 40 分鐘。做完第二冊之後回頭再讀一次，你會看到不一樣的東西。

---

## 一句話

> **不確定的事情，用 Code 探索；確定下來的事情，才固化成文件、測試與 Contract。**

整本書都是這句話的展開。如果你只記得一句，記這句。

---

## 第 1 節｜文件不是開發的前置作業

傳統的文件觀念長這樣：

```text
文件寫完  →  開始開發  →  文件過期
```

三步驟，第三步必定發生。你一定看過某份 spec 打開來全是三年前的東西，沒有人敢刪也沒有人敢信。

AI 時代要倒過來：

```text
探索  →  得到認知  →  把「已經確定的」寫下來  →  繼續開發
  ↑                                              │
  └──────────── 又發現新事實 ←───────────────────┘
```

差別在文件的角色：

| | 舊觀念 | 這門課 |
|---|---|---|
| 文件描述的是 | 我們**預計**要怎麼做 | 我們**已經確認**的事 |
| 寫的時機 | 開發前 | 確定下來的當下 |
| 過期時 | 沒人發現 | 立刻和 code 對不上，會痛 |

**文件不是計畫書，是知識的保存格式。**

這件事對 AI 協作特別重要，理由在第 5 節。

## 第 2 節｜七條不變量

這七條不隨專案階段改變，也不隨工具改變。違反任何一條，症狀都很具體 —— 下表右欄就是你會在現場看到的東西。

### 1. 沒有會失敗的驗收訊號，就不要開始寫

「做完了」如果無法被反駁，那就不是一個工程宣稱，是一句感想。

Spec 的本質不是文件，是**一條現在會紅、之後會綠的命令**。寫不出那條命令，代表你還不知道什麼叫做完 —— 那就回去把需求問清楚，不要開始寫。

> **違反時的症狀**：你和 AI 來回改了兩小時，每次它都說「已修正」，但你始終無法判斷到底好了沒有。

### 2. 一次只動一個變數

一張票、一個 slice、一個 commit。壞掉的時候你要能二分。

AI 的產出速度會誘惑你一次改五個地方，因為「反正它一次就寫完了」。然後它壞了，而你不知道是哪一個造成的。

> **違反時的症狀**：`git revert` 的時候發現無法只退掉壞掉的那一塊。

### 3. 證據先於宣稱

說「測試過了」而拿不出輸出，等於沒測。

這條是 AI 協作最容易破的一條，因為模型會用非常有自信的語氣說它跑過了。**它的自信與它是否真的跑過，兩者完全無關。**

> **違反時的症狀**：你相信了「已通過」，隔天發現那個測試從來沒被執行過。

### 4. 可逆性決定速度

可逆的決定用猜的就好，錯了改回來很便宜。
不可逆的決定（schema、對外 API、刪除資料、公開發布）先開閘門再動。

**這條是全書最重要的一條**，因為它同時是第 3 節那張表的選擇函數。

> **違反時的症狀**：你用「反正之後可以改」的心情做了一個之後改不動的決定。

### 5. 邊界是防線，不是建議

輸入驗證、權限、秘密，要擋在系統邊界，不能靠人或模型「記得」。

寫在 prompt 裡的約束是**建議**；寫在 schema、hook、型別、CI 裡的約束才是**防線**。前者會在某次對話被繞過，後者不會。

> **違反時的症狀**：你在 AGENTS.md 裡寫了「不要硬編碼金鑰」，然後在 diff 裡看到一把金鑰。

### 6. 卡住時縮小範圍，不是想更久

把問題切到能被證偽為止。切不下去，就是你還沒理解它。

> **違反時的症狀**：你盯著一段兩百行的錯誤訊息想了二十分鐘，然後決定「整段重寫」。

### 7. AI 是工廠，人是閘門

AI 負責產出，人負責放行。人不放行就不通過 —— 這是唯一能阻止幻覺進入交付物的機制。

前六條是傳統軟體工程本來就有的。**第 7 條是 AI 時代新增的**，而且是唯一無法自動化的一條：一旦你把放行也交給 AI，整條防線就空了。

> **違反時的症狀**：你連續按了三十次「同意」，然後發現十次之前它就走錯方向了。

## 第 3 節｜四個 Mode：不變量恆常，強度隨確定性升級

七條不變量在任何階段都成立。變的只是**用什麼形式滿足它**。

| 不變量 | Explore（探索） | Stabilize（穩定） | Systemize（系統化） | Productize（產品化） |
|---|---|---|---|---|
| 1 會失敗的驗收訊號 | 手動可重現的檢查 | Acceptance Criteria | Contract test | E2E + SLO |
| 2 一次只動一個變數 | 一次驗一個假設 | 一張票一個 slice | 一次一個 module | 一次一個 release |
| 3 證據先於宣稱 | 跑一次貼輸出 | 測試綠燈 | CI 綠燈 | 監控 + Runbook |
| 4 可逆性決定速度 | 全部可丟 | ADR 記不可逆決定 | Contract 凍結介面 | Migration + 回滾計畫 |
| 5 邊界是防線 | 先不管 | 輸入驗證 | Schema + Auth | Security Spec |
| 6 卡住就縮小範圍 | 換做法重試 | 二分找壞掉的票 | 模組隔離 | Incident 分級 |
| 7 人是閘門 | 自己看一眼 | Review 一個 slice | 跨模組 review | Change Approval |

### 怎麼知道自己在哪一格

**不要問「我現在是第幾階段」。** 那會讓你把它當成流水線，然後開始焦慮「我是不是跳級了」。

改問這一題：

> **這個決定如果錯了，改回來要多少成本？**

- 幾分鐘 → 直接做，錯了砍掉重來（Explore）
- 幾小時，只影響自己 → 留一條 acceptance criteria（Stabilize）
- 幾天，會影響別的模組 → 先把介面寫成 Contract（Systemize）
- 改不回來，或會影響到使用者的資料 → 先有 migration 與回滾計畫（Productize）

**不變量 4 就是 Mode 的選擇函數。** 同一個專案裡，不同部分可以處在不同 Mode —— 這很正常，不是混亂。

## 第 4 節｜升級規則：只要問一個問題

學生最常問的是「我要不要寫 spec / ADR / 架構文件」。

不要問這個。問這一題：

> ### 這個知識如果不存在，AI 下一次會不會重新猜一次？

**會 → 就該固化。**

理由很實際：AI 每一次 session 都是失憶的。你這次辛苦談出來的決定，如果沒有落成檔案、測試或型別，下一次它會重新發明一個不一樣的版本，而你要重新吵一次。

固化不等於寫 Markdown。看知識的性質決定它該去哪裡：

| 這是什麼知識 | 固化成 | 為什麼不是別的 |
|---|---|---|
| 需求 | Spec | 需要人讀懂與爭論 |
| 決策與它的取捨 | ADR | 重點是「為什麼」，code 表達不了 |
| 介面長什麼樣 | **Contract**（schema / type / OpenAPI） | 機器可驗證，比文字精確 |
| 行為應該如何 | **Test** | 會自動失敗，不會過期 |
| 系統怎麼組起來 | Architecture | 一張圖 + 模組表，通常就夠 |
| 掛掉怎麼救 | Runbook | 半夜三點沒人想讀架構文件 |

## 第 5 節｜有些東西不該寫成 Markdown

這是 AI Coding 教學最容易走偏的地方，也是社群對 SDD 最主要的批評 ——「Markdown 地獄」：規格越寫越多、越來越沒人看，最後產生**虛假的安全感**。

**不要這樣：**

```markdown
API request 應該包含：
name、email、age
```

**要這樣：**

```python
class UserRequest(BaseModel):
    name: str
    email: EmailStr
    age: int
```

差別不是風格，是**可驗證性**：

| | Markdown 描述 | Schema / Type / Test |
|---|---|---|
| 寫錯了 | 沒人發現 | 立刻壞給你看 |
| 過期了 | 沒人發現 | 立刻壞給你看 |
| AI 讀到之後 | 「大概長這樣」 | 「你只能長這樣」 |

一句話：

> **Code、Schema、Test 能當真相的地方，就不要再維護一份會過期的文字真相。**

SDD 不等於 Markdown Driven Development。

## 第 6 節｜什麼時候該升級：四個可觀測的訊號

「感覺該寫文件了」不是訊號，是心情。下面四個是可以被觀測、可以被別人驗證的：

| # | 訊號 | 怎麼看出來 | 該固化什麼 |
|---|---|---|---|
| 1 | 有東西不能隨便改了 | **有第二個檔案 import 它**，或同一個介面被改超過三次 | Contract |
| 2 | 出現第二個模組 | 出現**第二個可以獨立啟動的行程** | Architecture |
| 3 | 反覆 regression | 同一個檔案**兩週內因不相關的改動壞過兩次** | Acceptance test / Integration test |
| 4 | 忘記為什麼 | 你打出「當初為什麼…」這句話 | ADR |

第 4 個最好用，也最容易執行：**當你發現自己在問「當初為什麼」，那一刻就是寫 ADR 的時刻。** 不需要判斷這個決定重不重要 —— 你會忘記，就代表它值得記。

## 第 7 節｜兩個會殺死這套方法的失敗模式

### 失敗模式一：永遠停在 Explore

Vibe 很爽，固化很痛。所以人會用「還在探索」當免死金牌，無限期停在第一格。

三個月後系統長得像義大利麵，沒有一條測試，沒有人知道任何決定是為什麼做的，而每個人都還在說「我們還在快速迭代」。

**解法**：第 6 節那四個訊號是可觀測的。訊號出現就是升級，不接受「再等等」。找一個人負責喊，或寫成 CI 檢查。

### 失敗模式二：為要丟掉的程式碼寫測試

Explore 階段的程式碼**本來就是要丟掉的**。為它寫自動化測試不只浪費時間，還會產生沉沒成本 —— 寫了測試就捨不得丟，於是一個爛方向被自己的測試保護著活了下來。

要分清楚兩件事：

| | 是什麼 | 什麼時候要 |
|---|---|---|
| **可重現的檢查** | 一條能再跑一次、輸出能比對的命令。**可以是手動的** | Explore 就要 |
| **自動化測試** | 會自己失敗、進 CI 的那種 | 決定保留才寫 |

分界線很乾脆：

> **「我打算保留這段程式碼」的那一刻，就是「寫測試」的那一刻。**

這也是「把確定下來的事情固化」的最小單位。

## 第 8 節｜三層迴圈

實際開發不是一條線，是三層巢狀迴圈。它們同時在跑，週期不同：

```text
外迴圈（天）      需求 → 規格 → 拆解 → 驗證 → 交付
  中迴圈（時）      一張票 → 一個 slice → review → 併入
    內迴圈（分）      紅 → 綠 → 重構
```

第二冊會讓你把三層都跑過。現在只要記得：

- **內迴圈壞掉**，你會覺得寫程式很痛苦（改一行等三分鐘才知道對不對）
- **中迴圈壞掉**，你會覺得專案很混亂（不知道現在在做哪一件事）
- **外迴圈壞掉**，你會做出一個沒人要的東西（每一層都很順，方向是錯的）

三層都要有各自的驗收訊號。這就是不變量 1 在三個尺度上的展開。

## 一頁複習

遇到任何情境，依序問這五題：

1. **我能寫出一條現在會失敗的檢查嗎？** 不能 → 需求還沒清楚，回去問。
2. **這個決定錯了，改回來要多少成本？** 決定該用哪一格的工程強度。
3. **這個知識不存在，AI 下次會不會重新猜？** 會 → 固化，並依性質決定去哪裡。
4. **這件事該用 Code / Schema / Test 表達嗎？** 可以 → 不要寫 Markdown。
5. **我準備放行了，證據在哪裡？** 拿不出來 → 不放行。
