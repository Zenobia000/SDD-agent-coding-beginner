## 單元 1｜AI 時代的軟體開發典範轉移（09:00–09:45，3 張）

> **目標**：讓學員說得出「工作方式哪裡變了」，帶著問題進入後面的課。**互動點**：01 舉手調查、03 自評能力圖。

### 01 軟體開發正在發生什麼改變？

- **核心訊息**：人從「自己寫程式」，轉成「指揮 AI 產出，再由人驗證與整合」。
- **畫面**：左右對照，同一個需求「做一個請假申請頁」。左欄是傳統做法：人寫需求 → 人寫程式 → 人測試，每格標「人」。右欄是 AI 協作：人寫需求 → AI 寫程式 → 人驗證，中間那格標「AI」。底下一行大字：「最貴的工作從『寫』換成了『想清楚』和『驗』」。
- **講稿**：
  1. 今天先問一個問題：同一個需求，兩年前和現在，你的團隊做法一樣嗎？
  2. 右邊那欄，寫程式那格交給 AI 了，但頭尾兩格還是人。這門課兩天都在練頭尾那兩格。
  3. 寫程式變便宜以後，「想不清楚」的代價變大了，因為 AI 會很快把錯的東西做出來。
  4. 這兩天的承諾：第二天結束時，你們手上有一個照規格做出來、有測試證明的功能。
- **互動**：舉手調查三題：「用過 AI 聊天工具」「用 AI 寫過程式」「AI 寫的程式上過正式環境」。記下比例，第 27 張回來對照。
- **時間**：12 分鐘（含開場自我介紹與兩天流程）。
- **轉場**：「右邊那格的 AI，這幾年是怎麼一路變過來的？」

### 02 AI 從對話走向執行

- **核心訊息**：AI 的能力從「回答」走到「動手」，人的角色從「操作者」變成「審核者」。
- **畫面**：橫向時間軸四站：生成式 AI（聊天回答）→ Copilot（程式補全）→ Coding Agent（讀檔、改檔、跑指令）→ 多代理協作。每站下面一行：「人在做什麼」，依序是「複製貼上」「按 Tab 接受」「下任務、審 diff」「分派、驗收」。不放年份細節，不展開完整 AI 史。
- **講稿**：
  1. 重點不是哪個模型比較強，是 AI 能碰到的東西越來越多：從一個對話框，到你的整個專案資料夾。
  2. 第三站是今天的主角。Coding Agent 會自己讀檔案、改程式、跑測試，跑完再告訴你「完成了」。
  3. 它能動手，所以「怎麼約束它」比「怎麼問它」更重要。下午會用一整個單元講這件事。
  4. ⚠️ 引用前查證：＜各站代表產品的發布時間；如要放採用率數字，需要有公開來源的調查＞。
- **互動**：無。
- **時間**：13 分鐘。
- **轉場**：「AI 會寫程式了，那人的價值剩下什麼？」

### 03 AI 時代，人的競爭力在哪裡？

- **核心訊息**：能寫程式的人變多了，懂領域、會判斷需求、看得懂架構的人才是稀缺的。
- **畫面**：T 型與 π 型能力圖並排。T 型：一根「技術」柱。π 型：兩根柱，「技術」＋「領域知識」，上方橫槓寫「需求判斷、溝通、架構」。右下角一個小框：FDE（Forward Deployed Engineer，派駐客戶現場、把 AI 落地到業務的工程師）一行定義。
- **講稿**：
  1. 這張圖不是在預測哪些職位會消失，是在問：你的哪一根柱子，AI 最難取代？
  2. PM、SA 的領域知識，加上這兩天學的規格方法，就能審查 AI 的產出，不用自己寫程式。
  3. 工程師的價值，從「寫得快」移到「判斷 AI 寫的對不對、架構合不合理」。
  4. FDE 這類角色在 AI 公司越來越常見，因為 AI 落地卡住的通常不是技術，是不懂業務。⚠️ 引用前查證：＜FDE 職缺或企業轉型的公開案例與來源＞。
  5. 企業轉型的重點是讓不同角色用同一套規格協作，第二天的分組就是這樣設計的。
- **互動**：學員在便利貼寫下自己的兩根柱子，各寫一個詞。不用分享，第二天分組時用得到。
- **時間**：20 分鐘（含互動 5 分鐘）。
- **轉場**：「接下來看團隊以前是怎麼一起做軟體的，AI 進來之後哪些事變了。」

## 單元 2｜從傳統開發走向 AI 協作（09:45–10:30，4 張）

> **目標**：分清楚 Waterfall／Agile（專案管理方法）和 Vibe Coding／SDD（AI 開發實踐）是兩個層次的東西，不是一條直線演進。**互動點**：06 找碴、07 舉手選邊。

### 04 軟體專案以前如何開發？

- **核心訊息**：瀑布式和敏捷式是處理「需求會變」的兩種策略，不是一個淘汰另一個。
- **畫面**：左右對照。左：瀑布式，五個階段一路往下的階梯，標「需求先凍結、一次交付、回饋在最後」。右：敏捷式，一個循環箭頭，標「短週期、每輪交付、回饋在每一輪」。下方三列比較：需求變更成本、交付節奏、回饋機制。
- **講稿**：
  1. 瀑布式適合需求穩定、出錯代價高的系統，例如法規或金融結算。
  2. 敏捷式適合需求會變的產品，靠短週期把錯誤早點抓出來。
  3. 兩種都還在用。真正的問題是：AI 進來以後，「寫」這一段變快很多，前後兩段要不要跟著改？
- **互動**：無。
- **時間**：10 分鐘。
- **轉場**：「先看寫程式這一段，AI 的角色怎麼變的。」

### 05 Copilot 與 Coding Agent 差在哪裡？

- **核心訊息**：Copilot 幫你寫一行，Coding Agent 幫你做完一件事。後者要的是任務和審核，不是補全。
- **畫面**：上下兩條流程。上：Copilot，「人打字 → AI 建議下一行 → 人按 Tab」。下：Coding Agent，「人下任務 → Agent 讀檔、規劃、改檔、跑測試 → 人審 diff 與測試結果」。下面那條的「人審」框用強調色。
- **講稿**：
  1. Copilot 還是人在主導，每一行都經過你的眼睛。
  2. Coding Agent 一次改十個檔案，你沒有逐行看過。所以你需要別的東西幫你把關：規格、測試、diff。
  3. 今天下午會實際看 Claude Code 怎麼做：它會先說計畫，你同意了它才動手。
- **互動**：無。
- **時間**：10 分鐘。
- **轉場**：「工具這麼強，很多人的第一個反應是：那我直接叫它做就好了。」

### 06 Vibe Coding 為何快速普及？

- **核心訊息**：Vibe Coding 做原型很快，但規格不清楚的東西，做得越快歪得越快。
- **畫面**：一個預先做好的網站截圖（講師用一句話生成的會議室預約頁）。左邊三個綠勾：「30 秒做出畫面」「看起來能用」「不用懂程式」。右邊三個紅叉：「結束時間可以早於開始時間」「兩個人可以訂同一間同一時段」「沒人知道它到底做了哪些決定」。
- **講稿**：
  1. Vibe Coding 的意思是：用自然語言跟 AI 一直聊，聊到東西看起來對了就好。
  2. 拿來做原型、驗證想法，它很好用，這點不用否認。
  3. 問題出在交付的時候：沒有人說得出它做了哪些決定、哪些情況沒處理。
  4. 右邊的紅叉，下午第 27 張會在現場重現一次。
- **互動**：找碴。給學員 1 分鐘看截圖，猜這個網站哪裡會出事。收 2–3 個答案。
- **時間**：12 分鐘。
- **轉場**：「那有沒有辦法保留 AI 的速度，又不要歪掉？」

### 07 SDD 要解決什麼問題？

- **核心訊息**：Spec-Driven Development 用一份人審過的規格引導 AI 生成、測試和修改。它跟 Vibe Coding 可以混用。
- **畫面**：左右兩欄。左欄「自由探索」：對話 → 原型 → 看看。右欄「規格約束」：規格 → 測試 → 生成 → 驗證。中間一個雙向箭頭，標「探索完，把決定寫回規格」。
- **講稿**：
  1. SDD 的核心是一句話：AI 寫程式之前，先有一份人審過、可以檢查的規格。
  2. 規格不是厚重的 Word 文件，是 AI 讀得懂、人驗得了的幾份 Markdown。
  3. 兩種方法可以一起用。先 vibe 出一個原型確認方向，再把確定下來的決定寫成規格，交給 AI 照著做。
  4. 這就是今天下午單元 7 和明天要做的事。
- **互動**：舉手選邊：「你的團隊現在比較像左邊還是右邊？」不評價，只看比例。
- **時間**：13 分鐘。
- **轉場**：休息 15 分鐘。回來看一個軟體產品從頭到尾是怎麼誕生的。

## 單元 3｜AI 時代的軟體工程與規格治理（10:45–12:30，8 張）

> **目標**：建立 Plan → Build → Verify → Ship 的全局觀，並且能把一句模糊需求寫成驗收條件。12–14 是下午和明天的橋梁，要放慢。**互動點**：09 拆需求、10 MVP 分類、14 改寫驗收條件。

### 08 一個軟體產品如何誕生？

- **核心訊息**：Plan → Build → Verify → Ship，再靠回饋回到 Plan。AI 加速的是 Build，其他三段還是人要把關。
- **畫面**：一整張大循環圖，四個大區塊順時針排。每塊底下兩行：「做什麼」「產出什麼」。Plan：需求與規格；Build：程式碼；Verify：測試與審查；Ship：版本與交付。回饋箭頭從 Ship 回到 Plan。Build 區塊貼一個「AI 主力」標籤，其他三塊貼「人把關」。
- **講稿**：
  1. 這是今天最重要的一張圖。後面每一張投影片，都在講這圈裡的某一段。
  2. 明天的 D2 就是沿著這一圈走一次：上午 Plan，下午 Build、Verify、Ship。
  3. AI 讓 Build 從幾天縮到幾分鐘。後果是 Plan 和 Verify 變成瓶頸，也變成價值所在。
  4. 回饋那條線很重要：交付出去發現問題，要回到規格改，不是直接改程式。
- **互動**：無。
- **時間**：8 分鐘。
- **轉場**：「先從 Plan 的第一步開始：誰有問題？」

### 09 做產品，先確認誰有問題

- **核心訊息**：「我要一套請假系統」不是需求，是一個解法。需求要從誰、痛在哪、在什麼情境下開始。
- **畫面**：上方一個對話框：「我要一套請假系統」。下方四格：使用者是誰？痛點是什麼？在什麼情境？做到什麼算成功？四格一開始是空的，講完一格填一格。
- **講稿**：
  1. 把這句話直接丟給 AI，它會做出一套「它覺得」的請假系統，有十個功能，其中八個你不需要。
  2. 先問：誰在痛？員工、主管，還是人資？三種人想要的東西不一樣。
  3. 痛點要具體：「主管每週花太多時間審假」和「員工不知道自己剩幾天特休」，是兩個不同的系統。
  4. 成功要能量：「變方便」量不了；「員工 1 分鐘內送出一張假單」量得了。
- **互動**：拆需求。兩人一組 5 分鐘，選一個角色，把四格填完。請 2 組念出來，比較兩組做出來的系統會差多少。
- **時間**：15 分鐘（含互動 8 分鐘）。
- **轉場**：「知道誰痛了，下一步是決定這次只做多少。」

### 10 MVP：哪些功能現在不需要？

- **核心訊息**：MVP 是一條能從頭走到尾的最小流程，不是把每個功能都做一點點。
- **畫面**：左右對照。左：完整 HR 系統的功能地圖，十幾個方塊（請假、核准、額度、出勤、薪資、報表、通知……）。右：只有一條橫向的細長路徑：「填表 → 驗證 → 存檔 → 看到狀態」，四格貫穿畫面、資料庫、API。下方三欄分類：Must-have、Nice-to-have、Non-goal。
- **講稿**：
  1. 左邊每個功能都做一點，結果是沒有一個能用。
  2. 右邊叫垂直切片：從畫面一路穿到資料庫，只做一條，但這一條是真的能用的。
  3. 明天的 MVP 就是右邊這條。主管核准、額度、通知，全部列進「之後再做」。
  4. Non-goal 要寫下來，而且要寫理由。沒寫的話，AI 會很熱心地幫你做。
- **互動**：MVP 分類。投影片列 8 個請假相關功能，全班用舉手把每個放進三欄之一。爭議最大的那個，問「不做會怎樣」。
- **時間**：12 分鐘。
- **轉場**：「範圍定了，傳統團隊裡是哪些人負責把它變成軟體？」

### 11 傳統團隊有哪些角色？

- **核心訊息**：AI 可以幫每一個角色做草稿，但每一棒的決定還是要有人簽名負責。
- **畫面**：橫向接力圖，七個角色依序排：PM → BA → SA → Architect → Developer → QA → DevOps。每個角色上方寫他的產出（需求、業務流程、系統規格、架構、程式、測試、部署），下方寫「AI 可以幫忙的事」（草稿、窮舉情境、畫圖、寫程式、產生測試、寫設定）。最底下一條橫線貫穿：「決策與簽核：人」。
- **講稿**：
  1. 這七個角色在小公司可能是同一個人，大公司可能是七個部門。
  2. 每一棒 AI 都幫得上忙，但它不能替你決定「這樣算不算做完」。
  3. 明天每組 3–4 人，會分成規格軌和工程軌兩邊，就是把這七棒壓縮成兩棒。
- **互動**：無。
- **時間**：8 分鐘。
- **轉場**：「每一棒交出去的文件，名字聽起來都很像。到底差在哪？」

### 12 PRD、SRS、SAD、SDS 差在哪裡？（重點頁）

- **核心訊息**：四份文件回答四個不同的問題：為什麼做、做到什麼、怎麼組起來、每塊怎麼做。越往下越技術，越往下越能直接拿來寫程式。
- **畫面**：四層金字塔，由上往下：
  | 層 | 文件 | 回答的問題 | 一句請假系統的例子 |
  |---|---|---|---|
  | Why | PRD（產品需求文件） | 為誰做、做什麼、怎樣算對 | 「身為員工，我想用表單請假，以便不用再填紙本」 |
  | What | SRS（軟體需求規格） | 系統必須做到的行為，一條一條可以驗 | 「FR-02：結束日期早於開始日期時，系統拒絕送出」 |
  | Architecture | SAD（系統架構文件） | 由哪些部分組成、資料怎麼流 | 「瀏覽器 → FastAPI → SQLite；驗證在後端做」 |
  | Detailed Design | SDS（系統詳細設計） | 每一塊的欄位、API、模組 | 「`POST /api/leaves`，錯誤時回 422 與錯誤訊息」 |
  
  右側一條細線標「Test Plan：每一層都要有對應的驗證方法」。
- **講稿**：
  1. 這四份文件不是四份報告，是一條鏈。上一層的每一句，下一層都要有人接住。
  2. 判斷一句話放哪份文件的方法：有技術名詞嗎？有 → SAD 或 SDS。沒有、但寫得成 Given／When／Then → PRD 或 SRS。
  3. PRD 是寫給人看的，PM 主寫；SRS 是寫給系統的，SA 主寫；SAD、SDS 是工程師的。
  4. AI 讀得懂這四份，前提是每一份都夠短、夠具體。明天每份都有模板，而且有上限：PRD 最多 4 個 story、10 條驗收條件。
  5. 你們不用背名字。記住四個問題就好：為什麼、做什麼、怎麼組、怎麼做。
  6. 實務上很多公司不會四份都寫。這門課四份都走一次，是為了讓你們知道每一層在擋什麼錯。
- **互動**：快問快答。講師念 4 句話，學員喊它屬於哪份文件。例：「資料存在 SQLite」（SAD）、「員工可以看到自己的假單」（PRD）、「`leave_requests` 表有 `status` 欄位」（SDS）、「天數計算必須扣除週末」（SRS）。
- **時間**：15 分鐘。
- **轉場**：「知道四層之後，看一條需求怎麼一路穿過它們。」

### 13 一個需求如何一路變成程式？（重點頁）

- **核心訊息**：每一層都用編號指回上一層，最後由一個測試接住。鏈沒斷，才說得出「這條需求被哪個測試驗過」。
- **畫面**：一條橫向的追溯鏈，五個方塊用箭頭串起來，每塊放一個真實的例子：
  ```text
  US-01                 FR-02                    API-01                    TC-03
  身為員工，             結束日期早於開始日期時，   POST /api/leaves           Given 開始 10/20、結束 10/19
  我想送出請假申請，  →   系統拒絕送出並顯示      →  驗證失敗回 422，       →   When 送出
  以便不用填紙本          「結束日期不能早於開始日期」 body 帶 error 欄位          Then 回 422，畫面顯示該訊息
  （PRD）               （SRS，來源：AC-01.2）     （SDS）                   （Test Plan）
                                                                           ↓
                                                         @pytest.mark.req("TC-03", "FR-02")
  ```
  鏈下方一行：「反過來查也要通：測試失敗了，順著編號找得到是哪條需求。」
- **講稿**：
  1. 這叫 Traceability，可追溯性。聽起來很官僚，其實解決一個很實際的問題：AI 說「完成了」，你怎麼知道完成了什麼？
  2. 從左往右看：PRD 說員工要送出申請；SRS 把其中一個驗收條件拆成系統行為 FR-02，並標明來源 AC-01.2。
  3. SDS 說這個行為由哪支 API 負責、錯誤時回什麼；Test Plan 寫出一個具體的測試案例 TC-03。
  4. 最後一步：程式裡的測試用 `req` 標註它驗的是 TC-03 和 FR-02。
  5. 反過來也要走得通：明天你們會故意改壞一行程式，看到 TC-03 失敗，順著編號就知道壞的是哪條需求。
  6. 中間任何一環沒編號，鏈就斷了，AI 就可以在中間偷偷加東西或漏掉東西，而你看不出來。
- **互動**：給學員另一條需求「天數計算必須扣除週末」，兩人一組 5 分鐘，把五格填完（不用寫程式，只寫一句話）。講師挑一組上台，全班檢查哪一環寫得太模糊。
- **時間**：18 分鐘（含互動 8 分鐘）。
- **轉場**：「剛才填 TC 那一格時，有人寫了『計算正確』嗎？這就是下一張要處理的問題。」

### 14 什麼是可驗收的需求？（重點頁）

- **核心訊息**：一條驗收條件，要讓沒參加討論的人也判斷得出「過了沒」。Given／When／Then 加上具體數字，是最簡單的寫法。
- **畫面**：上下對照。
  - 上（紅框）：「請假功能要好用」「日期要正確」「錯誤時要有適當提示」。
  - 下（綠框）：「Given 開始日期 2026-10-20、結束日期 2026-10-19，When 員工送出，Then 系統拒絕，並顯示『結束日期不能早於開始日期』」。
  
  右側三欄分類，每欄放一個例子：
  | 正常情境 | 錯誤情境 | 邊界情境 |
  |---|---|---|
  | 10/20 到 10/21，送出成功，天數 2 | 沒選假別就送出，顯示「請選擇假別」 | 10/23（週五）到 10/26（週一），天數是 2，不是 4 |
  
  底部一條規則：「禁用字：正確、合理、適當、友善、好用」。
- **講稿**：
  1. 上面三句話，十個人會有十種解讀，AI 會有第十一種。
  2. Given 是前提狀態，When 是使用者做的事，Then 是看得到的結果。三段都要具體到可以照著做一次。
  3. 每個需求至少要有一條錯誤情境。只寫成功路徑的話，AI 會自己發明錯誤處理，而你不會知道它發明了什麼。
  4. 邊界情境最容易漏，也最容易出事。跨週末、跨月、半天，這些明天都會遇到。
  5. 寫不出具體數字的，代表這件事還沒決定。不要硬寫，放進「待決事項」，找負責的人決定。
- **互動**：改寫練習。投影片給 3 句爛驗收條件（「系統要能正確計算天數」「重複申請要擋下來」「送出後要有通知」），兩人一組 8 分鐘改寫成 Given／When／Then。抽 3 組念出來，全班挑出還有模糊字的地方。這是本單元的學員產出，請他們存成一份 Markdown 或拍照留著。
- **時間**：20 分鐘（含互動 12 分鐘）。
- **轉場**：「規格寫好了，AI 照著寫程式。那怎麼保證它不會把原本好的東西改壞？」

### 15 如何避免 AI 把軟體改壞？

- **核心訊息**：每一次修改都要有前後兩次驗證。Git 讓你回得去，測試讓你知道壞了沒，Review 讓第二雙眼睛看過。
- **畫面**：循環圖：修改前（Git 存檔點、測試全綠）→ AI 修改 → 修改後（跑測試、看 diff、Review）→ 通過才 commit，不通過回到存檔點。外圈標五個交付閘門：Git 版本管理、TDD、Code Review、DevSecOps（基本安全檢查）、人工驗收。
- **講稿**：
  1. AI 改程式很快，所以壞得也很快。重點不是不讓它改，是改了之後馬上知道有沒有壞。
  2. TDD 是先寫測試、看它失敗，再讓 AI 寫程式讓它通過。測試就是你給 AI 畫的紅線。
  3. Git 是存檔點。AI 改壞了，回到上一個存檔點，不用逐行找哪裡錯。
  4. 這張圖把上午收起來：Plan 寫規格，規格變成測試，測試擋住 AI 的錯誤。下午我們拿起工具，實際看這一圈怎麼跑。
- **互動**：無。上午總結：請學員說出上午記得最清楚的一個詞。
- **時間**：9 分鐘。
- **轉場**：午休。下午打開 Claude Code。

## 單元 4｜Claude Code 基礎操作（13:30–14:15，3 張）

> **目標**：每位學員在上課 repo 根目錄啟動 Claude Code，讓它解釋專案，並看過一次 diff。**互動點**：17 全班跟著做、18 看 diff。

### 16 今天要使用什麼工具？

- **核心訊息**：Claude Code 是在終端機裡工作的 AI，它看得到你的專案資料夾，可以讀檔、改檔、跑指令。
- **畫面**：一張實際操作畫面的截圖，標出四個區域：① 終端機與 Claude Code 對話區、② 編輯器（VS Code）的檔案樹、③ 專案資料夾（`leavebot-bootcamp/`）、④ 權限詢問的提示框。右側列常用指令：`/clear`、`/compact`、`@檔案`、`Shift+Tab`（計畫模式）、`/mcp`。
- **講稿**：
  1. 請大家打開上課 repo 的資料夾，在**根目錄**打開終端機，打 `claude`。一定要在根目錄，不然有些保護機制不會生效。
  2. 它不是聊天機器人，是能動手的 agent。它每次要改檔或跑指令，都會先問你。
  3. 編輯器開在旁邊，它改了什麼，你在檔案樹和 diff 裡看得到。
  4. 安裝檢核：每個人打 `hello`，有回應就舉手。沒回應的，助教過去處理。
- **互動**：全班安裝檢核。目標是 5 分鐘內全部舉手；沒過的人先跟旁邊的人共用畫面，不要卡住全班。
- **時間**：15 分鐘。
- **轉場**：「工具開好了。第一件事不是叫它寫程式，是叫它先讀懂這個專案。」

### 17 第一次讓 Claude Code 理解專案

- **核心訊息**：先讓 agent 解釋、提計畫，不要一開始就讓它動手。
- **畫面**：一段提示詞（大字）加上預期回答的截圖：
  ```text
  先不要修改任何檔案。讀 README.md、AGENTS.md 和 course/ 底下的檔案，
  用五句話告訴我：這個 repo 是做什麼的、明天要做出什麼、哪些檔案我不該改。
  ```
  下方標註：「先解釋 → 再計畫 → 你同意 → 才動手」。
- **講稿**：
  1. 這句提示的第一句最重要：「先不要修改任何檔案」。不寫的話，它可能很熱心地開始幫你整理。
  2. 看它的回答時，注意它讀了哪些檔案。工具列會顯示它開了什麼。
  3. 它說錯了也是好事，代表你的專案說明寫得不夠清楚。明天你們寫的規格，就是在防這種事。
  4. 再試一次計畫模式：按 `Shift+Tab` 切到 plan mode，請它「計畫怎麼在 README 加一段課前檢查清單」。它只會說計畫，不會改檔。
- **互動**：全班跟著打這兩段提示。請 2 位學員念出 agent 的五句話，比較兩個人得到的答案哪裡不同。
- **時間**：15 分鐘。
- **轉場**：「計畫看過了，如果要讓它真的動手，動手之前你要確認什麼？」

### 18 讓 AI 動手之前要確認什麼？

- **核心訊息**：確認它能碰哪裡、它改了什麼、危險的指令要你按頭。看 `git diff` 是最基本的審查。
- **畫面**：三欄對照表：
  | 確認什麼 | 怎麼看 | 例子 |
  |---|---|---|
  | 目錄範圍 | 啟動位置、它讀了哪些檔案 | 一律在 repo 根目錄啟動 |
  | 工具權限 | 每次改檔或跑指令前的詢問 | 不熟的指令選「否」，請它解釋 |
  | 變更內容 | `git status`、`git diff` | 每次說完成，先看 diff 再相信它 |
  
  下方一行紅字：「`rm -rf`、`git push --force`、`git add -A`：這類指令要你親自按同意，有些會被直接擋下。」
- **講稿**：
  1. 剛才那個 README 計畫，現在讓它真的改。它問你要不要改檔時，先別按，看它要改什麼。
  2. 改完之後，在另一個終端機打 `git diff`。這是你今天第一次審查 AI 的產出。
  3. 看完覺得不要，打 `git restore README.md` 就回去了。這就是上午說的存檔點。
  4. 有些指令它跑不了，是被擋下來的。是誰擋的，下一個單元揭曉。
- **互動**：全班讓 agent 改 README，看 `git diff`，再用 `git restore` 還原。用 `git status` 確認回到乾淨狀態才算過。
- **時間**：15 分鐘。
- **轉場**：「它為什麼會照這個 repo 的規則做事？那些規則寫在哪裡？」

## 單元 5｜Context Engineering 與 Agent Harness（14:15–15:00，4 張）

> **目標**：分清楚 Prompt、CLAUDE.md、Skills、Hooks、MCP、settings.json 各管什麼，知道哪些是建議、哪些是強制。**互動點**：19 改寫 Prompt、22 被 hook 擋下。

### 19 如何交代清楚一個 AI 任務？

- **核心訊息**：好的任務描述有五個零件：Goal、Context、Constraints、Success Criteria、Output Format。最常被漏掉的是 Constraints。
- **畫面**：上下對照。上：「幫我做一個請假頁面」。下：同一個任務的結構化版本，五個零件各用一個顏色標出來：
  ```text
  Goal：員工可以送出一張請假申請
  Context：讀 @course/LEAVEBOT.md 的公司規章
  Constraints：只做表單和送出，不做主管核准；不要新增套件
  Success Criteria：結束日期早於開始日期時拒絕送出；跑測試並貼結果
  Output Format：先列要改的檔案清單，我確認後再動手
  ```
- **講稿**：
  1. 上面那句，AI 會自己決定做多少、用什麼、怎樣算完成。三個決定都不是你做的。
  2. Constraints 是「不准它做什麼」。AI 的天性是多做，不寫就會多出你沒要的東西。
  3. Success Criteria 要寫成它可以自己檢查的事，例如「跑測試並貼結果」。只寫「做好」，它就會說它做好了。
  4. 這五個零件不用每次都寫滿，但每次下任務前，在心裡過一次。
- **互動**：兩人一組 5 分鐘，把「幫我做一個會議室預約網頁」改寫成五個零件。這份改寫等一下第 24 張會用到。
- **時間**：12 分鐘。
- **轉場**：「每次都寫這麼多很累。能不能有些東西寫一次就一直有效？」

### 20 Agent 為什麼需要 Harness？

- **核心訊息**：Prompt 只是一次對話。讓 agent 穩定做事，靠的是一整套 Harness：模型、上下文、工具、權限、工作流程、回饋。
- **畫面**：同心分層圖，由內到外：模型 → 上下文（Prompt、CLAUDE.md、檔案）→ 工具（讀檔、改檔、跑指令、MCP）→ 權限（settings.json、詢問）→ 工作流程（Skills）→ 回饋（測試、Hooks、diff）。最外圈標「Harness」。旁邊一句：「模型是引擎，Harness 是整台車。」
- **講稿**：
  1. 大家常以為 AI 好不好用，看的是模型強不強。實際上，同一個模型放在不同的 Harness 裡，表現差很多。
  2. 上下文：它這次看得到什麼。工具：它能做什麼。權限：它被允許做什麼。工作流程：它照什麼步驟做。回饋：它怎麼知道自己做錯了。
  3. 這五層都是用檔案設定的，就在上課 repo 裡。下一張逐一看。
- **互動**：無。
- **時間**：8 分鐘。
- **轉場**：「打開上課 repo，看這些檔案各管什麼。」

### 21 CLAUDE.md、Skills、MCP 的分工

- **核心訊息**：CLAUDE.md 是每次都帶著的專案規則；Skills 是叫了才載入的流程；MCP 是外接的工具能力。Archify 是一個 Skill，負責畫圖，不負責寫規格。
- **畫面**：上課 repo 的目錄樹，標出各檔案：
  ```text
  leavebot-bootcamp/
  ├── CLAUDE.md → AGENTS.md        ① 規則：每次對話都帶著
  ├── .claude/skills/<名字>/        ② 技能：打 /名字 才載入
  │   ├── grilling/                    讓 AI 拷問你 → 寫 PRD
  │   ├── to-architecture/             寫 SAD、SDS
  │   ├── tdd/                         先紅燈再綠燈
  │   └── archify/                     畫流程圖、架構圖、ERD
  ├── .mcp.json                     ④ MCP：context7 查文件、playwright 開瀏覽器
  └── course/                          課程素材，不是設定
  ```
  右側小表：「文件誰寫？Claude Code ＋ 模板。圖誰畫？Archify。」
- **講稿**：
  1. `CLAUDE.md` 只有一行，指到 `AGENTS.md`。裡面是這個專案的規則，例如「說完成之前要貼測試結果」。
  2. Skills 是一包寫好的工作流程。你打 `/grilling`，它就會照那份流程一輪一輪問你問題，而不是直接幫你寫。
  3. Archify 也是一個 Skill。它很會畫圖，但它不會寫 PRD。寫文件是 Claude Code 加上模板的工作，畫圖才交給它。
  4. MCP 是讓 agent 多一組外部能力，例如查最新的套件文件、開瀏覽器點畫面。能力越大，風險越大，不要亂加來路不明的 MCP。
- **互動**：全班打 `/compass`，看技能清單。請學員找出明天上午會用到的三個技能。
- **時間**：12 分鐘。
- **轉場**：「規則寫在 AGENTS.md，它大部分時候會遵守。但『大部分時候』夠嗎？」

### 22 Hooks、Settings 與執行邊界

- **核心訊息**：寫在 AGENTS.md 的規則是建議，agent 可能違反；寫成 Hook 的規則是強制，agent 繞不過去。
- **畫面**：兩欄對照：
  | | 規則（AGENTS.md） | Hook（.claude/hooks/） |
  |---|---|---|
  | 是什麼 | 每次對話都帶著的文字 | 動作前自動跑的腳本 |
  | 強度 | 大部分時候會遵守 | 做不到 |
  | 例子 | 「不准修改測試檔」 | `git add -A` 被擋下 |
  | 登記在哪 | `CLAUDE.md` 指過去 | `.claude/settings.json` |
  
  下方一段簡化的 `settings.json`，標出 `PreToolUse` 與 `guard-git.sh`。底部口訣：「違反了會有人受傷的，寫成 Hook；其他寫成規則；缺能力，接 MCP。」
- **講稿**：
  1. 請 agent 跑 `git add -A`。看它被擋下來。
  2. 擋它的不是 AI 自己懂事，是 `.claude/hooks/guard-git.sh` 這支腳本，登記在 `.claude/settings.json`。
  3. 差別在這裡：AGENTS.md 是請 AI 不要做；Hook 是讓 AI 做不到。
  4. 進階設定今天不要求大家操作。只要記得，哪一條規則被破壞會出大事，就該想辦法把它變成 Hook。
- **互動**：全班請 agent 跑 `git add -A`，被擋下後，請它說明是哪個檔案擋的。說得出 `guard-git.sh` 和 `settings.json` 的人舉手。
- **時間**：13 分鐘。
- **轉場**：休息 15 分鐘。回來看 AI 到底能做到什麼程度。

### 23 只用一句話，AI 能做到什麼？

- **核心訊息**：一句話就能得到一個能動的網頁。先看它做到了什麼，再看它替你做了哪些決定。
- **畫面**：大字顯示提示詞卡 **D1-1**：「幫我做一個會議室預約網頁」（放在 `playground/meeting-room/`）。旁邊一個空白的觀察表，兩欄：「它做得好的」「我沒說但它決定了的」。
- **講稿**：
  1. 這是最典型的 Vibe Coding。我只打一句話，什麼都不限制。
  2. 它在跑的時候，請大家看它的工具執行紀錄：讀了什麼、建了什麼檔案。
  3. 做完之後打開網頁。先說它好的地方：能選日期、能選會議室、能送出。
  4. 再問：會議室有幾間、叫什麼名字？時段是半小時還是一小時？這些我都沒說，是它決定的。
- **互動／Demo**：講師現場打 D1-1，開瀏覽器展示結果。學員填觀察表，至少寫 3 個「我沒說但它決定了的」。預期看到：它自己決定了會議室名稱、時段單位、是否需要填姓名、資料存在哪（通常是瀏覽器的 localStorage 或只在記憶體裡）。
- **時間**：15 分鐘。
- **轉場**：「如果我把要求說清楚一點，結果會差多少？」

### 24 如何讓網站更符合要求？

- **核心訊息**：同一個模型，結構化的提示詞得到的是「我要的」，不是「它猜的」。
- **畫面**：左右對照兩個網頁截圖：左是 D1-1 的結果，右是 D1-2 的結果。上方顯示提示詞卡 **D1-2**（Goal、Context、Constraints、Success Criteria、Output Format 五段）。
- **講稿**：
  1. 這一次用第 19 張學的五個零件。剛才大家兩人一組改寫過，我挑一份最完整的來用。
  2. 注意 Output Format：我要它先列要改的檔案，我同意了才動手。
  3. 比較左右兩個結果：右邊的會議室、時段、欄位，都是我指定的。
  4. 但還是有我沒想到的地方，例如兩個人訂同一間同一時段，我也沒說要怎麼處理。下一張看它做了什麼。
- **互動／Demo**：講師用學員改寫的版本（或預備的 D1-2）重做一次，左右並排比較。請學員指出右邊比左邊多遵守了哪些要求。
- **時間**：15 分鐘。
- **轉場**：「它做這些事的時候，到底在電腦上做了什麼？」

### 25 AI 執行任務時做了什麼？

- **核心訊息**：Agent 的每一步都留下紀錄：讀了哪些檔、建了哪些檔、跑了哪些指令、看到什麼錯誤。審查 AI 就從看這些紀錄開始。
- **畫面**：Claude Code 工具執行紀錄的截圖，標出五種動作：Read（讀檔）、Write／Edit（建檔、改檔）、Bash（跑指令）、讀到錯誤訊息、根據錯誤再改一次。右側放 `git status` 與 `git diff --stat` 的輸出。
- **講稿**：
  1. 往上捲剛才的對話，每個工具呼叫都在這裡。
  2. 它讀了什麼，決定了它知道什麼。它沒讀到的東西，它就會猜。
  3. 它遇到錯誤時，會讀錯誤訊息自己修。這是 Agent 比 Copilot 強的地方，也是它會繞圈的地方。
  4. 最後用 `git diff --stat` 看它總共動了幾個檔案、幾行。動的比你預期的多，就要問為什麼。
- **互動／Demo**：講師捲動紀錄，挑一個「讀到錯誤 → 自己修」的片段放大講解。如果這次沒有出錯，就展示 `git diff --stat`，請學員猜每個檔案是做什麼的。
- **時間**：12 分鐘。
- **轉場**：「看完它做了什麼，換你們來挑它的毛病。」

### 26 人如何與 AI 反覆協作？

- **核心訊息**：協作的節奏是：發現問題 → 描述差異 → 讓它改 → 預覽 → 確認。描述差異要具體，不要只說「不好看」。
- **畫面**：五步循環圖：發現問題 → 描述差異（現在是什麼、應該是什麼）→ 修改 → 預覽 → 確認。旁邊放提示詞卡 **D1-3** 的格式：「現在 ＜畫面哪裡＞ 是 ＜現況＞，我要的是 ＜期望＞。只改這一處，其他不要動。」
- **講稿**：
  1. 「這個不好看」AI 不知道怎麼改，它會隨便改一個方向，然後你再說不好看，這就是繞圈。
  2. 好的描述是對照：現在是什麼、應該是什麼。
  3. 「只改這一處，其他不要動」很重要。不寫的話，它常常順手把別的地方也改了。
  4. 每改一次就看一次預覽。不要一次堆五個問題給它。
- **互動／Demo**：請學員從右邊的網頁挑一個 UI 問題（例如按鈕太小、日期格式看不懂、送出後沒有提示），講師照 D1-3 的格式現場打給 AI，改完預覽。做兩輪。
- **時間**：15 分鐘。
- **轉場**：「畫面改好看了。那它做對了嗎？」

### 27 AI 做出來了，就代表做對了嗎？

- **核心訊息**：能執行、符合需求、品質可靠，是三件不同的事。Demo 能跑只證明了第一件。
- **畫面**：三層階梯：能執行（綠勾）→ 符合需求（問號）→ 品質可靠（問號）。旁邊是現場操作的截圖：預約時間填「開始 15:00、結束 14:00」，系統照樣接受，列表裡出現一筆時間倒過來的預約。
- **講稿**：
  1. 我現在輸入一筆預約：開始 15:00，結束 14:00。大家看它會怎樣。
  2. 它接受了。這不是 AI 笨，是我從頭到尾沒說「結束時間不能早於開始時間」。
  3. 這就是第 14 張講的：沒有寫出錯誤情境，AI 就自己決定怎麼處理。它的決定是不處理。
  4. 回到早上的舉手調查：有多少人的 AI 程式上過正式環境？上線之前，有人檢查過這種情況嗎？
  5. 怎麼避免？把這條寫成驗收條件，再寫成測試。明天你們會在請假系統上做一模一樣的事：結束日期早於開始日期。
- **互動／Demo**：講師現場輸入錯誤時間。如果 AI 剛好有擋（偶爾會），改試「兩個人訂同一間同一時段」或「預約過去的時間」，總有一個會漏（備案順序見 instructor-prep）。請學員再提一個他們覺得會漏的情況，現場試。
- **時間**：18 分鐘（含學員提案現場試）。
- **轉場**：「這些問題，與其靠我們一個一個試出來，不如一開始就寫下來。」

### 28 從 Vibe Coding 走向規格治理

- **核心訊息**：對話裡做的決定，對話一清掉就消失了。寫成文件，才能被追蹤、被審查、被下一個 AI 讀到。
- **畫面**：左邊是一長串對話紀錄（模糊處理），右邊是一份短短的「需求與假設清單」。中間箭頭標「整理成文件」。下方顯示提示詞卡 **D1-4**：請 AI 回顧這個網站的需求，列出它自作主張的假設。
- **講稿**：
  1. 下午我們跟 AI 來回了十幾輪，做了很多決定。明天換一個人接手，他看得到這些決定嗎？
  2. 請 AI 自己回顧：哪些是我要求的，哪些是它自己決定的。
  3. 它列出來的假設，每一條都要有人決定「對」或「不對」。這就是規格治理的第一步。
- **互動／Demo**：講師打 D1-4，把 AI 列出的假設投影出來。全班對每條喊「保留」或「改掉」，講師現場標記。預期看到 5–10 條假設，例如時段單位、會議室數量、是否要登入、資料存哪裡。
- **時間**：15 分鐘。
- **轉場**：「決定好了，接下來讓 AI 寫成正式的文件，再把流程畫出來。」

### 29 讓 AI 產出文件與視覺化流程

- **核心訊息**：文件交給 Claude Code ＋ 模板；圖交給 Archify。兩件事分開做，各自檢查。
- **畫面**：兩步流程：① Claude Code 讀模板 `course/templates/02-prd.md` → 產出 `playground/meeting-room-v2/prd.md`；② Archify 讀這份 PRD → 產出流程圖 HTML。下方顯示提示詞卡 **D1-5**。右下角一個小框：「沒有 Node？改請 Claude Code 在 PRD 裡畫 Mermaid 流程圖。」
- **講稿**：

  3. 第二步：讓 Archify 依 PRD 畫流程圖，畫出正常流程和失敗分支。

- **互動／Demo**：講師先示範一次（約 10 分鐘）。接著學員在自己的 `playground/` 做：可以用講師的會議室網站，也可以用自己 D1-1 做出的版本。20 分鐘內產出 PRD 草稿和一張流程圖。助教巡場，優先處理 Archify 跑不起來的人（改走 Mermaid）。
