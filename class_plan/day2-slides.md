# D2備課稿｜由規格走到交付

不要在一開始展示六份長文件；每次只開當前輸入、卡片與Gate。

## 09:00–09:45 單元8：從 D1 體驗接到 LeaveBot：確認問題與範圍

講師開場：昨天學會把創意說清楚；今天換共同題目，把決策留下來。

學生動作：讀題目、完成最小 Brief，訪談理由、過去日期與重複送出三項決策。

卡片：A（[同版提示詞](../handbook/site/prompts.html)）。

Gate：主線與延伸分清楚；三個問題已定案或由講師接手。

## 09:45–10:30 單元9：把共識寫成 PRD 與 SRS

講師開場：先定義可判斷的成功與失敗，再設計系統。

學生動作：先產 PRD 並審 AC，再把同一組承諾轉成 SRS；不一次寫完六份文件。

卡片：B,C（[同版提示詞](../handbook/site/prompts.html)）。

Gate：PRD 有成功與失敗條件；每個 AC 在 SRS 有對應，沒有新增範圍。

## 10:45–11:30 單元10：Archify 流程檢查與最小系統設計

講師開場：用圖找漏掉的錯誤分支，再定資料與 API。

學生動作：先把 SRS 畫成流程，再依固定技術棧建立最小 SAD／SDS。

卡片：D,E（[同版提示詞](../handbook/site/prompts.html)）。

Gate：圖與 SRS 一致；成功、拒絕與不存檔分支明確；API 與欄位可直接實作。

## 11:30–12:30 單元11：人定預期結果，選案例再拆兩張票

講師開場：AI 提議案例，預期結果與範圍由人審。

學生動作：選 6–12 個代表 TC，建立追溯表，拆骨架與表單切片兩張票。

卡片：F,G（[同版提示詞](../handbook/site/prompts.html)）。

Gate：每個 TC 有來源與人工確認的預期結果；兩張票能在新對話接手。

## 13:30–15:00 單元12：從空白骨架到一條可驗收的表單功能

講師開場：先接通首頁與 API，再逐一做紅燈、綠燈。

學生動作：先完成 000 骨架，再於新對話實作 001；第一個業務測試的紅燈由全組親眼確認。

卡片：H（[同版提示詞](../handbook/site/prompts.html)）。

Gate：表單、驗證、SQLite、我的假單接通；測試實際執行，拒絕輸入不存檔。

## 15:15–16:30 單元13：重現錯誤、修復，再走一次需求變更

講師開場：測試要能抓住錯誤，需求改動也要回到規格。

學生動作：在可還原的練習分支做一次講師指定的錯誤，再修復；將理由長度上限由 200 改為 100，先審影響。

卡片：I,J（[同版提示詞](../handbook/site/prompts.html)）。

Gate：有修復前後證據；依規格→案例→測試→程式更新，舊測試仍通過。

## 16:30–17:30 單元14：操作驗收與交付

講師開場：程式、文件與口頭宣稱必須對得起來。

學生動作：展示成功與失敗、核對一條追溯鏈、保存版本並說明未驗證項。

卡片：K（[同版提示詞](../handbook/site/prompts.html)）。

Gate：他人可依 README 啟動；測試與人工操作有證據，不含秘密或資料庫。

## 收尾提問

今天哪一條規格防止了AI自行決定？哪個測試真的抓到一次錯？如果換人接手，必須讀哪幾個檔案？每組用一條追溯鏈與成功／失敗操作回答。
