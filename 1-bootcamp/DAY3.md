## 單元 9｜自主期檢討與第二條切片

**為什麼**：自主期的「AI 誤解紀錄」是全課最誠實的教材。每一筆誤解，背後都是一句寫得不夠清楚的規格。

### 實作

**全班（40 分鐘）**：每組挑一筆最有代表性的誤解上台講三件事：

1. 規格原本怎麼寫
2. AI 做成什麼樣子
3. 你們把規格改成什麼

講師會把全班的誤解分類，通常會出現這幾種：

| 誤解類型 | 例子 | 下次怎麼避免 |
|---|---|---|
| 規格沒寫，AI 自己決定 | 半天假自動算成 4 小時 | 驗收條件寫具體數字 |
| 規格寫了，但很模糊 | 「合理的錯誤訊息」 | 把錯誤訊息的文字直接寫出來 |
| 兩份文件互相矛盾 | PRD 說可以撤回，架構沒有撤回的 API | 改完一份，檢查另一份 |
| 規格對，AI 沒讀到 | 規則寫在對話裡，沒寫進檔案 | 規則一律進檔案 |

**各組（50 分鐘）**：照自主期的節奏，做第二張票。

### 通過訊號

- [ ] 你們的規格至少改了一處，而且改動有 commit
- [ ] 第二張票開工了

## 單元 10｜AI 與人類的測試分工矩陣

**為什麼**：AI 很會窮舉，它可以在一分鐘內想出 50 種奇怪的請假情境。但它分不出哪些是真的會發生、哪些重要。**窮舉交給 AI，判斷交給人。**

### 重點：兩種測試，兩種分工

| | 驗收測試 | 邊界測試 |
|---|---|---|
| 來源 | 規格裡的驗收條件 | AI 窮舉 |
| 數量 | 少，每條驗收條件一個 | 多，幾十個 |
| 誰決定「預期結果」 | **人**（規格軌） | AI 提議，**人審核** |
| 失敗代表 | 沒做到需求 | 有沒想到的情況 |

**最危險的事**：讓 AI 同時決定「要測什麼」和「預期結果是什麼」，然後再讓它寫程式去通過。這等於讓學生自己出題、自己改考卷。

### 實作

**規格軌（主導）**：
1. 把每一條驗收條件變成測試案例表的一列，「預期結果」欄位由你填。
2. 讓 AI 窮舉 50 個邊界情境。
3. 逐一審查：每一個標記「保留 / 刪除 / 要問人資」。

**工程軌**：看規格軌保留下來的情境，標出哪些「現在的程式一定會失敗」。

### 可以這樣問 AI

```text
讀 @1_requirements.md 和 @1-bootcamp/LEAVEBOT.md 的公司規章。

針對「員工用一句話請假」這個功能，窮舉 50 個邊界情境。
涵蓋：日期表達方式、跨月跨年、半天、假日、額度不足、撞期、
奇怪的輸入、惡意的輸入。

用表格輸出：編號、輸入句子、情境說明、你認為的預期結果、你的信心（高/中/低）。
「預期結果」只是你的建議，最後由我決定。
```

> 注意最後一句。不寫的話，它的建議會被當成正確答案直接進測試。

### 通過訊號

- [ ] 測試矩陣裡，每一列的「預期結果」都經過人看過
- [ ] 50 個情境裡，你刪掉了一些，並且說得出為什麼
- [ ] 至少一個情境標了「要問人資」—— 那是規格的洞

## 單元 11｜TDD 循環與破壞測試

**為什麼**：測試是你給 AI 畫的紅線。有了它，AI 改程式碼時你不用逐行檢查，只要看測試是不是綠的。

### 重點：紅燈 → 綠燈 → 重構

```text
1. 紅燈  先寫測試，跑一次，它應該失敗（因為功能還沒寫）
         ↳ 如果它一開始就通過，這個測試沒有在測任何東西
2. 綠燈  讓 AI 寫最少的程式碼讓它通過
3. 重構  在測試保護下整理程式碼，測試要一直是綠的
```

**為什麼一定要先看到紅燈**：AI 寫的測試常常「怎樣都會過」。先看到它失敗，你才知道它真的在檢查東西。

### 實作 A：TDD 循環（60 分鐘）

**工程軌（主導）**：挑測試矩陣裡 3 個「現在一定會失敗」的情境，用 `/tdd` 一個一個做。

**規格軌**：每一輪都要親眼看到紅燈，才准工程軌讓 AI 寫實作。

### 實作 B：破壞測試法（45 分鐘）

這是今天的高潮。

1. 測試全綠的狀態下，**由規格軌**手動改壞一行程式碼。例如把特休的計算從 `>=` 改成 `>`。
2. 跑測試。**看它變紅。**沒變紅 → 你的測試有洞，回到單元 10 補。
3. 把紅燈的錯誤訊息交給 AI，只說「測試失敗了，修好它」，不告訴它你改了哪裡。
4. 看它能不能自己找到並修好。

### 可以這樣問 AI

TDD：

```text
/tdd

我要讓這個測試案例通過：
輸入「明天請特休」，員工特休剩 0 天 → 不可送出，訊息「特休剩餘 0 天」

先只寫測試，跑給我看它失敗。我確認之後你才能寫實作。
```

破壞測試的修復：

```text
pytest 失敗了，輸出如下：
<貼上完整錯誤訊息>

找出原因並修好。修完之後跑完整的 pytest，把結果貼給我。
不准修改任何測試檔。
```

> 「不准修改任何測試檔」是關鍵。不寫這句，AI 常常會選擇改測試讓它通過。

### 通過訊號

- [ ] 你親眼看到至少 3 次紅燈轉綠燈
- [ ] 破壞測試：改壞的那一行，測試有抓到
- [ ] AI 修復時，沒有動到任何測試檔（用 `git diff` 確認）

### 常見卡關

| 狀況 | 處理 |
|---|---|
| 測試一開始就是綠的 | 測試沒在測東西。檢查它的斷言（assert）是不是寫反或寫空了 |
| AI 修好了，但改了測試 | 退回，`git restore` 測試檔，重新下指令並加上「不准改測試」 |
| 破壞了程式碼，測試卻沒變紅 | **這是今天最有價值的發現。** 回單元 10 補一個測試 |

## 單元 12｜審查 AI 寫的程式碼

**為什麼**：測試只能抓到你想得到的錯。有些問題測試抓不到：寫死的密碼、沒必要的套件、看起來能跑但很難維護的結構。

### 重點：不寫程式的人也能審什麼

| 檢查項目 | 怎麼看 | 規格軌也能做嗎 |
|---|---|---|
| 改動範圍是不是只有這張票 | `git diff --stat` 看改了哪些檔案 | ✅ |
| 有沒有新增套件 | 看 `pyproject.toml` 或 `requirements.txt` 有沒有變 | ✅ |
| 有沒有寫死的金鑰、密碼 | 搜尋 `key`、`password`、`token` | ✅ |
| 剩餘天數是不是在規則模組裡算的 | 問 AI「特休剩餘天數在哪個函式算？」再自己打開確認 | ✅ |
| 錯誤處理是不是吞掉了錯誤 | 看有沒有空的 `except` | ⚠️ 需要一點程式基礎 |

### 實作

**兩組交換**：用 `/code-review`（Claude Code）或 `/review`（Codex）審查隔壁組的改動，再由人逐條判斷 AI 的審查意見哪些成立。

### 通過訊號

- [ ] 一份審查紀錄：AI 提了幾條意見、你們採納幾條、為什麼不採納其他的
